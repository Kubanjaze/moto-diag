## What shipped

- **Crash reports.** Every exception the API answers with a bare 500 is
  sent to Sentry as one event: its kind, its message (session tokens,
  emails and phone numbers blanked, cut to 500 characters), the stack as
  file, function and line, the request id, the method, the route template
  (never the path with its ids), the status, the version, the environment
  and the host name. Never a header, a body, a query string, a user or a
  customer. Mapped errors (404, 422, a domain error) send nothing.
- **Request timings.** One request in ten sends a transaction: the route
  template, the method, the status and the two times. `/healthz` and every
  `OPTIONS` request are skipped; a 429 never reaches the middleware.
- **The client** is the standard library (`src/motodiag/telemetry/`): one
  thread per worker, a queue of 100 that drops and counts rather than
  making a request wait, a pause on a 429, a warning at most once a minute,
  never the key in a log. Off without `MOTODIAG_SENTRY_DSN`; a malformed
  one is logged once and the API runs on.
- **`motodiag config show` masks the DSN.** `motodiag telemetry status`
  and `motodiag telemetry check`. The guide: `docs/guide/telemetry.md`.
- **The launch checklist** has a dated note: Sentry is a third destination
  for the privacy policy's "where the data goes"; the phone's binary is
  unchanged.
- **F244 filed:** `config show` prints `stripe_webhook_secret` in full.

### Crash reports: switch them on and prove they arrive

**Which computer:** the home desktop. **Which window:** the Ubuntu
terminal. Paste this whole block once 343 is merged to `master`. It brings
the server's copy up to date, checks that the settings file has exactly
one Sentry line and is private (without showing it), restarts the server
(it may ask for your Ubuntu password), says whether crash reports are on,
and sends one test message to Sentry.

```bash
bash <<'EOF2'
set -u
SRV=~/motodiag/server
ENVF=~/.config/motodiag/server.env
bad() { echo; echo "SOMETHING IS OFF: $1"; exit 1; }
git -C "$SRV" fetch -q origin master </dev/null || bad "could not fetch from GitHub"
git -C "$SRV" merge -q --ff-only origin/master </dev/null || bad "could not bring the server's copy up to date"
"$SRV/.venv/bin/python" -c "import motodiag.telemetry.sender, motodiag.cli.telemetry" </dev/null || bad "the server cannot load the new code; it may need: $SRV/.venv/bin/pip install -e '$SRV[server]'"
[ -f "$ENVF" ] || bad "the settings file $ENVF is missing"
[ "$(stat -c %a "$ENVF")" = "600" ] || bad "the settings file must be private: run  chmod 600 $ENVF  and paste this again"
COUNT=$(grep -c '^MOTODIAG_SENTRY_DSN=' "$ENVF")
echo "Sentry lines in the settings file: $COUNT"
[ "$COUNT" = "1" ] || bad "the settings file must have exactly one line starting MOTODIAG_SENTRY_DSN="
echo "Restarting the server (your Ubuntu password if asked)..."
sudo systemctl restart motodiag-api.service || bad "could not restart the server"
for i in $(seq 30); do curl -s -o /dev/null http://127.0.0.1:8000/healthz && break; sleep 2; done
curl -s -o /dev/null http://127.0.0.1:8000/healthz || bad "the server did not come back"
export PATH="$SRV/.venv/bin:$PATH"
set -a; . "$ENVF"; set +a
motodiag telemetry status </dev/null || bad "crash reports are not on"
motodiag telemetry check </dev/null || bad "the test message did not reach Sentry"
echo "ALL GOOD"
EOF2
```

Then, in a browser, open the Sentry project `motodiag-api` and look for the
message "telemetry check from …" with the event id the block printed.

Whoever merges copies the lines this prints (the status, the event id and
the ALL GOOD) into "After the merge" below. Nothing it prints contains the
key.
