## 4. The push guard — how it actually works

`.claude/settings.json` → `PreToolUse` on `Bash` →
`.claude/skills/closeout/pre_push_guard.sh`.

* It **filters itself** from `tool_input.command` on stdin. It does **not**
  use the hook's `if` field — see §5.
* It engages **only on a push that puts commits on `master`**. Phase-branch
  pushes pass. A guard blocking every push would block every
  work-in-progress push for a whole phase.
* It exits **0** before doing any work, and **0 on any internal error**. It
  can only ever exit 2 for a real `master` push with a real failure.

**If a hook ever blocks your shell:** edit `.claude/settings.json` with the
**Write tool**, which does not pass through a `Bash` matcher. Every instinct
at that moment is to reach for a shell, and the shell is what is gone.

## 5. Four facts about the tooling, measured — do not re-derive

1. **Skills are enumerated at session start, from the session root.** A
   skill created mid-session is not invocable in that session. Reproduced at
   both candidate roots. **Start moto-diag sessions at the repository root**;
   no symlinks, no `.claude/` at the parent.
2. **`PreToolUse` ignores the hook's `if` field in this build.
   `PostToolUse` honours it.** Measured with non-blocking marker hooks: same
   field, same value, same matcher, opposite behaviour. **Never add `if`
   back to the push guard.**
3. **Hook config loads with roughly one turn of delay.** A guard verified in
   the turn that installed it looks broken. Wait a turn before changing
   anything.
4. **A committed hook needs workspace trust.** A fresh clone has no guard,
   and **a hook that silently does not run reads exactly like one that
   passed** — which is why the test, not the hook, is the guarantee.

| 255C marque adjacency | the phantom "32 false `One` rows" | would have deleted **457 real rows across 108 models** |

for, and it needs a control like any other claim.**

produced the number.** Its instances include a reported `0` that answered a
neighbouring question, and a docstring calling a behaviour "deliberate" —

## 8. Standing rules this session operated under

* Regression reported with **commit hash and collected count**, always.
* Negative claims need a **positive control**; a check that cannot fail is
  not a check; break it on purpose and see it fail.
* **Targeted edits only** on source and tests — no `sed`, no `re.sub`, no
  index surgery. (A script with a completeness assertion is acceptable for a
  bulk move; assert that every line lands exactly once.)
* Deploy backups to `~/backups/motodiag/`, **retain 5**, never `/tmp`; print
  the before-state; dry-run on a copy first.
* ROADMAP rows **≤ 120 words**, counted by `roadmap_words.py` — body cell,
  whitespace-split, a markdown link is one word.
* F-numbers are **one global sequence across both repos**.
* Commit messages via **quoted heredoc** (backticks otherwise execute).
* Phase discipline: Step 0 → v1.0 committed *and pushed before code* →
  build → v1.1 → phase log → roadmap row → `implementation.md` row → merge →
  deploy → findings. Phase work happens on a `phase-*` branch.

## 9. Two habits that caught real defects — keep them

**Run a new check against something it was not written for.** `closeout`
run against 255C found two genuine gaps *and* a bug in itself. A check
exercised only on its own phase passes once and then rots silently — that is
literally how bug #6 was found.

**Read `git status` output instead of trusting that `add -A` did
something.** `workspace-docs/.gitignore` is an allowlist beginning with
`/*`; a commit and a push both succeeded while adding nothing, leaving a
`CLAUDE.md` pointing at three files that were not in the repository — the
dangling-pointer failure this phase had just built a check for.
