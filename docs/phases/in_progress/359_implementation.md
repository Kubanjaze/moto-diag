## Logic

### Migration 072 (`content_cleanup_starters_f158`)

It runs in this order, and every statement is keyed on the exact old text,
so that a re-run or a drifted row matches nothing:
1. **Retire:** `UPDATE workflow_templates SET is_active = 0` for the two
   starter slugs. Their descriptions become one line naming the templates
   that replace them:
   - `generic_ppi_v1`: `ppi_engine_v1` and `ppi_chassis_v1`;
   - `generic_winterization_v1`: `winterization_v1`.

   Their items are left as they are: they are history, and are shown
   nowhere.
2. **Re-point the two incoming links.** `ppi_engine_v1` and
   `ppi_chassis_v1` lose "Companion to generic_ppi_v1 (the quick check)",
   by deleting the clause; each still names the other.
3. **F163, chassis part:** `ppi_chassis_v1` item 2 loses three
   unsupported sentences, by deletion (listed in `359_step0.md`, S0-7).
4. **VIN step, if it survives the refute:** `ppi_chassis_v1` item 1 gains
   one cited sentence in its instruction, and the matching words in its
   pass and fail lines.
5. **Known-issue text, live rows only.** On a fresh database these rows
   do not exist yet when the migration runs: the loaders write them after
   `init_db`, from the edited seed.
   - Rows 31 and 4615 first: each field whose live text is the known old
     value is set to the seed's value, and no other field changes.
   - Then F158's substring edits, each keyed on (make, title, field, old
     substring).
6. **Rollback:** every step reversed, keyed on the new text, in reverse
   order.

**Where the text lives:**
- F158's edits are hand-written tuples in `migrations.py`, read before and
  after each edit.
- The two lagging rows' full old and new field texts are generated by a
  script from the live copy and the seed build, into
  `src/motodiag/core/migration_072_live_rows.py`, so no long text is
  retyped by hand.

### The seed JSON

The 25 rows' fields in 12 `known_issues_*.json` files are edited with the
Edit tool, one edit per sentence. The thermostat row's F158 edit is one of
them, and row 4615's seed is already the target. No identity column
(make, model, title) changes, so F129's duplicate-on-reseed cannot happen.

### `workflow show` on a retired template (`cli/workflow.py`)

When `is_active` is 0, `show` prints the name, "retired", and the
description (which names the replacements), then exits 1, with no items.
`list` already filters on `is_active`.

## Key Concepts

- **Retire** means `is_active = 0`, not a delete. The rows, items and
  history stay; the rollback restores them to active.
- **Keyed on old text** (F129's shape): an UPDATE matches only the exact
  old text, so a re-run is a no-op and a live row that drifted is left
  alone, and seen in the diff.
- **A seed build is not live:** loading the seed does not rewrite an
  existing row. Live changes reach live only through a migration.

## Decisions

1. The starters' descriptions become a retirement line naming the
   replacements. `show` prints it, so a user who types an old slug is
   sent somewhere.
2. Known-issue edits delete words where the sentence still stands without
   them, and rewrite only as far as removing the reference needs. They add
   no claim (K9's rule).
3. Internal wording outside F158's four patterns ("this project",
   "corpus", "refut…", "census", "this file") is not in the fixed set. It
   stays open under F158 and is named at close-out.
4. The VIN sentence is the only new claim, so it is the refute pass's
   centre. The pass also refutes every changed sentence against its
   neighbours.
