## S0-2. What the paste block can and cannot be pointed at

- `deploy.dryrun`, `apply_live` and `verify_live` already take `repo`,
  `db`, `migrate` and `parity_build` as arguments (Phase 358: "Paths are
  arguments, so tests run it on fixture databases"). The command line
  fixes `repo` to the script's own checkout and `migrate` to that
  checkout's `src/`.
- Live is found through `live.py`, which reads `MOTODIAG_LIVE_CONFIG` when
  it is set; backups go to `Path.home()/backups/motodiag`.
- So **a stand-in for live needs no new knob and loosens no refusal**: the
  trial sets `MOTODIAG_LIVE_CONFIG` to a file naming a copy of live, and
  `HOME` to a trial folder, so its backups, its retain-5 and its deploy
  checkout are the trial's own. The prompt's stop ("if the deploy tools
  cannot be pointed at a stand-in without loosening a refusal") does not
  arise.

## S0-3. A hole the plan must close: whose deploy code runs against live

`fleet_git.NEVER` keeps every rank off `.claude/skills/fleet/` and the
guards, but **not** off `.claude/skills/deploy/` or the rest of
`.claude/skills/closeout/` (`may_touch("engineer", …)` is true for both).
Running the branch's own `deploy.py` against live, as a builder does
today, would let a model-written branch change the refusals that guard
live. So the block runs **master's** deploy tools (the fleet's own
checkout, `~/motodiag/fleet/code`, which the operator moves onto master by
hand), and refuses a branch that changes anything under
`.claude/skills/deploy/` or `.claude/skills/closeout/`. Only the branch's
`src/` is imported, for the migration and the seed build — the change
itself, which the dry run on a copy shows before anything touches live.

## S0-4. Decisions (rule 1: none is a stop)

1. **The dry run runs in the block**, not in the dispatcher. Reasons:
   - the dry run takes a backup and retain-5 deletes the oldest; that is
     a change to the backup folder, and only the operator's paste should
     make it;
   - apply-live refuses unless live still equals the dry run's backup
     (bar `SERVER_WRITES`). In the block, the backup is seconds old when
     the apply runs; from the dispatcher it would be hours old, and any
     use of the server between would refuse the apply;
   - the dispatcher then reads live in one place only: `verify-live` on
     the resume, as the prompt asks.
   The comment cannot show the exact diff in advance; it says what the
   change does in one sentence (the Engineer's `live_change`) and names
   the tables in the scope file. The block shows the full change in plain
   words before it asks.
2. **The block's work is a script**, `.claude/skills/deploy/through_fleet.py`,
   so every refusal in it has a test and a fixture. The block itself is
   three lines: the script, the label off, ALL GOOD.
3. **Where it works:** a fresh clone of the fleet's mirror at the pushed
   commit, `~/motodiag/deploy/<phase>`, never the builder's checkout and
   never the server's. The diff and the answer are committed there (the
   deploy skill's "committed and unchanged"), and the live diff after the
   apply. Nothing is pushed from it: on the resume the dispatcher fetches
   those commits into the held clone, checks they change only the phase's
   three deploy files, and they go to GitHub with the close-out, through
   the push gate.
4. **The operator's answer** is saved, verbatim with its time, as
   `docs/phases/in_progress/<phase>_deploy_answer.md`, committed with the
   dry-run diff. The close-out round quotes it in the phase log, and the
   dispatcher refuses a `pr-ready` whose phase log does not carry it.
5. **The API** is stopped for the apply and started after, as the Mac's
   sequence does (`remote.py api-stop` … `api-start`), but only when
   `motodiag-api.service` serves the database being changed. On a
   stand-in it is left alone, so the trial never stops the real server.
6. **The resume** is `needs-hands` coming off a run held with
   `why: deploy`, as F221's `why: space` hold is today.
7. **The order of the Red Team and the apply** stays as today: the Red
   Team reviews after the close-out. A finding that would change an
   applied migration is a rule-1 stop: after a live diff is on the branch,
   any later change to `src/motodiag/core/migrations.py` refuses the
   `pr-ready`, and the fix round's brief says so.
8. **Q1** passes a migration only with the dry-run diff, the live diff
   (scope problems none, equal to the approved diff) and the answer
   committed, and `verify-live` run by the dispatcher outside the fence
   exiting 0. In the fence (no `live_check`), a migration still refuses.
9. **The planners:** a plan with a migration carries a section
   `## The database step` (what the change does to live, the tables and
   columns it adds, and that it alters or deletes no existing row). The
   Captain writes it; the XO and the Engineer read a migration as in scope
   only with it; a plan that alters or deletes existing live rows still
   lists that as a rule-1 stop.
