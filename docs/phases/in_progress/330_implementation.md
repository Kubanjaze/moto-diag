## Goal

A new shop today is set up one command at a time, by someone who already knows the commands: `motodiag shop profile init` for the shop, `motodiag user create` and `motodiag shop member add` for each person, `motodiag shop customer add` and `motodiag garage add` and `motodiag shop customer link-bike` for every customer and bike, `GET /v1/terms` and `POST /v1/terms/accept` for the terms, and `motodiag workflow run` for a first checklist. Nothing sequences them, nothing says which are done, and a shop with fifty bikes types fifty commands. The Step 0 report (`330_step0.md`) found no onboarding flow, no bike import and no staff setup anywhere in `src`, and classified the phase an extension: the pieces exist, and the wizard adds to them without changing what they do.

After this phase a new shop is onboarded from the server's command line in one sitting:

1. **`motodiag shop onboard run`** walks the owner through five steps, in order, each one skippable and each one safe to run again: the shop's profile; the owner's own login, made the owner of the shop; the staff, each with a login and a role; the Terms of Service, shown by their addresses and accepted by the owner for themselves (334 went before 330 "so that 330's onboarding can include the step", K84); and the bikes, imported from one CSV file or typed one at a time, each linked to its customer. It ends with the first diagnostic walkthrough: one workflow checklist walked through on the terminal, saving nothing, so the owner has seen a diagnosis before the first real bike arrives. The last screen says what was made and what to do next.
2. **`motodiag shop onboard import-bikes FILE`** is the import on its own, with a `--dry-run` that writes nothing: a shop's bikes and their customers, from a plain CSV with a header row, all rows checked before any is written.
3. **`motodiag shop onboard status`** says which steps are done, read from the tables that already exist. No new table, no migration, no change to live: the wizard writes only through the functions the existing commands call, and only new rows.

Every existing command keeps its behaviour. The wizard is a front door onto `create_shop`, `create_user`, `add_shop_member`, `record_acceptance`, `add_vehicle`, `create_customer`, `link_customer_bike` and the workflow walk; it does not change the profile init, any shop command, or the diagnostic workflow. If the build finds it must, the classification becomes a reshape and that is a stop, as the Step 0 report says.

**Why the command line and not the app.** The Step 0 report classifies this phase as an extension of the shop CLI, which already holds the first-time profile wizard; the signup flow that would trigger an onboarding screen (Phase 329) has not started; and every app screen so far has been its own row built by a session on the app's repository (303B, 334B, 372B; K81, K84, K98, K99). This plan ships the server-side wizard. An app screen for it, if the operator wants one, is a row of its own on the operator's word, named in the handoff's "What is open", not a change this plan makes under `src/`.

## Rule-1 stops anticipated

- **A real fork: none known.** The Step 0 report classifies the phase an extension of the shop CLI and leaves no second plan that would ship something different. Where this plan leaves a build choice (the exact wording of prompts and report lines, the dataclass or dict shape of `BikeRow` and `ImportReport`), either choice ships the same behaviour. **Five readings, recorded in the phase log and told to the operator with the pull request:** (1) the wizard is the server's command line, not an app screen or an API route, for the reasons under Goal; an app screen is a row of the operator's own making; (2) "bike inventory" is the shop's customers' bikes, not parts stock; (3) the shop's `owner_user_id` stays the default, and ownership is the `owner` role, as 303 built it; (4) the terms are accepted only by the owner present, for themselves, never for staff; (5) a bike is identified only by its VIN, and a row without one is added again on a second import, reported. If the Engineer finds that any of the five must change an existing command's behaviour to hold, that is the reshape the Step 0 report names, and a stop with kind `fork`.
- **A threshold or a rule's definition: none changed; anything that would is a stop.** The wizard keeps `MIN_PASSWORD_LENGTH`, `SHOP_ROLES`, `TERMS_VERSION`, `_sole_shop_id_or_fail`'s one-shop rule, `_resolve_shop_identifier`'s rule, the `VehicleBase` year range and `customer add`'s `shop_id` rule exactly as they are. Foreseeable stops, each with kind `threshold-or-rule`: a bike quota applied by the import (none today; the Shop plan has no bike limit, 404); accepting the terms on behalf of another person; a customer match looser than the exact phone or exact name above; any change to `TERMS_EXEMPT_PATHS`, to a switch's default, or to an existing command's output or options.
- **A test that cannot be made green: none known.** If an existing test pins the list of `shop` sub-groups, `register_shop`'s registrations, the guide's section text, or the count of CLI commands, it is updated with the reason in the commit message after a grep; a pin this phase cannot satisfy inside this plan is a stop.
- **A login or a credential: none in the build.** Every test makes fixture users with fixture passwords on a temporary database (`cli_db`'s form), and no test reads live (244H). The build creates no login for a real person: running the wizard on live for the first shop is the operator's own act, on a later day, from the handoff's block, after a backup. If anything in this phase would require the wizard to run on live before the close-out, that is a stop.
- **A live-database change that alters or deletes rows: none.** The phase has no migration and no database step. The wizard and the import only add rows, through functions that update or delete nothing (`create_shop`, `create_user`, `add_shop_member` reactivates an existing row only when the same member is re-added, which the wizard's "already done" path never does; `record_acceptance`, `add_vehicle`, `create_customer`, `link_customer_bike`). The live step after the merge is read-only (`status`). Any write to live inside the phase, or any step that would update or delete an existing row, is a stop.
