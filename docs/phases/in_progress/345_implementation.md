# Phase 345 — Cloud backup + sync

**Version:** 1.0 | **Tier:** Standard | **Date:** 2026-10-31

---

## Goal

Live is one SQLite file and three upload folders on the home desktop, and today the only copy of it is on the same disk: `deploy.py backup` (Phase 382) writes a backup-API copy into the operator's backups folder and keeps five (K27). A failed disk, a stolen machine or a bad migration that slips every gate loses the shop's data. Step 0's census (run on this branch from `2df4799`) found no offsite copy, no encryption and no restore tool anywhere in `src/`: 0 hits for `offsite`, `encrypt` and `point-in-time`, 0 for `Backblaze`. The hits Step 0 left unexamined were read for this plan: `rg -n -i "\bS3\b|boto|cloud|restore|offsite" src` finds Whisper's "cloud transcription", the word "restore" in docstrings and migration rollbacks, and nothing that copies, syncs or restores the database. So this is an extension, as Step 0 classified it: new code beside the local backup, changing nothing the local backup does.

This phase ships the row's three promises, as the operator decided them in K62:

- **Offsite encrypted backups.** A snapshot of live (the database, by SQLite's backup API, and every uploaded video, photo and audio file) is encrypted on the desktop with a passphrase only the operator holds, and uploaded to one private Backblaze B2 bucket through its S3-compatible API, with an application key limited to that bucket. The key lives only in `~/.config/motodiag/backup.env` (mode 600) under the four names K62 gives, and never in the repository, a log, an issue, a chat or the fleet's fence. The ciphertext is useless without the passphrase; the bucket's operator cannot read a shop's data.
- **Automatic sync.** A systemd timer on the desktop takes a snapshot every night. The database is uploaded whole each time; a media file is uploaded once, by its content hash, and skipped on every later run, so a night's run moves only what is new. A missed night (the machine was off) runs at the next boot.
- **Point-in-time restore.** `motodiag backup list` shows every snapshot by the time it was taken; `motodiag backup restore --at <time> --to <folder>` brings back the newest snapshot taken at or before that time, decrypts it, checks every hash and the database's integrity, and writes it into an empty folder of the operator's choosing. It never writes over live: that is the deploy skill's domain and a rule-1 stop.

What the operator gets: one command to see that last night's copy exists, one to get a copy back from any night, and the knowledge that the shop's data survives the desktop. F205's relative media paths (Phase 383) are what make the restored folder usable on any machine, as the plan of record's 2026-10-19 entry said this phase would need.

3. **`src/motodiag/backup/crypt.py`** (new): the encryption, with the `cryptography` package already in the fence's venv and the server's (`push` extra). `encrypt_file(src, dst, passphrase)` derives a 32-byte key with scrypt (a 16-byte random salt; cost 2**17, r 8, p 1 by default, the cost written in the header so a test may use a smaller one) and encrypts with AES-256-GCM in streaming mode (`Cipher(AES, GCM)` with `update()` over 1 MiB chunks), writing a header (magic `MDBK`, version 1, log2 of the cost, salt, 12-byte nonce), the ciphertext and the 16-byte tag. `decrypt_file(src, dst, passphrase)` reads the header, streams the plaintext to a temporary file beside `dst`, and renames it onto `dst` only after the tag verifies; on a wrong passphrase or a changed byte it raises `BackupTampered` and leaves nothing at `dst`. Every write of plaintext goes through this one function, so there is one format.
   Finish line: a round trip of a file larger than one chunk equals the original byte for byte; two encryptions of the same bytes differ in every byte after the magic; a single flipped byte in the ciphertext, in the tag and in the header's salt each refuses and leaves no file at the destination; a wrong passphrase refuses; a file whose magic is not `MDBK` refuses before reading further.

4. **`src/motodiag/backup/store.py`** (new): the object store, in the standard library. The fence's venv is read-only and has no `boto3` (checked for this plan: `.venv/lib/python3.14/site-packages/` holds `cryptography` and no `boto3` or `botocore`), and a test that skipped for a missing package would be a new skip, which F206's pinned list refuses; so the S3 client is written here, about a hundred lines. `ObjectStore` is a `Protocol`: `put(key, path, sha256)`, `get(key, path)`, `list(prefix) -> list[ObjectInfo]` (key, size, last modified), `exists(key)`. **`list` takes no delimiter and returns every key under the prefix**, so neither the Protocol, the fake store nor the `ListObjectsV2` call knows about `CommonPrefixes`; any grouping of keys into folders is the caller's (item 6 does it for the snapshot folders). The `ListObjectsV2` query is `list-type=2&prefix=<prefix>` and, on a later page, `continuation-token=<token>`, every value URI-encoded as SigV4 requires, with the keys sorted; that is the one canonical query string the client ever signs, and the known-answer and fake-transport tests below cover it. `S3Store(endpoint, bucket, key_id, secret, transport=urllib_transport)` signs each request with AWS Signature Version 4 (service `s3`, the region read from the endpoint host, `s3.<region>.backblazeb2.com`; path-style URLs `https://<endpoint>/<bucket>/<key>`; `x-amz-content-sha256` of the payload for PUT, `UNSIGNED-PAYLOAD` for GET and LIST; `x-amz-date`; the host header). `put` streams the file as the body with `Content-Length`; `list` reads `ListObjectsV2` XML with `continuation-token` paging until `IsTruncated` is false. The `transport` is one callable, `(method, url, headers, body) -> (status, headers, body)`; the default uses `urllib.request` with a 60-second timeout, and tests pass an in-process fake, so no test opens a socket (the fence runs under `--unshare-all`, and `tests/support/network_guard.py` refuses anything but loopback). A non-2xx status raises `StoreError` with the status and the response's `<Code>` and `<Message>`, and never the request's headers. The signing's canonical request, string to sign and signature are three functions each under McCabe 20, so the ratchet's `COMPLEX_FUNCTIONS` pin (25) does not move.
   Finish line: a known-answer test reproduces the signature of AWS's published worked example for a GET of an object (the `examplebucket` GET of `test.txt` on 24 May 2013 with key `AKIAIOSFODNN7EXAMPLE`), and a second reproduces AWS's published worked example for a bucket listing with a query string (the same bucket and day, `max-keys=2&prefix=J`), so the query-string encoding the `list` call depends on is held by a published vector too; the fake transport recomputes each request's signature from the secret it holds and refuses a request whose signature or signed headers differ, with the control that a request with the host header left unsigned is refused; put, get, list and exists round-trip through the fake; a listing of 2,500 keys comes back whole through three pages; a 403 from the fake raises `StoreError` whose text holds the status and code and not the key id.

5. **`src/motodiag/backup/snapshot.py`** (new): one snapshot. `take_snapshot(db_path, data_dir, settings, store, work, clock=None) -> Manifest`:
   - copies the database with `sqlite3.Connection.backup` into the work folder (the same API `deploy.py backup` uses, so the running API is never blocked and the copy is consistent), runs `pragma integrity_check` on the copy and refuses to upload one that is not `ok`, records its sha256, size and `max(version)` from `schema_version`;
   - walks `videos/`, `photos/` and `audio/` under the data folder (the three folders the upload routes write, `_resolve_storage_dir` in `api/routes/videos.py`, `photos.py` and `transcripts.py`), records each file's path relative to the data folder in POSIX form (F205's form) and its sha256;
   - lists `media/` in the store once, encrypts and uploads each media file whose key `media/<sha256>.enc` is absent, and skips the rest: that is the sync;
   - encrypts and uploads the database as `snapshots/<UTC time, YYYYMMDDTHHMMSSZ>/motodiag.db.enc`, then the manifest as `snapshots/<time>/manifest.json.enc`: the time taken, the label, the host name, the schema version, the database's plaintext sha256 and size, the ciphertext's sha256, and the media list (relative path, sha256, size, key). The manifest is uploaded last, so a snapshot folder with a manifest is complete by construction;
   - deletes the work folder's plaintext copy in a `finally`, and appends one JSON line to `work/runs.log`: time, label, outcome, snapshot key, media uploaded and skipped, bytes sent, or the error's text.
   Times are `motodiag.core.timestamps.utc_now()` and an injectable `clock` for tests; no private `_now` helper, so `PRIVATE_HELPERS` stays at 19.
   Finish line: on a fresh database (`init_db` on a temporary path) with three media files, the fake store holds one database object, three media objects and one manifest, and the manifest decrypts to the three relative paths and hashes; a second run with one new media file uploads exactly one media object and a new database and manifest, with the control that deleting a media object from the fake makes the next run upload it again; a copy that fails `integrity_check` (a planted corruption of the copy, through a test seam) uploads nothing and the run log says why; no plaintext copy remains in the work folder after a run that succeeded or one that raised.

6. **`src/motodiag/backup/restore.py`** (new): reading it back. `list_snapshots(store) -> list[SnapshotRef]` calls `store.list("snapshots/")` once, with no delimiter (item 4's `list` has none), and groups the keys by their folder itself: the key's second path segment is the folder, parsed as the snapshot's time; a folder counts as a snapshot only when it holds both `manifest.json.enc` and `motodiag.db.enc` (a folder with the database and no manifest is an interrupted upload, listed by nothing); the database object's size comes from the listing. The result is newest first, and it needs no passphrase. The prefix holds two keys a night, so a year of snapshots is well inside one page, and the paging of item 4 covers it past that. `pick(refs, at)` returns the newest snapshot taken at or before `at` (`latest` is the newest), or raises `NoSnapshotBefore` naming the oldest time there is. `restore(ref, store, settings, to_dir, *, db_only=False, current_db=None, current_data_dir=None)`: refuses when `to_dir` exists and is not empty; refuses when `to_dir` is, contains or lies under the current database's folder or the current data folder (never over live); downloads and decrypts the manifest, then the database to `to_dir/motodiag.db`, checks its sha256 against the manifest and `pragma integrity_check`; then each media file to `to_dir/<relative path>`, checking its sha256; a mismatch raises `BackupTampered`, and the partial folder is removed so a failed restore leaves nothing. `verify(ref, store, settings)` does the database half into a temporary folder and deletes it: the nightly proof that a snapshot can be read back. Both return a `RestoreReport` (time, schema version, rows by table from the restored copy, media count and bytes).
   Finish line: three snapshots taken at injected times T1 < T2 < T3 restore as follows: `--at` between T2 and T3 gives T2's rows, `latest` gives T3's, before T1 refuses naming T1; a fourth folder holding only a database object (the manifest deleted from the fake) is not listed, with the control that putting the manifest back lists it; the restored database's table dump equals the source's at that time and each media file's bytes equal the original's; a non-empty target refuses; a target inside the current data folder refuses with the control that a sibling folder does not; a media object corrupted in the fake refuses and leaves no target folder; `verify` leaves no file behind.

- **A test it cannot make green:** the two SigV4 known-answer tests (item 4) rest on AWS's published worked examples; if the implementation cannot reproduce a published signature and the Engineer cannot tell the vector from the code, it stops rather than loosening the test to its own output. - **A live-database change:** none. Nothing here writes to live: snapshots read it through the backup API, and `restore` refuses a target that is, contains or lies under the current database's folder or data folder. A restore over live, should the operator ever want one, is a live-database change that alters or deletes rows, goes through the deploy skill with the operator's approved diff, and is a stop.
