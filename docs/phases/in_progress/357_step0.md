# Phase 357 — Step 0: saved runs, the schema, and where a run's powertrain comes from

**Measured 2026-09-28, before v1.0**, on `phase-357` branched from
`master` at `b0ff03a`, against a freshly migrated database in the session
scratchpad (`s0.db`, `init_db`, schema 72). No step read
`data/motodiag.db`.

## S0-1: K8, the row's verbs

Row 357 promises five actions. Each gets a command a user runs, and each
command is driven by a `CliRunner` test on a `tmp_path` database:

| the row's verb | the command |
|---|---|
| start | `motodiag workflow start <slug> (--bike SLUG \| --vehicle-id N \| --work-order N) [--powertrain P]`: saves the run and one row per item, prints the run's number, then walks the items as `run` does |
| record | every answer in the walk is saved as it is given. `motodiag workflow record <run> <item#> pass\|fail\|skip [--notes TEXT]` records or corrects one item without the walk |
| finish | `motodiag workflow finish <run>`: refused while an item is unanswered; sets the run complete. The walk's last answer asks "Finish this run now?" and calls the same code |
| resume | `motodiag workflow resume <run>`: walks the unanswered items of an unfinished run, in order |
| read back | `motodiag workflow runs [--bike \| --vehicle-id \| --work-order] ` lists runs; `motodiag workflow report <run>` prints one run: bike, work order, powertrain, status, every item's result, notes and the diagnosis printed at a fail |

A finished run refuses `record` and `resume`. Quitting the walk (Ctrl-C or
end of input) leaves the run unfinished, with every answer given so far
saved: that is what `resume` is for.

## S0-2: what is reused from 356, and what changes

Reused unchanged:
- `_template_or_refuse`: a retired template prints its retirement line,
  an unknown slug its message, both exit 1, before anything is saved.
- `checklist_workflow` and `stop_on_fail=False`: the walk still goes
  through Phase 82's engine, every item answered whatever an earlier one
  found.
- `_print_item`, `_ANSWERS` (`p`/`f`/`s` to `StepResult`), `POWERTRAINS`,
  and the coverage refusal (`<slug> covers ice, hybrid, not electric.`).
- `workflow run` itself: it stays the unsaved walk, its output unchanged,
  and its 32 tests are not edited.

What changes:
- **The walk loop moves into one helper** that `run`, `start` and
  `resume` call. For `run` it records into the engine only; for the saved
  commands each answer is also written to the database before the next
  item is shown.
- **The database is the record; the engine is the walker.** `resume`
  builds `checklist_workflow` over the unanswered items only. `record`
  may answer item 5 before item 3, so replaying saved answers into the
  engine's single index would not be faithful. Counts and the summary on
  `finish` and `report` come from the saved rows.
- **The run keeps the item list it started with.** A template edited
  between `start` and `resume` (359 changed items by migration) does not
  add or remove items from a run already started.

## S0-3: the schema — migration 073 adds two tables and three indexes, nothing else

```sql
CREATE TABLE workflow_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    template_id INTEGER NOT NULL,
    vehicle_id INTEGER NOT NULL,
    work_order_id INTEGER,
    powertrain TEXT NOT NULL CHECK (powertrain IN ('ice', 'electric', 'hybrid')),
    status TEXT NOT NULL DEFAULT 'in_progress'
        CHECK (status IN ('in_progress', 'complete')),
    started_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    finished_at TIMESTAMP,
    CHECK ((status = 'complete') = (finished_at IS NOT NULL)),
    FOREIGN KEY (template_id) REFERENCES workflow_templates(id) ON DELETE RESTRICT,
    FOREIGN KEY (vehicle_id) REFERENCES vehicles(id) ON DELETE RESTRICT,
    FOREIGN KEY (work_order_id) REFERENCES work_orders(id) ON DELETE SET NULL
);
CREATE INDEX idx_workflow_runs_vehicle ON workflow_runs(vehicle_id, started_at);
CREATE INDEX idx_workflow_runs_work_order ON workflow_runs(work_order_id);

CREATE TABLE workflow_run_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id INTEGER NOT NULL,
    checklist_item_id INTEGER,
    sequence_number INTEGER NOT NULL,
    title TEXT NOT NULL,
    required INTEGER NOT NULL,
    result TEXT CHECK (result IN ('pass', 'fail', 'skipped')),
    diagnosis TEXT,
    notes TEXT,
    answered_at TIMESTAMP,
    UNIQUE (run_id, sequence_number),
    CHECK ((result IS NULL) = (answered_at IS NULL)),
    CHECK (result IS NOT 'skipped' OR required = 0),
    CHECK (diagnosis IS NULL OR result = 'fail'),
    FOREIGN KEY (run_id) REFERENCES workflow_runs(id) ON DELETE CASCADE,
    FOREIGN KEY (checklist_item_id) REFERENCES checklist_items(id) ON DELETE SET NULL
);
CREATE INDEX idx_workflow_run_items_item ON workflow_run_items(checklist_item_id);
```

- **Keys.** A run's items are found by `UNIQUE (run_id, sequence_number)`,
  whose automatic index also serves "the items of run N, in order". The
  vehicle index serves `runs --bike` newest first; the work-order index
  `runs --work-order`. The item index lets SQLite apply `ON DELETE SET
  NULL` without a scan when a checklist item is deleted.
- **What a result row copies from its item** (`sequence_number`, `title`,
  `required`), and why: the item can be edited or deleted after the run
  (`delete_checklist_item` exists; 359 retired two templates). The read-back
  must still say which item this was. `diagnosis` is the text printed at
  the fail, copied then, so `report` shows what the mechanic was told, not
  what the template says later. The instruction text is not copied: the
  walk prints it live, from the item.
- **The rules the schema holds** rather than the command: a finished run
  has a finish time and an unfinished one does not; an answer has a time
  and no answer has none; a skip only on an optional item; a diagnosis
  only on a fail.
- **`ON DELETE RESTRICT` on the vehicle**, as `work_orders` has: a bike
  with saved runs cannot be deleted and take its inspection history with
  it. Measured on the scratch database: today `garage remove` on a bike
  with a work order raises `IntegrityError: FOREIGN KEY constraint
  failed` (`vehicles/registry.py:161`, no handling in `cli/main.py:525`).
  A bike with a saved run will do the same. That traceback is older than
  this phase; it is filed as F176, not fixed here.

### "Tied to a bike or a work order"

| given | the run's vehicle | the run's work order |
|---|---|---|
| `--bike` or `--vehicle-id` | that bike | none |
| `--work-order N` | the work order's `vehicle_id` (a work order always has one: `NOT NULL`) | N |
| both, naming the same bike | that bike | N |
| both, naming different bikes | refused, exit 1, nothing saved | — |
| neither | refused, exit 1, pointing at `workflow run` for a walk that saves nothing | — |
| a work order that does not exist, or is `completed` or `cancelled` | refused | — |

So `vehicle_id` is never null, and `runs --bike` finds a run started from
a work order too.

### The migration and the live database

- **It only adds:** two tables, three indexes, and one `schema_version`
  row. It changes and deletes no existing row, so it is not a rule-1 stop.
  The dry run will show this, and the scope file will say it: the two
  tables and three indexes under `"schema"`, `schema_version` +1, every
  other table unchanged. If the dry run shows anything else, I stop and
  ask.
- **The rollback peels it:** drop the three indexes, drop
  `workflow_run_items`, then `workflow_runs`. The tests check the rollback
  by `rollback_to_version(MIGRATION - 1)` and by table presence, and pin the
  schema head only as `SCHEMA_VERSION >= 73` and `== max(MIGRATIONS)`.
  There is no literal pin of the head (F124), so migration 074 does not
  break them.

## S0-4: the powertrain, a real fork

**Measured, and it bears on every option:**
- `garage update` has no `--powertrain` (`cli/main.py:607`: `--mileage`,
  `--notes`, `--vin`). **Nothing in the CLI can correct a bike stored with
  the wrong powertrain.** The API can: `PATCH /vehicles/{id}` takes one
  (`api/routes/vehicles.py:104`).
- **F174 lists three `ice` defaults; there is a fourth.** The API's
  create request defaults `powertrain` to `"ice"`
  (`api/routes/vehicles.py:83`). A bike added from the app without one is
  stored as `ice` too. F174's entry is amended to say so.
- The gate is the same as in 356: 8 active templates cover all three
  powertrains, 5 cover ice and hybrid only. No item carries a
  powertrain.

### Option A: `--powertrain` or the prompt, as in 356; a bike whose stored value disagrees is refused

```
$ motodiag workflow start brake_service_v1 --bike srf-2021 --powertrain electric
Bike #3 (2021 Zero SR/F) is stored as ice, not electric. Nothing was saved.
(exit 1)
```

- Ships: the run's powertrain is what the mechanic states, checked
  against the bike. The saved run records it.
- Tests: flag and prompt each start a run; a disagreement is refused with
  nothing saved; an uncovered template refused as in 356.
- **The gap:** an electric bike stored as `ice` can never start a run as
  electric. The only way through is to type `ice`, which the refusal
  forces and which then admits the ice-only templates. With no CLI
  command to correct the bike, the refusal has no remedy.

### Option A+ (recommended): A, plus `garage update --powertrain`

The same as A, and the refusal names its remedy:

```
Bike #3 (2021 Zero SR/F) is stored as ice, not electric.
If the bike is electric: motodiag garage update --bike srf-2021 --powertrain electric
```

- Ships: A, and `garage update` gains `--powertrain` (the same three
  choices). It writes one column through `update_vehicle`, which already
  accepts it. It changes no default and no existing row by itself.
- Tests: A's, plus `garage update --powertrain electric` then a start as
  electric succeeds; `garage update` with no field still refused.
- F174 stays open: new bikes are still stored as `ice` without the flag.
  But every wrong value now meets a refusal the first time a run is
  started, and the mechanic can fix it in one command.

### Option B: A+, and fix F174's default at `garage add`

- Ships: A+, and `garage add` without `--powertrain` asks for it (a
  prompt with the three choices) instead of storing `ice`. No migration:
  the column's default stays, because changing it means rebuilding the
  `vehicles` table, which the live apply would show as rewriting every
  vehicle row.
- Tests: A+'s, plus `garage add` without the flag prompts and stores the
  answer; with the flag it does not prompt. Every existing test that
  calls `garage add` without the flag has to give an answer: 12 call
  sites in 8 test files, 6 of them gate tests (grep of `"garage", "add"`
  over `tests/`); which omit the flag is counted at v1.0.
- F174: the CLI door closes. The API's create default (`:83`), the model
  default and the column default remain, so F174 stays open for them, and
  existing live rows are still indistinguishable.

### Option C: trust the bike's stored value

- Ships: the smallest change. `--powertrain` is not taken with a bike;
  the stored value gates the template.
- Tests: the stored value gates; a bike stored as electric is refused an
  ice-only template.
- **Wrong by F174:** an electric bike stored as `ice` is given
  `valve_adjustment_v1` and the other four ice-only templates, and the
  saved run records `ice` for it. No refusal ever surfaces the error.

### Recommendation

**A+.** The run records what the mechanic says the machine is, as 356
does; a disagreement with the garage is caught instead of saved; and the
refusal can be acted on. B is A+ with a larger change to an existing
command, which touches every test that adds a bike, and it still leaves
F174 open for the API. C saves the wrong value silently.
