## S0-4. The outbound client (decided)

- **Standard library only** (`urllib.request`): the core dependencies
  hold no HTTP library, httpx is only in the optional `[push]` extra, and
  none is added.
- One small module, `core/outbound.py`, used by the three services:
  - an honest User-Agent naming the app and its version (not Python's
    default, which NHTSA refuses; not a browser's);
  - a timeout (20 s), no retry loop, one request per command step;
  - **it never returns an empty result for a failure.** It returns the
    body, or raises `ServiceUnavailable` naming the service and the kind:
    unreachable (DNS, connection, timeout), blocked (403, or an HTML body
    where JSON or XML was expected), an error status, or a body it cannot
    parse. NHTSA's 400 with a valid `{"Count":0}` body is read as zero
    results **only** on the recalls endpoint, and only when the body
    parses with that shape.
- **Every command that calls a service** prints the service's name when
  it fails ("NHTSA recalls could not be reached: …"), exits non-zero, and
  shows what is stored locally with its date, labelled as stored. It
  never prints an empty list as if there were none.
- **Tests never reach the network.** An autouse fixture in
  `tests/conftest.py` refuses any socket connection or name lookup to a
  non-loopback address, and fails the test naming the host. A planted
  known-bad test (run in a subprocess by the guard's own test) must fail
  on it. Services are exercised through recorded fixtures, one success and
  one failure per service at least.
- **The smoke calls:** one live call per service during the build, made
  through the app's own command so the logged call proves the real client:
  URL, time (UTC), HTTP status and body size, logged in the phase log; the
  response kept as that service's success fixture. Any other fixture is
  built from the documented or recorded format and says so in its header.
- **Tailnet-only holds:** nothing new listens. No route is added.

## S0-5. Recalls: what is stored and when it is refreshed (decided)

- **Stored locally, refreshed only when a user asks.** `motodiag advanced
  recall refresh --make M --model N --year Y`, `--bike SLUG`, or `--vin
  VIN` (vPIC decodes it first), and `--all-bikes` for every garage bike
  with a make, model and year. There is no scheduler: nothing refreshes by
  itself, and every lookup prints the date its data was fetched.
- **Each fetch is recorded** (new table `recall_fetches`: make, model,
  year as asked, when, the URL, the HTTP status, how many results, and
  `ok` or the failure). A failed fetch changes no stored recall.
- **One campaign, many vehicles.** `recalls.campaign_number` is unique and
  a campaign covers many models and years, so a fetched campaign is one
  `recalls` row (with `source = 'nhtsa'` and when it was fetched) plus one
  row per make, model and year in a new `recall_vehicles` table. The
  lookups (`check-vin`, `lookup`, `list`, per-bike open recalls, the
  predictor's feed) read fetched campaigns through `recall_vehicles`, and
  the existing rows' own make, model and year as before.
- **Severity: NHTSA gives none.** A fetched campaign NHTSA flags "park it"
  (`parkIt`) or "park outside" (`parkOutSide`) is stored `critical`, which
  is NHTSA's own do-not-ride or fire warning; any other is stored
  `unrated` and shown as "not rated by NHTSA". Nothing is stored as
  `medium` by default (the column's default).
- **What an answer may say** (F103: a wrong model name and a clean year
  look the same):
  - campaigns found: listed, each "may apply to this bike; whether this
    VIN is included, check nhtsa.gov/recalls or the maker";
  - zero found: "NHTSA listed no recall for 2012 HARLEY-DAVIDSON ROAD KING
    as named, on 2026-…. NHTSA matches the model name exactly, and a name
    it does not use also returns none: this is not an all-clear." Never
    the green "Clear" panel;
  - never fetched: "No recall data fetched for this model", with the
    refresh command;
  - the service down: the failure, then what is stored, with its date.
- **`--all-bikes`** asks for the F103 known-present campaign first and
  stops if it does not come back; it fetches one bike at a time with a
  pause between requests; any failure makes the run exit non-zero and
  lists the bikes not refreshed, and a failed bike keeps its previous
  data and date.
- `recall mark-resolved` works on fetched campaigns unchanged (by recall
  id); `recall list --bike` shows open and resolved.

## S0-6. VIN decoding (decided)

- `motodiag advanced vin decode VIN [--refresh]`: vPIC's flat decode with
  the model year when position 10 gives one. Stored per VIN (new table
  `vin_decodes`: make, model, year, manufacturer, vehicle type, vPIC's
  error code and text, the response, the URL, when). A stored decode is
  shown with its date; `--refresh` fetches again. vPIC's own error code is
  shown when it reports one (a partial decode is labelled partial).
- **vPIC down:** it says so, and shows the offline decode labelled
  "offline: maker and year only".
- `recall check-vin` uses the stored or fetched decode for its model, so
  it can ask NHTSA about the right model year.
- `--bike SLUG --save`: writes the VIN to the bike only when asked; it
  never overwrites a bike's make, model or year, and prints any
  disagreement.

## S0-7. Tax (decided, except the questions below)

**The model, per jurisdiction:**
- `tax_jurisdictions`: a code (`US-MA`, ISO 3166-2 style, any country), a
  name, the currency its invoices are in.
- `shop_tax_jurisdictions`: which jurisdiction a shop is in, one per
  shop. **A separate table rather than a column on `shops`,** so the
  table that holds the smoke shop is not altered.
- `tax_rates`: the rate, the date it takes effect, the date it is valid
  until, its source (title, URL), when the source was checked, and its
  provenance: `regulation` (shipped, from the regulator's text) or `shop`
  (entered by the shop, by whom).
- `tax_line_rules`: for each of labour, parts, diagnostic and shop
  supplies, taxable or not, with the same dates, source and provenance.
- **The check** (`tax status`, and on every invoice): a rate or rule past
  its validity fails; a shop with no jurisdiction, no rate valid on the
  invoice date, or no rule for a line type the invoice carries is
  refused, naming what is missing and the command that records it. Tax is
  never assumed.
- **The invoice records** the rate it used, the rate's id and source, and
  which line types were taxed (new columns on `invoices`, which holds 0
  live rows), and prints them. Tax is computed on the taxable lines only.
- One combined rate per jurisdiction. A place whose tax has several parts
  (a state and a county, or GST and PST) is entered as the combined rate;
  itemising the parts is part of row 368's future.

**Massachusetts, shipped (`regulation`):**

| item | value | source |
|---|---|---|
| rate | 6.25%, effective 2009-08-01 | the guide (S1), TIR 09-11 (S2) |
| parts, separately stated | taxable | 830 CMR 64H.1.1(2)(b)1 and (5)(a) (S3); the guide's "parts for a car repair" |
| labour, separately stated | not taxable | 64H.1.1(2)(a)1 and (5)(a); the guide lists "Car repairs" under "Tax-Exempt Items & Sales" |
| diagnostic fee | not taxable | 64H.1.1(2)(a)1: a service with no transfer of property. This is the build's reading of that clause; the pages do not name a diagnostic fee |
| shop supplies | **not shipped** | none of the pages names a shop-supplies charge. A Massachusetts shop records its own rule, with its source, before an invoice with a shop-supplies line can be made |

Every generated invoice itemises parts on their own lines, the condition
(2)(b)1 sets. Massachusetts has no county or city sales tax on these
sales; the guide states the rate statewide.

**Everywhere else:** `motodiag shop tax` records a jurisdiction, its rate
and its rules, each with its source, effective date and valid-until date,
all required. The same check applies.

## S0-8. Exchange rates (decided, except question 3)

- `exchange_rates`: base, quote, rate, the rate's own date, valid until,
  source (`ECB` with the feed URL, or `shop` with who entered it and their
  source), when fetched or entered.
- `motodiag shop currency refresh` fetches the ECB daily feed (one XML
  document, EUR against about 30 currencies) and stores it.
  `shop currency rates` lists what is stored, with dates and validity;
  `shop currency set` records a shop's own rate; `shop currency convert
  AMOUNT FROM TO` prints the result, the rate, its date, its source, and
  "cross rate through the euro" when it is one.
- The ECB's caveat is printed with every conversion that uses its rates:
  "published for information purposes only".
- A rate past its validity is refused, naming the refresh or set command.
- The shop's currency comes from its tax jurisdiction (Massachusetts:
  USD), and an invoice is written in it unless another is asked for. The
  hard-coded `"USD"` goes.

## Questions for the operator

### 1. The invoice API's `tax_rate` (F184)

Today `InvoiceGenerateRequest.tax_rate` defaults to 0.0. The CLI's
`--tax-rate` follows whichever option is picked.

**(A) Remove the field. The rate comes from the shop's jurisdiction on
record. (Recommended.)**
- The route computes tax exactly as the CLI does, from the shop's valid
  rate and line rules, and records the rate and source on the invoice.
  A shop with no valid rate gets 409, naming what is missing and the CLI
  command that records it (no route records a rate).
- The CLI's `--tax-rate` is removed the same way.
- One source of truth, and every invoice carries a sourced rate.
- Snapshot: one property removed from `InvoiceGenerateRequest`.

**(B) Keep the field, required, with no default.**
- The caller states a rate on every invoice; the invoice records it with
  source "entered when invoicing, by user N".
- Two sources of truth: the shop's record and whatever the caller sends.
  The jurisdiction's line rules would still decide which lines are taxed.
- Snapshot: the default goes and the field becomes required.

**(C) Keep the field, optional, with no default.**
- Absent: the shop's rate on record, as A. Present: an override, recorded
  with source "entered when invoicing, by user N".
- Allows a one-off rate (for example an out-of-state sale) without a new
  record, and is also the way around the record.
- Snapshot: the default 0 goes and the field becomes `number | null`.

**(D) Leave the API model unchanged; the route ignores an absent field.**
- The route uses the record unless the caller sent a value (pydantic's
  `model_fields_set`). No snapshot change and no mobile session.
- The published contract then says the default is 0 when it is not, a
  model that disagrees with what the route does (the F9 family).

### 2. Validity windows the sources do not state (new thresholds)

**(a) Massachusetts's rate and line rules.** The DOR states when 6.25%
took effect (2009-08-01) and no end. **Proposed: valid for 12 months from
the date the DOR's pages were last checked** (checked 2026-09-30, so
valid until 2026-09-30 + 12 months = 2027-09-30). `shop tax confirm`
records a new check, with the date and the page, and moves the validity
12 months from it. After that date, invoices are refused until someone
re-reads the pages and confirms.
- Alternatives: 6 months; or until the end of the next calendar year.

**(b) ECB rates.** Published each TARGET working day; no validity stated.
**Proposed: usable through the 4th calendar day after the rate's own
date** (Thursday's rate lasts through Monday), which covers the longest
regular closure, Good Friday to Easter Monday. After that the conversion
is refused until `shop currency refresh`.
- Alternatives: the same day and the next only (a stale rate is refused
  over every weekend unless refreshed); or 7 days.

A shop's own rate (tax or exchange) carries the valid-until date the shop
enters, which is required; no window is proposed for those.

### 3. May ECB rates convert an invoice? (found at Step 0)

The ECB's page: "The reference rates are published for information
purposes only. Using the rates for transaction purposes is strongly
discouraged."

**(A) ECB rates for conversions shown to the user only; an invoice in
another currency converts at a rate the shop records itself (its bank's
or processor's), with source and validity. (Recommended.)**
- `shop currency convert` and any shown conversion use ECB rates, with
  the caveat printed. An invoice asked for in CAD uses the shop's own
  CAD rate, or is refused naming `shop currency set`.
- Follows the source's own statement.

**(B) ECB rates may also convert an invoice,** with the caveat printed
and recorded on the invoice. Works with no rate entered by the shop; uses
the rates against their publisher's advice.

**(C) No ECB at all:** every rate is entered by the shop. No outbound
call for row 289.
