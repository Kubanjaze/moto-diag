# Phase 348 — Audit log (who did what, when)

**Version:** 1.0 | **Tier:** Standard | **Date:** 2026-10-29

---

## Goal

A shop can answer "who did what, and when". Today nothing records it: Step 0 found no audit log, event log or `log_event` in src (its census, run on this branch from `47b93ea`). The pieces that look like one each record one thing: Phase 10's log lines, Phase 166's and 167's own audit tables, and the Stripe webhook record in `src/motodiag/billing/webhook_handlers.py`. Nothing enforces append-only behaviour on any of them. Phase 303 shipped staff logins and left the resolved caller on every credentialed request, `request.state.caller` (user id, credential kind, credential id), for this phase to read (`docs/phases/completed/303_implementation.md`, Goal: "What this makes for Phase 348").

This phase ships the row's three promises, as an extension (Step 0's classification), changing no existing route's or command's behaviour:

- **Immutable event log.** One event per write request on the API (POST, PUT, PATCH, DELETE), recorded by one middleware from the caller 303 leaves on the request: who (user id, username at the time, credential kind and id, client address), what (method, path without its query string, the handler's name, the path's ids, the shop when the path names one, the status) and when (UTC). The log is an append-only SQLite file of its own, beside the database in use: two triggers refuse UPDATE and DELETE, and every row carries a hash chained to the row before it, so a change or a removal in the middle is found by `motodiag audit verify`.
- **Security audit trail.** Two readers: `motodiag audit list` for the operator (the whole trail, filtered by user, shop, time and path, with `--json`), and `GET /v1/shop/{shop_id}/audit` for a shop member who holds `manage_users` at that shop, showing only that shop's events. Logins, failed logins, logouts, password changes and the owner's resets are in the trail by the same rule as every other write, because they are writes.
- **Compliance readiness.** What a compliance reader does: `motodiag audit verify` proves the chain intact and prints the count and the head hash; `motodiag audit export` writes the trail as JSON lines to a file the operator keeps. Nothing is ever deleted from the log, and no request body, query string, password or token is ever in it.

**Where the log lives, and why not a migration.** The Captain's recommendation, for the operator's word at the one stop below: the log is its own SQLite file, created by the writer on first use, not a table of the main database by migration 088. Two measured reasons. First, a phase with a migration has no path through the fleet (F232, `docs/FOLLOWUPS.md`): the fence has no `live.json`, so every `deploy.py` mode exits 4, and the Quartermaster's Q1 refuses a pull request that changes `src/motodiag/core/migrations.py` (`.claude/skills/fleet/quartermaster.py`, V8). Second, the deploy gates compare live with its backup and set aside only `api_keys.last_used_at` (`SERVER_WRITES` in `.claude/skills/deploy/deploy.py`, F208, F210): an audit table in the main database gains a row on every write request, so any use of the server between a dry run and its apply would refuse the apply, and any use after it would fail verify-live's check 8, for every phase after this one. A file of its own is outside that comparison by design, and a restore of the main database from a backup leaves the trail whole. The alternative, migration 088, is written at the end of Logic; it holds this phase until a fleet phase that names 348 settles F232.

2. **`src/motodiag/audit/__init__.py` and `src/motodiag/audit/log.py`** (new): the store. `audit_path_for(db_path, settings=None) -> str` is the one rule for where the file is: `settings.audit_db_path` when set, else `audit.db` in the folder of the database in use. `ensure_log(path)` creates the table `audit_events` (`id`, `occurred_at`, `request_id`, `actor_user_id`, `actor_username`, `credential_kind`, `credential_id`, `client_address`, `forwarded_for`, `method`, `path`, `endpoint`, `path_params`, `shop_id`, `status`, `prev_hash`, `row_hash`) and two triggers, `audit_events_no_update` and `audit_events_no_delete`, each `BEFORE` the statement with `RAISE(ABORT, 'audit_events is append-only')`; it is idempotent. `append_event(path, event) -> int` runs one `BEGIN IMMEDIATE` transaction: it reads the last row's id and `row_hash` (the first row's `prev_hash` is `GENESIS`, sixty-four zeros), assigns the next id, computes `row_hash` as SHA-256 over `prev_hash` and the row's fields in column order as compact JSON with sorted keys, and inserts; `occurred_at` is `motodiag.core.timestamps.utc_now()`, no private helper (the ratchet's `PRIVATE_HELPERS` pin stays 19). `list_events(path, *, shop_id, user_id, since, until, path_prefix, limit, before_id)` reads newest first and returns an empty list when the file does not exist, never creating it. `verify_chain(path)` walks every row in id order, recomputes each hash, checks each `prev_hash` against the row before, checks both triggers exist, and returns the count, the head hash and the first bad id, or that the triggers are missing. `export_events(path, out_path)` writes every row as one JSON line and refuses an existing file. The connection is `motodiag.core.database.get_connection(path)`, passed the audit path explicitly.
   Finish line: an UPDATE and a DELETE on the file both raise and change nothing; a row changed in a copy whose triggers were dropped is named by `verify_chain`, and so is a row removed from the middle; two connections appending at once leave one intact chain; the file holds no `mdk_` or `mds_` text after a request that carried a token in its query string, with the control that a planted token turns the same assertion red; `list_events` on a missing file returns nothing and makes no file.

3. **`src/motodiag/api/middleware.py`: `AuditMiddleware`**, and the db-path resolution `RateLimitMiddleware._try_resolve_api_key` and `_caller_tier` each carry today moved into one helper `_request_db_path(request)` that all three use (one change, no behaviour change, the rate-limit tests pass with no edit). A `shop_id` path parameter becomes the event's `shop_id`. A route that raises is recorded with status 500 and the exception is re-raised. A failure in the audit write is logged at ERROR on `motodiag.audit` with the request id, and the response is returned as it was (the operator's part (b)). GET, HEAD and OPTIONS are not recorded, and neither is a request the limiter refused, because the middleware is registered innermost, inside `RateLimitMiddleware`.

## Non-goals

- Recording what the CLI does: the CLI has no authenticated user (`src/motodiag/shop/attribution.py`), and an actor model for it is its own decision.
- Recording reads (GET), the live socket, or anything a route does inside a transaction; the trail says a request was made and how it answered, not what rows changed.
- Existing write paths (shop, invoicing, parts) emitting events from their own code: Step 0's reshape, back to Step 0 if the operator picks it.
- The app's screen for the trail. Phases 185–204 are the mobile repository's (`ROADMAP_AUTHORITY.md`).
- A retention period, a purge, a redaction, or a sink beyond the file export: the log holds id numbers, never a customer's fields or a request body, so a customer erasure (`src/motodiag/memory/erase.py`) leaves nothing in it to remove; whether an erased customer's id numbers in the trail matter for compliance is for the phase that owns erasure.
- The deploy skill's backup of the audit file: filed as a finding in item 8, settled with 345.
- A migration of any kind under the plan as written; anything under data/; seed data; a split or an eval protocol; any change to `SERVER_WRITES`.
- The fleet's own gaps this phase lives through again, F231 and F232: each is a later fleet phase that must name the first-shop phase it unblocks (K43 rule 4).
