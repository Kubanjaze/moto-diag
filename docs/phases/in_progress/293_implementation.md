## Goal

A shop today has no way to keep its own service manuals and parts books in Mekno. The Phase 117 substrate is there and empty: the `manual_references` table (migration 010, `src/motodiag/core/migrations.py` line 929) and its CRUD in `src/motodiag/reference/manual_repo.py`, listed with the rest of `motodiag.reference` as "substrate, awaiting Track P" in `tests/support/integration_gaps_allowlist.py` (lines 87 to 94). Nothing uploads a file, stores it, reviews it, renders a page or searches one; no role exists that is not a shop's own; the plans have no storage limit for manuals; and the terms say nothing about files a shop uploads that someone else wrote. The Step 0 report found the same and classified the phase an extension (K128), the Science Officer's reshape having turned on one question the operator has now answered: a new version of the terms is accepted by everyone through the sign-in gate as it already is.

After this phase, the server side of the library is live:

1. **A shop's admin uploads a PDF manual or parts book** it owns, tagged with a title, its kind, a make, a model and a year range, through `POST /v1/shop/{shop_id}/manuals`. The server checks it on the spot: a real PDF by its bytes, at most 300 MB, within the shop's plan's storage, not locked by a password, carrying no scripts, attachments or launch actions, clean by the virus scanner, and able to open, render and give up its text. A file that fails is refused with the reason. With no scanner on the machine, every upload is refused: none is let through unscanned (K119).
2. **A person at Mekno reviews it** before anyone can open it (K119). The reviewer is a new kind of account, the first that can open any shop's files, held in a table of its own and granted from the server's command line. The reviewer sees the queue and the pages, and approves, fixes the tag and approves, or rejects with a reason the shop sees; every decision records who and when. After approval any member of the shop can send a page back for review, and a complaint takes the file down until it is decided.
3. **Every member of the shop opens the right page, searches, and zooms.** The server turns each page into an image and a thumbnail in the background and takes its text into an FTS5 index, with `pypdfium2`, which is permissively licensed (not PyMuPDF, which is AGPL). `GET /v1/shop/{shop_id}/manuals` lists by make, model and year; `GET /v1/shop/{shop_id}/manuals/{id}/pages/{n}` serves the page image at a size the app can zoom; `GET /v1/shop/{shop_id}/manuals/search?q=` finds the page with the words. Only approved files are opened or searched; the shop's own list also shows its pending, rejected and taken-down files with their reasons. Another shop never sees any of it: a file stays private to the shop that uploaded it, because showing one shop's bought manual to another would be redistributing it.
4. **The storage limit is the plan's** (K119, K123): Individual 2 GB, Shop 20 GB, Company 50 GB, at most 300 MB a file, as one new limit in `TIER_LIMITS`, counting the bytes of the files the shop uploaded and not the page images made from them. Over it, the upload is refused with how much is used and how to free space, and nothing is charged.
5. **The uploaded files join the nightly backup** (K121): the manuals folder joins the three upload folders the snapshot sends, each file once by its content hash. The page images are not backed up; they are made again from the files after a restore, by a command this phase adds, and a restore test holds it.
6. **The terms and the privacy policy ship as version 1.1** (K119, K122), with the upload clause and what a person at Mekno sees, together with `TERMS_VERSION`, `TERMS_DATE` and the site's two pages. A lawyer's read becomes a later version, as K84 did for 334. The sign-in gate is unchanged: with `MOTODIAG_TERMS_REQUIRED` on, a user who has not accepted 1.1 can only read and accept the terms, see who they are, or sign out (K128). The switch is off on live (`docs/handoffs/2026-11-20_334_closed.md`), so the new version blocks no one until the operator turns it on.

The app's screens are 293B, a mobile session's. This phase refreshes the app's copy of the API on the app repository's branch of this phase's name, never `main`, as 403 allows, and the handoff carries the step that merges that branch into the app's `main` after the server's merge, which 334's handoff lacked.

**Why the reviewer is its own table and not a shop role.** Every role on the server is a shop's own (`RoleName` in `src/motodiag/auth/models.py`, `SHOP_ROLES` in `src/motodiag/shop/rbac.py`), checked through `shop_members`. A reviewer must open a file from any shop while being a member of none, so a `shop_members` row cannot express it, and widening `SHOP_ROLES` would change what every shop command and route means by a role (a rule's definition). A table of user ids is the smallest thing that says "this account reviews", and a test holds that no one else can open a file waiting for review.

**Why the page images are regenerated, not backed up.** K123 makes the images derived data: the shop is charged for the file, and the file is what the shop owns. The draft's section 1 gives the sizes: a 700-page manual is about 20 MB as a publisher's text PDF and 50 to 150 MB as a scan, and its page images and thumbnails, at about 200 to 400 KB a page, come to about 100 to 300 MB. So the images are two to three times the size of a scan and five to fifteen times the size of a text PDF; either way they outweigh the files, and backing them up would make the nightly snapshot mostly copies of what the files already hold. A restore brings the files back and one command renders the pages again; the same command is the recovery path when a server restart cuts a render short. The privacy policy's Backblaze line ("every upload, each night") stays true: the uploads are the files.

Adding the columns rewrites the table's definition, so the dry run lists `manual_references` as a changed object; its rows do not change.
- **Two indexes on it:** `idx_manuals_shop_status` on (`shop_id`, `status`) and `idx_manuals_shop_sha` on (`shop_id`, `file_sha256`).
- **A new table `manual_pages`:** `id`, `manual_id` (referencing `manual_references`, deleted with it), `page_number`, `image_path`, `thumb_path`, `text`, `created_at`, with a unique index `idx_manual_pages_manual_page` on (`manual_id`, `page_number`).
- **A new full-text index `manual_pages_fts`** (an FTS5 virtual table over `manual_pages`' `text`, reading its content from `manual_pages` rather than keeping a copy, with `manual_id` and `page_number` carried unindexed), kept in step by three triggers on `manual_pages`: `manual_pages_ai` after insert, `manual_pages_ad` after delete and `manual_pages_au` after update. **SQLite makes four working tables of its own for it,** which the dry run lists as added: `manual_pages_fts_data`, `manual_pages_fts_idx`, `manual_pages_fts_config` and `manual_pages_fts_docsize`. There is no `manual_pages_fts_content`, because the text stays in `manual_pages`. When the index is created SQLite writes its own first rows into `manual_pages_fts_config` (its version) and `manual_pages_fts_data` (its empty structure); these are the only rows added to any table besides the one below, and the scope file names them with the counts the migration test measured. **Two of the four have no rowid** (`manual_pages_fts_idx` and `manual_pages_fts_config` are WITHOUT ROWID), so the deploy step reads them by their key: Logic item 1a (K131), on master's deploy code, which has it before this step runs.
- **A new table `manual_reviewers`:** `user_id` (the key, referencing `users`), `granted_at`, `granted_by_user_id` (referencing `users`).
- **One row in `schema_version`,** as every migration adds, recording 92.

It changes no existing row and deletes no row in any table. On live `manual_references` has held no row since Phase 117 created it, and the dry run's diff shows the count. The scope file names exactly the rows above (`schema_version`, and the FTS5 working tables' own first rows) and nothing else; if the dry run shows any other row added, or any row changed or removed, the step stops. The Engineer stops after the regression of record. The operator first merges item 1a into master and moves the fleet's code copy (K131), then applies the migration from the handoff's first paste block, from the Mac, with the dry run's list shown before the yes.
