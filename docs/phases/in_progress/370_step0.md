## S0-4. The format: `YYYY-MM-DDTHH:MM:SS.mmm+00:00`

Python: `datetime.now(timezone.utc).isoformat(timespec="milliseconds")`, for
example `2026-10-06T19:42:07.123+00:00`. Fixed width, 29 characters.

Why this one and not SQLite's `YYYY-MM-DD HH:MM:SS`, the shape 281 and 191B
chose for their month starts:
- **It compares with what already compares against it.** The month start
  becomes `2026-10-01T00:00:00.000+00:00`, the same shape.
  - The API's `GET /v1/sessions?since=` already builds an aware UTC `T`
    cutoff (`api/routes/sessions.py:_parse_since`).
  - The CLI's `--since 2026-10-05` and `--until` (which appends `T23:59:59`)
    are `T`-shaped too.
  - SQLite's shape would put a space against a `T` on the same date: the
    191B bug again, on the session list's filters.
- **A reader cannot mistake it for local time.** The offset is in the
  string. A naive UTC string reads four hours off to anyone, and to
  JavaScript, which takes a date-time with no offset as local.
- **Every JavaScript engine must parse it.** `YYYY-MM-DDTHH:mm:ss.sss±HH:mm`
  is ECMAScript's own Date Time String Format, with exactly three fraction
  digits. More digits, as today's `.228127`, are implementation-defined.
  The app parses session times with `new Date(iso)` and runs on Hermes,
  which no machine here can test (no Hermes binary on disk).
- **Microseconds are dropped.** Nothing reads them. Every session list
  orders by `created_at DESC, id DESC`, so `id` breaks ties.
