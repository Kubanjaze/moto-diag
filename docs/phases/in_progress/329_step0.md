## What Step 0 measured

1. **PR 99 merges onto `135bde2` and its tests pass**: 79 (`test_phase329_*`)
   plus 409's 22, on FastAPI 0.136.3, live's line. On FastAPI 0.165.0 (what
   an unpinned install takes today) 409's anonymous-surface pin fails, as
   F287 and F312 already record; the cloud venv is pinned to 0.136.3, and
   to live's pypdf 6.14.2 and pypdfium2 5.15.2 (as 409's log did).
2. **A form-action problem in PR 99's pages, found by reading the CSP.**
   The site's staged `_headers` lets `/signup/*` post only to
   `https://api.getmekno.com`, and the server's confirm page allows
   `form-action 'self'`. Each of those posts is answered by a 303 redirect:
   to a getmekno.com page, or to Stripe's checkout. Browsers check
   `form-action` against the redirect's target too (Chrome does, and the
   CSP 3 text says so), so as staged the form would end on a blocked page
   and the confirm button could never reach Stripe. Fixed in this phase,
   with a test that reads both policies and every redirect target the
   routes can send.
3. **330's wizard and the sign-up make a shop differently.** The wizard
   (`src/motodiag/cli/shop_onboard.py`) calls `create_shop` with no
   `owner_user_id`, so every hand-made shop's row says owner 1 (the system
   user), and `UNIQUE(owner_user_id, name)` then makes shop names unique
   across all hand-made shops; the owner is only the `shop_members` row.
   The sign-up passes the new owner's id, so its shop's row names its real
   owner. The membership, the login and the terms acceptance are the same.
   Nothing reads `shops.owner_user_id` for access (membership decides), so
   nothing breaks today; but the two kinds of shop differ, and the prompt
   asks for a finding when they do: filed as a finding (below).
4. **The payments feed reaches the sign-up.** Stripe cannot call the
   server's webhook (it is polled, Phase 371, K65), and
   `payments/event_feed.py` hands every `customer.subscription.*` event to
   the same `dispatch_event`, so a paid sign-up completes within about 20
   seconds of Stripe's event. The feed runs in `motodiag-payments.service`,
   which reads the same `server.env` as the API, so the welcome email sends
   from there with the same settings.
5. **A failure in `_complete_signup` is not retried** (`SubscriptionEventError`
   is recorded as processed with its error), so the cursor never holds on
   it; it needs a person, hence the support email in the gap list.
6. **The migration path.** Migration 093 adds two empty tables and changes no
   row, so it is not a rule-1 stop, but it reaches live only through the
   deploy skill: a scope file, the dry run from the Mac, the diff committed,
   `apply-live` after the regression of record and before the close-out
   commit (K18). The units start with `--skip-migrations`.
7. **Chunked uploads (F310)** are due "before 410 and before 329's first
   self-serve shop". 329 ships with the shops' switch off (K141), so no
   self-serve shop exists until the operator turns it on after shop 10;
   the handoff says that switch waits for F310. Individuals meet the
   app's 100 MB video message (409's app half). Not built here.
8. **The app.** K152: "the app only signs in". The sign-in screen's line
   "No account yet? Email support@getmekno.com" noted on 2026-11-25 is an
   app change, and pointing from the app to a web sign-up touches Apple's
   rules on outside purchases, which 410 reads at its Step 0. So no app
   change in 329; carried to 410.
9. **Unpaid sign-ups keep a password hash forever** in PR 99. The draft
   privacy 1.3 line says 30 days; the form's route deletes unpaid sign-ups
   older than that, and spent or expired codes older than a day.
