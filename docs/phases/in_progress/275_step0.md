## S0-3. How the two calendars relate (decided)

An appointment is the customer's booking: who comes in, with which bike,
when, and which mechanic sees them. A bay slot is where a work order's
work happens. They are different facts, and neither is copied into the
other:
- **The link is the work order.** Migration 077 gives `appointments` a
  `shop_id` and a `work_order_id` (0 live rows, so no row changes).
  `shop appointment check-in` opens the work order from the appointment,
  or links one given, and the appointment then points to it; its bay slots
  are that work order's.
- **One calendar, read live from both tables.** `shop calendar` lists a
  range's appointments and bay slots together, and the iCal output is
  built the same way, each event from exactly one row with a stable UID
  (`appointment-<id>@…`, `bay-slot-<id>@…`). There is no second store to
  drift.
- **Conflicts:** booking a mechanic over their own active appointment is
  refused. An appointment that overlaps a bay slot of a work order
  assigned to the same mechanic is booked with a warning that names the
  slot, since a short consultation during a lift job is ordinary.
- **Time slots** come from the shop's recorded hours
  (`{"mon": "08:00-17:00", …}`). With no hours recorded for that day, the
  command says so and takes `--open`/`--close`; it never assumes 9 to 5.

Say if you want it otherwise.

## S0-4. Accounting files: what the data gives

- **Customer:** `customers.name` (Xero's `ContactName` must match the
  contact in Xero exactly, per the page; the export uses the name as
  stored).
- **Accounts:** nothing names an account. A per-shop mapping, set by the
  user, maps each line type (labour, parts, diagnostic, shop supplies)
  and the tax to the shop's own accounts (and, for Xero, its tax rate's
  display name). The export refuses while any needed mapping is missing,
  and names it; no account is invented.
- **Tax:** one amount per invoice. For Xero it is spread over the lines
  in proportion to their amounts, the rounding remainder on the last
  line, so the lines sum to the invoice's tax exactly; prices are written
  tax-exclusive, as the page requires with `TaxAmount`.
- **Due date:** not recorded on generated invoices. Written when recorded,
  otherwise left blank (Xero: "Any other fields can be left blank").
- **Which invoices:** issued in the range, not cancelled. Each export is
  recorded, and an invoice already exported to that target is left out
  unless asked for, so a second import does not post it twice.
- **Nothing is uploaded.** The file is written locally.

## Questions for the operator

### 1. iCal: a file, or a feed

**(A) An `.ics` file, by command. (Recommended.)**
- Ships `motodiag shop calendar export --shop S --from D --to D
  [--mechanic U | --bay B] --out FILE.ics`, and `shop calendar` to view
  the same range in the terminal.
- One-way, a snapshot: the user imports it, and re-exports after
  changes. UIDs are stable and a cancelled appointment is written with
  `STATUS:CANCELLED`, so a re-import updates rather than duplicates in
  apps that honour UIDs.
- No route, no gate 11, no mobile session.

**(B) A feed a calendar app subscribes to, on the tailnet API.**
- Ships A's command, plus `GET /v1/shops/{id}/calendar.ics` and
  `shop calendar feed create/list/revoke`.
- **Authentication:** calendar apps cannot send the API's `X-API-Key` or
  `Authorization: Bearer` header. The feed would need its own read-only
  secret token in the URL (`…/calendar.ics?token=…`), stored hashed,
  scoped to one shop (or one mechanic), revocable. A URL token is a
  second way into the API and ends up in each app's settings.
- **Reach:** only a calendar app that fetches from a device on the
  tailnet. Google Calendar's "From URL" is fetched by Google's servers,
  which cannot reach a tailnet address, so it cannot subscribe. (I
  believe iCloud-stored subscriptions are also refreshed by Apple's
  servers; unverified, it would be checked before building.)
- **Gate 11:** a new path in the OpenAPI document, so gate 11 (and 12–14
  in `--full`) goes red until a moto-diag-mobile session refreshes the
  snapshot, as 360 and 361 did.

### 2. Confirmations

A confirmation cannot be queued in the notification outbox without a new
event, and a new event changes the table's CHECK and, by F37's lint, the
API's request model. Nothing in the app sends a notification anyway: the
outbox is marked sent by the user.

**(A) A new outbox event, `appointment_confirmed`, and the API with it.**
- Migration 077 rebuilds `customer_notifications` with the new event and
  an `appointment_id` (4 live rows copied unchanged; `work_order_quotes`
  references the table, so the rebuild keeps its ids).
- The API's `NotificationTriggerRequest` gains the event and an
  `appointment_id`. That is an API change: gate 11 red until a mobile
  session refreshes the snapshot. The mobile app could then queue a
  confirmation.

**(B) As A, but the API model keeps its ten events** under a written
per-line opt-out of F37's lint. No schema change and no mobile session,
but the API can list a confirmation it cannot queue, and the opt-out is a
standing exception to the rule the lint exists for.

**(C) A confirmation the shop sends by its own means, recorded in the
contact log. (Recommended.)**
- Ships `shop appointment confirm ID --channel phone|sms|email|in_person`:
  it prints the confirmation (day, time, bike, mechanic, the shop's
  address and phone) for the staff to send or read out, sets the status
  to `confirmed`, and records an outbound contact in 274's log
  (`customer_communications`) with the text.
- No notification event, no API change, no mobile session. It records
  what happened, which is the same thing the outbox records today.

### 3. Which QuickBooks file (found at Step 0)

The prompt expected a choice between Online and Desktop. Intuit's pages
make it sharper: **QuickBooks Online's invoice import refuses any company
that has set up sales tax** ("If you have set up sales tax in your
account, you can't import invoices this way"). A shop that charges sales
tax on parts cannot use it.

**(A) QuickBooks Online, the journal-entry import. (Recommended.)**
- One journal entry per invoice: `Journal No.` the invoice number;
  debit Accounts Receivable with the customer as `Name`; a credit per
  line type to its mapped income account; the tax credited to the mapped
  sales-tax liability account. Debits equal credits, tested per entry.
- Works on every QuickBooks Online plan, with sales tax set up.
- In QuickBooks it is a journal entry, not an invoice: the tax does not
  reach QuickBooks' own sales-tax centre, and the entry carries no line
  items. Whether a payment can be received against it in QuickBooks is
  not stated on Intuit's page and is not claimed.

**(B) QuickBooks Online, the invoice import.** Real invoices with lines,
for a company with no sales tax set up. Refused by QuickBooks for any
other. Can ship alongside A as a second format (`--as invoices`).

**(C) QuickBooks Desktop, an IIF file** with invoices and their
sales-tax line (Intuit's `iif1` sample). Desktop only; Intuit stopped
selling Desktop Pro Plus and Premier Plus to new US subscribers after
2024-09-30, and gives no support for IIF.

### 4. Xero's header row (a note, with a default)

Xero's page says not to delete or rename the template's columns, and the
template itself is behind a Xero login. The page names the columns it
explains (`ContactName`, `EmailAddress`, the `POAddress` fields,
`InvoiceNumber`, `Reference`, `InvoiceDate`, `DueDate`,
`InventoryItemCode`, `Description`, `Quantity`, `UnitAmount`, `Discount`,
`AccountCode`, `TaxType`, `TaxAmount`, `TrackingName`, `TrackingOption`,
`Currency`, `BrandingTheme`). **Default:** the file uses exactly these
names, the test pins them against this list, and the log records that the
header was not compared with a downloaded template. If you can download
the template from a Xero organisation, paste its first line and the test
pins that instead.
