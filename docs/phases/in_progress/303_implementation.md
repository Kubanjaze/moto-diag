# Phase 303 — Multi-user auth with roles

**Version:** 1.0 | **Tier:** Standard | **Date:** 2026-10-27

---

## Goal

A shop's staff get their own logins. Today a person reaches the API only by pasting an API key that the operator mints by hand on the server (`motodiag apikey create --user N`, Phase 176), and the CLI has no command that creates a staff user at all. The roles the row names already exist: Phase 112 seeded owner, tech, service_writer and apprentice with their permissions, and Phase 172 gave each shop member a role that `has_shop_permission` in `src/motodiag/shop/rbac.py` walks. Phase 180's shop routes already refuse a non-member and check the member's permission on every write. What does not exist is the front door: no password is ever set or checked, no session token is issued, nothing logs out.

This phase ships that front door and nothing behind it:

- **Owner, tech, service writer and apprentice:** a user is created with a password from the CLI, then given a role at a shop with the existing `shop member add`. Login returns the user's memberships and roles, so a client knows what the person may do.
- **Permission gating** on the new path, with the existing tables: the owner's password reset for a member needs `manage_users` at that shop, through `require_shop_permission`. No existing command or route gains a gate it does not have today (Step 0's classification, extension, holds only on that).
- **Session management:** a login makes a session token, shown once and stored hashed exactly as an API key is; a session expires, is revoked by logout, by a password change, by the owner's reset, by the CLI, or when the user is deactivated. Every route that takes an API key today also takes a session token, and so does the live socket, so a logged-in tech reaches the shop console, the knowledge base and the live stream the same way a key does.

**Where a session lives.** The Captain's recommendation, for the operator's word at the one stop below: a session is a row of the existing `api_keys` table, whose columns (`user_id`, `key_prefix`, `key_hash`, `name`, `last_used_at`, `is_active`, `created_at`, `revoked_at`) are every column a session needs but an expiry, and the expiry is computed from `created_at` and one setting. A session token begins `mds_`, an API key begins `mdk_`, and the existing `verify_api_key` refuses anything that is not `mdk_`, so the two never pass for each other. This design has no migration, so there is no dry run, no live apply and no deploy order to keep, and the fleet runs the phase end to end as it stands. The alternative, a new `user_sessions` table by migration 088, cannot be deployed by the fleet as it is today; what that would take is written under the stops, and the operator chooses.

The Science Officer asked for the `authenticate` and `password` hits in src to be read before the build. Read for this plan: they are the users table's nullable `password_hash` column and its model and repository field (Phase 112, `src/motodiag/auth/models.py`, `src/motodiag/auth/users_repo.py`), the API-key layer (Phase 176, `src/motodiag/auth/deps.py`, `src/motodiag/auth/api_key_repo.py`) and docstrings that say the CLI has no authenticated user (`src/motodiag/shop/attribution.py`, `src/motodiag/cli/diagnose.py`). No password or session code exists. Phase 112's note that real authentication would arrive with Track H is half answered: Track H's Phase 176 shipped API keys and left passwords unwritten. That is a plan note, not a stop, and this phase writes the other half.

What this makes for Phase 348: every request resolved from a session or a key leaves the resolved caller (user id, credential kind, credential id) on the request, so 348's log can record which staff login did what (the plan of record, 2026-10-27: "348's log records which staff login did what, which 303 makes").

## The operator's requirements (K55)

The operator's four security requirements for this phase, verbatim, recorded as **K55** in `docs/decisions.md` (2026-10-27). They are the operator's words, applied literally, and where they and the text below differ, they govern: requirement 1 adds to item 7's reset gate, requirement 2 to item 3's `authenticate`, requirement 3 removes the `api_key` query parameter from item 5 for a session (a key keeps it, as today), and requirement 4 fixes how item 3 computes expiry. Each is listed with the test that will prove it, and in the finish lines of items 3, 5 and 7.

1. "The owner's password reset must refuse when the person being reset is an owner at any shop, or belongs to any other shop where I don't have manage_users; test it with a member who owns a second shop."
   Test: `tests/test_phase303_auth_api.py`. A member of the caller's shop who owns a second shop is refused by `POST /v1/auth/shops/{shop_id}/members/{user_id}/password`, and so is a member who is an owner at any shop, and a member who also belongs to a shop where the caller has no `manage_users`; the target's hash and sessions are unchanged after each refusal. The control: a plain tech of the caller's shop, with no other membership, is reset (204).
2. "A login with an unknown or passwordless username must still run the password check against a fixed dummy hash before saying no, so a wrong name and a wrong password take the same time; test that both paths run the check."
   Test: `tests/test_phase303_sessions_repo.py`. With `verify_password` wrapped by a spy, `authenticate` with an unknown username and with a user whose hash is null each calls it exactly once, against the module's fixed dummy hash, and returns `None`; a wrong password for a real user calls it once against that user's hash. The control: the dummy hash is a well-formed `scrypt$…` string, so the check runs the full derivation and does not return early on a bad shape.
3. "A session token must never land in a log: the live socket takes a session only through the bearer subprotocol, not the api_key query string; test that no "mds_" text appears in the captured logs."
   Test: `tests/test_phase303_live_session.py`. A session opens `/v1/live/{id}` through the `bearer.<token>` subprotocol; the same token in the `api_key` query string is refused with the socket's no-credential close code; across login, a REST call with the session, the subprotocol open and the refused query-string attempt, the captured logs (`caplog` at DEBUG for every logger, the access log included) hold no "mds_" text. The control: a planted log line carrying the token turns the same assertion red.
4. "Session expiry must compare real UTC times, never date text, because created_at is SQLite's "YYYY-MM-DD HH:MM:SS"; test sessions made 30 days plus a minute ago and 30 days minus a minute ago."
   Test: `tests/test_phase303_sessions_repo.py`. `created_at` is parsed into a timezone-aware UTC `datetime` and compared with the current UTC time; a session whose `created_at` is written as 30 days plus a minute ago verifies to `None`, and one 30 days minus a minute ago verifies to its row, under `session_lifetime_days = 30`. A mutation that compares the text instead is in `303_mutate.py` and turns one of the two red.

2. **`src/motodiag/auth/passwords.py`** (new): `hash_password(plain) -> str` and `verify_password(plain, stored) -> bool`. The stored form is one string, `scrypt$<n>$<r>$<p>$<salt>$<hash>`, from `hashlib.scrypt` (n 2**14, r 8, p 1, 32-byte key) with a fresh 16-byte salt from `secrets`, compared with `hmac.compare_digest`. `MIN_PASSWORD_LENGTH = 8`; shorter raises `PasswordTooShort`. A stored value that is null, empty or not in this form verifies false, so the seeded system user and every pre-existing user can never log in until a password is set. The library is the Captain's decision, not a stop: the standard library installs nothing on the desktop's service, and the stored string carries its parameters so a later change still verifies old hashes. Recorded in the phase log as a decision.
   Finish line: a password verifies against its own hash; a wrong password, a null hash and a hash of a different shape all fail; two hashes of one password differ; the system user never verifies.

3. **`src/motodiag/auth/sessions_repo.py`** (new) and one line in `src/motodiag/auth/api_key_repo.py`. `ApiKey` gains a property `kind`: `"session"` when `key_prefix` begins `mds_`, else `"api_key"`; nothing else in that module changes. In the new module: `SESSION_PREFIX = "mds_"`; `create_session(user_id, client, db_path) -> (ApiKey, plaintext)`, the token `mds_` plus `secrets.token_urlsafe(24)`, stored with `key_prefix(plaintext)` and `hash_api_key(plaintext)` and `name` `session:<client>` (or `session`), the same shape as a key; `session_expires_at(row, lifetime_days) -> str`, computed from `created_at`, never stored; `verify_session(plaintext, lifetime_days, db_path) -> Optional[ApiKey]`, which returns a row only when its prefix is `mds_`, its hash matches, it is active, it is not past its expiry and its user is active, and updates `last_used_at` as `verify_api_key` does (the one column `deploy.SERVER_WRITES` already names, F208: no gate changes); `revoke_session(session_id, db_path)`, `revoke_user_sessions(user_id, keep_session_id=None, db_path)` and `list_user_sessions(user_id, include_revoked=False, db_path)`, each confined to rows whose prefix begins `mds_`; and `authenticate(username, password, db_path) -> Optional[dict]`, which returns the user row on a match and `None` for an unknown name, a wrong password, a user with no password and an inactive user alike, with one reason string, so the login route cannot tell a caller which it was. A change to the lifetime setting moves every open session's expiry at once, and the guide says so.
   Finish line: each function's tests; `verify_api_key` refuses an `mds_` token and `verify_session` refuses an `mdk_` key; a request authenticated by a session changes `last_used_at` of its own row and no other byte of `api_keys` (the control, compared row for row); an expired, a revoked and a deactivated user's session each verify to `None`; K55 requirement 2 (an unknown and a passwordless name each run the check against the fixed dummy hash) and requirement 4 (30 days plus a minute expired, 30 days minus a minute valid, compared as UTC times) each have their test.

4. **`src/motodiag/auth/deps.py`**: a session is a second credential, resolved by the same functions everywhere. `resolve_credential(plaintext, db_path) -> Optional[ApiKey]` dispatches on the prefix: `mdk_` through `verify_api_key` as today, `mds_` through `verify_session` with `settings.session_lifetime_days`, anything else `None`. `get_api_key` calls it and stashes the result on `request.state.api_key` as today; `require_api_key` keeps its 401 and its message names a session token too. `resolve_tier(credential, db_path) -> Optional[str]` is the one tier function: for a key caller, the user's own active subscription, exactly today's rule; for a session caller, the user's own active subscription, else what the operator's answer to part (c) says, under the recommended reading the highest active subscription of an owner-role active member of any shop the caller is an active member of. `AuthedUser` gains `credential_kind` (`"api_key"` or `"session"`, default `"api_key"`); `api_key_id` and `api_key_prefix` stay as they are, because a session is a row of the same table. `get_current_user` uses `resolve_tier` and stashes `request.state.caller` (user id, credential kind, credential id) for Phase 348. `require_tier` is unchanged. The eight `kb.py` routes change nothing: their `ApiKey` annotation stays true.
   Finish line: `tests/test_phase176_auth_billing.py` and `tests/test_phase180_shop_api.py` pass with no edit; a session token reaches `/v1/shop/profile/list` with the same 401, 402 and 403 semantics a key gets; a revoked or expired session is 401; a tech's session with no subscription of their own reaches a shop route under the recommended reading; the kb routes answer a session.

5. **`src/motodiag/api/routes/live.py`**: its step 1 calls `resolve_credential` in place of `verify_api_key`, so an `mds_` token in the `api_key` query parameter or the `bearer.<token>` subprotocol opens the socket; its step 2 calls `resolve_tier(credential, db_path)`, and the module's own `_resolve_tier(user_id)` is removed, so one function decides every caller's tier (deps, the middleware and the socket). The close codes and reason strings are unchanged.
   Finish line: a session opens `/v1/live/{id}` for its own diagnostic session and is closed with the same codes a key gets for no subscription and for another user's session; `tests/test_phase18*_live*.py` and every existing live test pass with no edit; the "tier rule" mutation in the mutation script breaks exactly one function; K55 requirement 3: a session opens the socket only through the bearer subprotocol, the `api_key` query string refuses it, and no "mds_" text appears in the captured logs.

6. **`src/motodiag/api/middleware.py`**: `_try_resolve_api_key` calls `resolve_credential`, and the limiter's tier comes from `resolve_tier`, so a logged-in caller is limited at their tier and not as an anonymous address. The limiter key stays `key:<id>`: ids are unique in the one table and a key caller's string is unchanged. Login itself stays limited as anonymous by the existing settings; nothing is added to `_RATE_LIMIT_EXEMPT_PATHS`.
   Finish line: a session caller's `X-RateLimit-Limit` is their tier's; an unauthenticated login attempt counts against the address's anonymous budget.

7. **`src/motodiag/api/routes/auth.py`** (new), included in `src/motodiag/api/app.py` under `/v1` beside the others; `src/motodiag/api/openapi.py` gains an `auth` tag, `/v1/auth/login` in `PUBLIC_PATH_PREFIXES`, and the `bearerAuth` scheme's text says a session token is accepted too.
   - `POST /v1/auth/login` `{username, password, client?}` → 200 `{token, expires_at, user: {id, username, full_name, email}, memberships: [{shop_id, shop_name, role, permissions}]}`; 401 with one problem type for every failure (no 404 for an unknown name). No key or session needed.
   - `GET /v1/auth/me` → the same user and memberships block plus `credential: {kind, id, prefix}` and `tier`; any credential.
   - `POST /v1/auth/logout` → 204, revokes the calling session; a key caller gets 400 (`not-a-session`).
   - `GET /v1/auth/sessions` → the caller's unrevoked sessions (prefix, client, created, expires, which one is current); `DELETE /v1/auth/sessions/{id}` → 204 for one of the caller's own, 404 for anyone else's and for a key's id.
   - `POST /v1/auth/password` `{current_password, new_password}` → 204; wrong current is 401; too short is 422; every other session of the user is revoked, the calling one kept.
   - `POST /v1/auth/shops/{shop_id}/members/{user_id}/password` `{new_password}` → 204; `require_tier("shop")`, then `require_shop_permission(shop_id, caller.id, "manage_users")`, then the target must be an active member of that shop (404 otherwise); all the target's sessions are revoked. This is the row's permission gate on the new path: an owner may, an apprentice may not, a member of another shop may not.
   Finish line: each status above has a test; a token appears in exactly one response body ever; the problem-detail envelope and request id match the existing routes (`src/motodiag/api/errors.py` maps the new `NotASessionError` and `PasswordTooShort`); K55 requirement 1: the reset refuses a member who owns a second shop, an owner at any shop, and a member of any other shop where the caller has no `manage_users`.

8. **`src/motodiag/shop/rbac.py`**: one addition, `list_member_permissions(shop_id, user_id, db_path) -> list[str]`, the permission names the member's role grants, by the same join `has_shop_permission` walks. Nothing else in the module changes.
   Finish line: an owner lists every seeded permission, an apprentice its read-mostly set, a non-member and an inactive member an empty list; `has_shop_permission` agrees with the list for every name.

9. **`src/motodiag/cli/user.py`** (new), registered from `src/motodiag/cli/main.py` as the top-level group `user`, the way `apikey` is (no command or alias takes the name today: the groups are `config`, `db`, `garage`, `intake`, `apikey`, `subscription`):

   - `user list [--include-inactive] [--json]`: id, username, full name, active, whether a password is set (never the hash), open sessions.

   - `user deactivate USER`: `deactivate_user` (which already refuses the system user) and revokes sessions.

   And in `src/motodiag/cli/apikey.py`, `apikey list` and `apikey show` skip rows whose prefix begins `mds_`, so sessions appear only under `user sessions`; `apikey revoke` is unchanged, and revoking a session by id through it is harmless and tested.

## Rule-1 stops anticipated

- **A real fork, part (a) of the one question:** where sessions live, two plans that ship different things. The API-key table, with no migration and the fleet running end to end, is the Captain's recommendation and the plan as written. A new table by migration 088 is the other plan; what it would take is written at the end of Logic, and it cannot go through the fleet as it stands.
- **A real fork, part (b), Step 0's first stop:** gate only the new login path, or gate the existing CLI and the diagnostic commands too. The plan takes the first: every existing command and route behaves exactly as today for the callers it has today, and the only new gate is `manage_users` on the owner's reset. The second reading changes what current commands do, is a reshape by Step 0's own words, and goes back to Step 0 for the Admiral.
- **A real fork, part (c), not in Step 0:** how a staff member who logs in meets `require_tier("shop")`, which reads a subscription per user. A tech has no subscription of their own, so without a rule every shop route answers their session 402. Two plans: (i) a session caller's tier is their own subscription, else their shop owner's, and an API-key caller is resolved exactly as today; (ii) the tier rule changes for every caller, keys included, which changes today's behaviour and is a reshape. The Captain recommends (i); `resolve_tier` is built to the operator's words.
- **A threshold or a rule's definition, part (d):** two numbers the operator confirms in the same answer: a session lives 30 days from login (`session_lifetime_days`), and a password is at least 8 characters. No lockout count, no idle timeout and no change to `deploy.SERVER_WRITES` (a gate's definition, F212) are planned; if the Red Team asks for any, it is a stop, not a change the builder makes. Step 0's "credential decision" on how passwords are stored is a library choice, none of rule 1's five kinds, and is decided in Logic item 2 and logged.
- **A test it cannot make green:** none expected. If `tests/test_phase176_auth_billing.py`, `tests/test_phase180_shop_api.py` or any existing live-socket test goes red under items 4 to 6, that is the signal the change altered today's behaviour, and the builder stops rather than editing them.
- **A login or a credential:** none needed from the operator, and none written anywhere by the agent. The operator's own password is set by the operator's hand after the merge and is never typed into an issue, a log or a paste block.
- **A live-database change:** none under the plan as written: no migration, no row altered or deleted, and a login writes only its own new row and `last_used_at`, as a key does today. ## Non-goals

- The app's login screen. Phases 185–204 are the mobile repository's (`ROADMAP_AUTHORITY.md`); until a mobile phase adds the screen, the app keeps its API key, and the API this phase ships is what that screen will call.
- Gating the CLI, the diagnostic commands or any existing route beyond what it checks today (part (b)'s second reading).
- A lockout after failed logins, an idle timeout, a stored expiry column, or any addition to `deploy.SERVER_WRITES`.
- Password reset by email, single sign-on, two-factor, or retiring API keys.
- Phase 348's audit log itself; this phase only leaves the caller on the request for it.
- A migration of any kind under the plan as written; anything under `data/`; seed data; a split or an eval protocol.
- The fleet's own gaps this phase measures and files: a way back from a rule-1 stop, and a deploy stage. Each is a later fleet phase that must name the first-shop phase it unblocks (K43 rule 4).
- F210's general rule (row 330's need, K52). A login between a later phase's dry run and its apply adds an `api_keys` row that phase's apply would refuse, as a key minted in that window does today; this phase adds to that case and does not settle it.
