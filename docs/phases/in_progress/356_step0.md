# Phase 356 — Step 0: the engine, the checklist, and how a run picks its powertrain

**Measured 2026-09-27, before v1.0**, on `phase-356` branched from
`master` at `a2eafef`, against a freshly migrated database in the session
scratchpad (`s0/f.db`, `init_db`, schema 72). No step read
`data/motodiag.db`.

## S0-1: K8, the row's verbs

Row 356 promises four actions. Each needs a way for a user to do it, and
`motodiag workflow run <slug>` is that way for all four:

| the row's verb | how a user does it |
|---|---|
| each item in order | `run` prints item 1, waits for the answer, then item 2 |
| pass or fail recorded as the mechanic answers | the answer at each prompt goes to the engine's `report_result` |
| the template's diagnosis printed on a fail | printed right after a fail answer |
| a summary at the end | printed when the last item is answered |
| chooses its powertrain | the operator's pick below (S0-4) |

Each is driven by a `CliRunner` test with input.

## S0-2: Phase 82's engine, and what a checklist needs from it

`src/motodiag/engine/workflows.py`, 411 lines, imports nothing from
`motodiag.workflows`:

- `StepResult`: `pass`, `fail`, `unclear`, `skipped`.
- `WorkflowStep`: `step_number`, `test_instruction`, `expected_pass`,
  `expected_fail`, `result`, `mechanic_notes`, `diagnosis_if_fail`,
  `next_step_if_pass`, `next_step_if_fail`.
- `DiagnosticWorkflow.report_result(result, notes)` records the result on
  the current step, sets `working_diagnosis` to the step's diagnosis on a
  fail, advances, and returns the next step or `None` when
  `is_complete()`.
- `is_complete()` is true when the index reaches `max_steps` (default
  10), or the end of the steps, **or when any step has failed and a
  working diagnosis is set**.
- `get_results_summary()` gives status, `steps_completed`,
  `steps_total` and a per-step list with the instruction cut to 80
  characters. It has no title.

**Measured: fed a checklist, the engine stops at the first fail.** Built
from `brake_service_v1` (7 items) and `valve_adjustment_v1` (8), a pass
then a fail gives `next=None`, `is_complete()` true, status `complete`,
2 of 7 (and 2 of 8) answered. Every item of the 13 active templates has a
`diagnosis_if_fail` (0 without one), so every fail would end the run.
That is the engine's decision tree ("narrows the diagnosis ... until a
confident conclusion"); a checklist goes through every item whatever an
earlier one found.

### The mapping, item to step

| `checklist_items` | `WorkflowStep` |
|---|---|
| `sequence_number` | `step_number` |
| `instruction_text` | `test_instruction` |
| `expected_pass`, `expected_fail` | the same |
| `diagnosis_if_fail` | the same |
| `title`, `description`, `required`, `tools_needed`, `estimated_minutes` | no field: the command keeps the item beside its step, by index, and prints them |

- Items come in `sequence_number` order from `get_checklist_items`.
- `max_steps` is set to the number of items. The largest active template
  has 8, under the default 10, but a limit that silently ends a run
  should not depend on that.
- **Optional items** (`required = 0`; 28 of 91 items in the active
  templates, all 7 of `drivetrain_service_v1`) accept pass, fail or
  skip, and a skip is `StepResult.SKIPPED`. A required item accepts pass
  or fail only: the row says "pass or fail". `unclear` is not offered.
- The summary is printed by the command from the engine's steps (each
  step's `result`) and the items beside them: counts of passed, failed,
  skipped, and each failed item with its diagnosis.

### One engine change is needed

`DiagnosticWorkflow` gains `stop_on_fail: bool = True`, and
`is_complete()`'s third clause applies only when it is true. The runner
sets it false. The default keeps Phase 82's behaviour, and its 26 tests
(and Gate 3's use of it) do not change; a new test holds both values.

The alternative, no engine change, is to leave `diagnosis_if_fail` off
each step so the engine never concludes early. It was rejected: the
diagnosis would then live outside the engine the row connects to, and
`working_diagnosis` would be wrong.

## S0-4: the powertrain, a real fork

Items carry no powertrain (F165). Applicability is the template's
`applicable_powertrains`: 8 active templates cover ice, electric and
hybrid; 5 cover ice and hybrid only (`emissions_v1`,
`engine_break_in_v1`, `ppi_engine_v1`, `track_prep_v1`,
`valve_adjustment_v1`). **In both options the powertrain gates the
template and nothing else**: no item is filtered, because none carries
one. Powertrain-specific steps in templates that cover both kinds are
optional (272's S0-4), and the mechanic skips them.

### Option A: the run asks, or takes `--powertrain`

```
$ motodiag workflow run valve_adjustment_v1 --powertrain electric
valve_adjustment_v1 covers ice, hybrid, not electric.
(exit 1)

$ motodiag workflow run brake_service_v1
Powertrain (ice, electric, hybrid): electric
Brake service — brake_service_v1 · for electric · 7 items
1. <title>
  <instruction>  Pass: …  Fail: …
  Result [p/f]: …
```

- Ships: a `--powertrain` choice; without it, a prompt with the same
  three choices. No garage lookup.
- Tests: the flag and the prompt each start a covered run; each refuses
  an uncovered one before item 1; a planted template that stops covering
  the powertrain turns the acceptance red.
- Holds against nothing it cannot check: a mechanic can type the wrong
  powertrain.

### Option B: a bike from the garage supplies it

```
$ motodiag workflow run valve_adjustment_v1 --bike zero-2021
2021 Zero SR/F is electric; valve_adjustment_v1 covers ice, hybrid.
(exit 1)

$ motodiag workflow run brake_service_v1 --vehicle-id 3
Brake service — brake_service_v1 · 2021 Zero SR/F (electric) · 7 items
…
```

- Ships: `--vehicle-id N` or `--bike SLUG` (the forms `diagnose quick`
  takes, through its resolver), one of them required; the powertrain is
  `vehicles.powertrain`. A run with no bike is refused.
- Tests: garage rows in a `tmp_path` database; a covered bike runs, an
  uncovered bike is refused, an unknown bike is refused, neither flag is
  refused.
- Measured risk: `garage add` defaults `--powertrain` to `ice`
  (`cli/main.py:442`), so an electric bike added without the flag is
  stored as ice and would be given ICE-only templates. A mechanic with
  no garage row cannot run a checklist at all.
- It reads the link 357 will save (row 357: a run "tied to a bike or a
  work order"), without saving it.

### Option C: both

`--bike`/`--vehicle-id` supplies the powertrain when given; otherwise
`--powertrain` or the prompt; both given and disagreeing is refused. The
union of A's and B's tests, plus the disagreement.

### Recommendation

**A.** It ships what the row scopes ("nothing saved"), depends on no
garage row, and cannot be misled by the garage's `ice` default. The bike
link belongs with 357, where a run is tied to a bike and saved, and
there it can supply the powertrain as C does.
