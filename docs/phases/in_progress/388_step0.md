## S0-5. F215, and what bubblewrap does about it here

**What F215 found on the Mac** (`docs/FOLLOWUPS.md`, F215;
`387_phase_log.md`, bug fix #1): Read, Grep and Glob need no permission, so
the read-only ranks could read any file the operator's account can, and
their text lands in a public repository. Path-scoped deny rules held for
the paths listed (`rank_call.SECRET_HOMES`), but that is a denylist: a
canary in the scratchpad was still read. It asks the fence phase to confine
reads to the clone, a planted read outside it refused.

**What bubblewrap does here** (`bwrap --version` → 0.11.1; `unshare -Ur
true` → exit 0, so unprivileged user namespaces work and no `sudo` is
needed). A prototype fence, run as the operator's user:

- **Layout:** `--unshare-all --clearenv`; `/usr` and `/etc` bound
  read-only with the four root symlinks; a private `/proc`, `/dev` and
  `/tmp`; **no `/home` at all**; under `/fleet`, the clone writable at
  `/fleet/moto-diag`, the run directory writable at `/fleet/run`,
  `workspace-docs` read-only at `/fleet/workspace-docs`, the claude binary
  read-only at `/fleet/bin/claude`; then `--remount-ro /fleet` and
  `--remount-ro /`.
- **Writes outside refused**, each by `bwrap … touch <target>`: the real
  repository's tree and its `.git`, `~/.claude` and `~` → "No such file or
  directory" (not mounted); `/`, `/fleet`, `/usr`, `/etc` → "Read-only file
  system"; `mkdir -p /home/lilcu` → "Read-only file system". Nothing
  appeared on the host (`ls` of the targets afterwards).
- **Reads confined:** `cat /home/lilcu/.config/gh/hosts.yml` → "No such
  file or directory". This is F215's case closed by construction rather
  than by a list: the operator's home is not in the fence's view.
- **Inside works:** writes to the clone, the run directory and `/tmp`; `git
  add` and `git commit` in the clone.
- **Pushes fail:** to the clone's `origin` (the real repository's path,
  absent inside) → "Please make sure you have the correct access rights";
  to GitHub over https → "Could not resolve host: github.com".
- **No network at all** under `--unshare-net`: a direct connect to a GitHub
  address → "Network is unreachable".
- **Network for the model call only** (the prototype `net_proto.py`): a
  proxy outside the fence on a unix socket allows `CONNECT
  api.anthropic.com:443` and refuses everything else with 403; a bridge
  inside the fence listens on `127.0.0.1` and forwards to the socket;
  `HTTPS_PROXY` points claude at it. Claude Code 2.1.309 honours it
  (`strings` of the binary: `HTTPS_PROXY` 105 hits, `NO_PROXY` 93). Run with
  a dummy `ANTHROPIC_API_KEY` (no credential, nothing billable): claude
  reached the real API through the gate and was refused "Invalid API key";
  the proxy log has 3 lines `ALLOW CONNECT api.anthropic.com:443`, and
  `curl https://github.com/` and `git ls-remote` from inside got
  `DENY CONNECT github.com:443` (2 lines), "CONNECT tunnel failed,
  response 403". A first socket path in the scratchpad was refused, "AF_UNIX
  path too long" (the limit is 108 bytes): the socket lives in a short
  directory under `/tmp`, bound into the fence by its own path.
- **The fence's config:** with `CLAUDE_CONFIG_DIR` in the run directory,
  claude wrote its `.claude.json` there (`ls -la` of the directory), so the
  import approval for `/fleet/moto-diag` can be seeded in it before the run.

**What stays readable inside:** `/usr` and `/etc`, read-only. Nothing under
`/etc` that the operator's user can read holds the fleet's or the
operator's credentials (`/etc/shadow` and the ssh host keys are root's).
**And one known limit:** the model's credential reaches the fence as an
environment variable, the way `orchestrate.py`'s `run_stage` passes it; a
seat with Bash could print its own environment. The read-only ranks have no
Bash; the first writing seat's phase has to answer this.

## S0-7. What this phase decides, and why

- **The model call is the fenced part; the rank's script is not.** `xo.py`
  and `yeoman.py` run in the dispatcher's process against the fresh clone;
  every `claude` they start goes through `fence.sh`, and every `gh` runs
  outside it. Inside the fence `gh` would need the operator's login file,
  which the fence must not see. The scripts are the repository's own code
  at a commit; the model is the actor that is not trusted.
- **Seeding the import approval** in the fence's config is the fence
  reproducing the operator's approval of 2026-09-23 (this file's change log,
  "the working-rules index is imported") for the fleet's clone path. The
  prompt's ninth case asks for the import to resolve inside the fence; it
  cannot resolve without it (S0-2).
- **The sweep reads the ten state labels, not `mission`.** `mission` marks
  what the issue is and stays for its whole life; a comment on it every day
  would be noise.
- **The daily digest** is written in the stage's clone and kept in the
  dispatcher's state directory; it is not committed (nothing in this phase
  writes to the repository) and not posted. Its delivery is a later phase's.
- **The second Windows task holds the VM**, the same action as 382's, so
  the fleet does not depend on the API's task; the unit is enabled and
  starts with systemd.
