## S0-1 — the plan's nouns in `src/`, and the greenfield question

Vocabulary: `pre-purchase`, `PPI`, `compression`, `leak-down`, `oil
sample`, `fuel quality`, `starter`, `charging health`, `visual
inspection`, over `src/` and `tests/` (case-insensitive, both trees,
excluding `__pycache__`).

What exists:

- **The Phase 114 substrate, complete.** `src/motodiag/workflows/`
  (370 lines): `WorkflowCategory` with 13 members — `PPI` among them —
  `WorkflowTemplate`, `ChecklistItem`, and 11 repo functions
  (create/get/list/update/deactivate/count templates; add/get/update/
  delete items). Migration 007 created `workflow_templates` +
  `checklist_items` and seeded 2 templates with 9 starter items, one of
  which is an engine-compression step inside `generic_ppi_v1`.
- **Phase 82's in-memory engine** (`engine/workflows.py`) — diagnostic
  workflows, a different mechanism, not a template consumer.
- **`engine/wiring.py`** (Phase 92) — a generic charging-circuit
  reference (13.8–14.5 V at 5000 RPM), authored for this project, not
  manufacturer data, and never sourced to a document.

What does not exist: **no user entry point calls the workflows package.**
`grep -rn "template_repo\|workflows" src/motodiag/cli/ src/motodiag/api/`
returns nothing that imports it. No command, no route. A template seeded
by 259 would be as unreachable as Phase 92's reference data was before
244V gave `ref` a front door — the exact shape 244V was built to stop.

**Decision: extension, not greenfield.** The phase is content on the 114
substrate — one migration (067) seeding an engine-PPI template — plus the
one front door the substrate has never had (`motodiag workflow` list /
show). No new tables: `workflow_templates`/`checklist_items` already carry
every field the six subjects need (instruction_text, expected_pass/fail,
diagnosis_if_fail, tools_needed, estimated_minutes).

## S0-2 — the substrate census (what 067 seeds into)

Snapshot `data/motodiag.db`: schema 66 (`schema_version` table, max 66),
`workflow_templates` = 2 rows (`generic_ppi_v1` ppi,
`generic_winterization_v1` winterization), `checklist_items` = 9.
`generic_ppi_v1`'s description says *"Track N phase 259 expands with
engine-specific content"* — a forward pointer this phase either
satisfies or makes stale; migration 067 re-points it at the new
template.

Two schema facts that shape the seed:

- `workflow_templates.slug` is UNIQUE; `checklist_items` has **no unique
  constraint at all** — migration 007's `INSERT OR IGNORE` on items is a
  no-op guard, and re-running an item insert on an already-migrated
  database would duplicate rows. Migration 067 therefore seeds inside the
  one-shot migration journal (like 007 does), not from any re-runnable
  loader path.
- Item identity is prose (title), the same shape as F129's
  `known_issues` complaint. Editing a seeded item's title on a live
  database would duplicate it. Migration 067 seeds once and 259's tests
  pin the content; later corrections must go through a migration keyed on
  the OLD text, the F129 workaround.

## S0-4 — powertrain applicability

The six subjects are ICE subjects: an electric machine has no
compression, no engine oil to sample, no fuel, no starter motor cranking
an engine. `applicable_powertrains = ["ice", "hybrid"]` for the new
template (a hybrid carries an ICE); **not** `"electric"`. This matters
because the substrate defaults to all three and `list_templates` filters
by JSON substring, so a template that kept the default would be offered
for a Zero.
