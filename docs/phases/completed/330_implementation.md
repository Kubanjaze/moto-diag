## Goal

A new shop today is set up one command at a time, by someone who already knows the commands: `motodiag shop profile init` for the shop, `motodiag user create` and `motodiag shop member add` for each person, `motodiag shop customer add` and `motodiag garage add` and `motodiag shop customer link-bike` for every customer and bike, `GET /v1/terms` and `POST /v1/terms/accept` for the terms, and `motodiag workflow run` for a first checklist. Nothing sequences them, nothing says which are done, and a shop with fifty bikes types fifty commands. The Step 0 report (`330_step0.md`) found no onboarding flow, no bike import and no staff setup anywhere in `src`, and classified the phase an extension: the pieces exist, and the wizard adds to them without changing what they do.

After this phase a new shop is onboarded from the server's command line in one sitting:

1. **`motodiag shop onboard run`** walks the owner through five steps, in order, each one skippable and each one safe to run again: the shop's profile; the owner's own login, made the owner of the shop; the staff, each with a login and a role; the Terms of Service, shown by their addresses and accepted by the one owner at the keyboard, for themselves (334 went before 330 "so that 330's onboarding can include the step", K84); and the bikes, imported from one CSV file or typed one at a time, each linked to its customer. It ends with the first diagnostic walkthrough: one workflow checklist walked through on the terminal, saving nothing, so the owner has seen a diagnosis before the first real bike arrives. The last screen says what was made and what to do next.
2. **`motodiag shop onboard import-bikes FILE`** is the import on its own, with a `--dry-run` that writes nothing: a shop's bikes and their customers, from a plain CSV with a header row, all rows checked before any is written.
3. **`motodiag shop onboard status`** says which steps are done, read from the tables that already exist, for one shop or for every shop, and it never refuses. No new table, no migration, no change to live: the wizard writes only through the functions the existing commands call, and only new rows.

Every existing command keeps its behaviour. The wizard is a front door onto `create_shop`, `create_user`, `add_shop_member`, `record_acceptance`, `add_vehicle`, `create_customer`, `link_customer_bike` and the workflow walk; it does not change the profile init, any shop command, or the diagnostic workflow. If the build finds it must, the classification becomes a reshape and that is a stop, as the Step 0 report says.

**Why the command line and not the app.** The Step 0 report classifies this phase as an extension of the shop CLI, which already holds the first-time profile wizard; the signup flow that would trigger an onboarding screen (Phase 329) has not started; and every app screen so far has been its own row built by a session on the app's repository (303B, 334B, 372B; K81, K84, K98, K99). This plan ships the server-side wizard. An app screen for it, if the operator wants one, is a row of its own on the operator's word, named in the handoff's "What is open", not a change this plan makes under `src/`.

2. **`status`** (`shop_onboard.py`; reads only; never refuses).
   - `shop onboard status [--shop NAME|ID] [--json]` prints, for each shop it covers, a block of five rows, each `done` or `not yet`, read from existing tables through existing functions:
     - **shop:** a shop exists.
     - **owner:** an active `shop_members` row with role `owner` whose user has a password set (`list_shop_members` and `get_user`; `password_hash` is never printed, as `user list` never prints it).
     - **staff:** at least one active member in another role. This row says `none yet` rather than `not yet`, because a one-person shop is complete.
     - **terms:** `done` only when at least one active owner member exists **and** every active owner member has `has_accepted(user_id, TERMS_VERSION)`. With no owner the row is `not yet`, never vacuously `done`. An older version's acceptance does not count (334's rule).
     - **bikes:** at least one bike linked to one of the shop's customers (`customer_bikes` joined to `customers` where `shop_id` is the shop's).
     A sixth line says that the walkthrough leaves no record and is offered by `run`.
   - **Which shops it covers.** With `--shop`, that one shop, found as `_resolve_shop_identifier` finds it (an unknown name or id is the one refusal, that function's own). With no `--shop`: no shop registered prints one block whose five rows are all `not yet`, and exits 0; one shop prints its block; several shops print one block per active shop, from `list_shops()` in the order `profile list` uses, each headed by the shop's id and name, and exit 0. `status` does not go through `_resolve_shop_identifier`'s no-identifier branch, so it never prints "Multiple shops exist" and never exits 1 on a healthy database, whatever it holds. `--json` gives a list of objects, one per shop covered, each with `shop_id`, `shop_name` and the five rows under their names; with no shop registered, a list of one object whose `shop_id` is null.
   - The reading is one function per row, `step_shop(...)`, `step_owner(...)` and so on, each taking a shop row (or `None`) and returning `(done, detail)`, so `run` and `status` share them and a test can call each alone.
   - Finish line: on a fresh database every one of the five rows is `not yet` (the terms row included, because no owner exists) and the exit code is 0; after each step of `run`, its row turns; `--json` gives the same five under their names; a shop whose owner accepted version `0.9` only shows `terms` as `not yet`; with two shops and no `--shop`, two blocks print, in id order, and the exit code is 0; `--shop` with a name that exists prints only that block.
3. **`run`: the five steps, then the walkthrough** (`shop_onboard.py`).
   - **The one rule for every step:** a step whose `status` row is `done` (for the staff step, anything but `none yet`) prints that row's detail and asks nothing. A step not done prints what `status` knows, asks "Do this step now? [Y/n]", and is skipped on `n`. The walkthrough is the one part that asks on every run, because it leaves no record to read; it is behind its own question, "Walk through a checklist now? [y/N]", so one `n` passes it. So on a database where the five rows are `done`, `run` asks exactly one question, the walkthrough's.
   - Every answer is a `click.prompt` or `click.confirm`, so a test drives the whole wizard through `CliRunner(input=...)`. The order is fixed, because each step uses what the one before made.

A second owner is not made here: the closing screen names `motodiag user create` and `motodiag shop member add --role owner` for that.

[y/N]"; for each, username, full name, email, role (`click.Choice(SHOP_ROLES)` less `owner`, default `tech`), a first password twice, hidden; `create_user` then `add_shop_member`. The loop ends on `n`, and the step ends by saying that each person changes their own password at `POST /v1/auth/password` after their first login, and that they log in from the app at `POST /v1/auth/login`. The closing screen then says how a real one is saved: `motodiag workflow start <slug> --vehicle-id N`.
     Finish line: a walk answered `p` for every item ends with the workflow module's summary line, the closing screen follows it, and no `workflow_runs` row is written (the table's count before and after is equal); with a template that covers only `ice` and a last-imported bike that is `electric`, the powertrain prompt offers `ice` alone, its default is `ice`, the walk runs for `ice` and the closing screen prints; a fresh database with every template deactivated prints the message and no walkthrough prompt; `n` at the walkthrough question runs no walk.

## Rule-1 stops anticipated

- **A real fork: none known.** The Step 0 report classifies the phase an extension of the shop CLI and leaves no second plan that would ship something different. Where this plan leaves a build choice (the exact wording of prompts and report lines, the dataclass or dict shape of `BikeRow` and `ImportReport`), either choice ships the same behaviour. **Five readings, recorded in the phase log and told to the operator with the pull request:** (1) the wizard is the server's command line, not an app screen or an API route, for the reasons under Goal; an app screen is a row of the operator's own making; (2) "bike inventory" is the shop's customers' bikes, not parts stock; (3) the shop's `owner_user_id` stays the default, and ownership is the `owner` role, as 303 built it; (4) the terms are accepted only by the one owner who says they are at the keyboard, for themselves, never for staff and never for an absent owner; (5) a bike is identified only by its VIN, and a row without one is added again on a second import, reported. If the Engineer finds that any of the five must change an existing command's behaviour to hold, that is the reshape the Step 0 report names, and a stop with kind `fork`.

- **A test that cannot be made green: none known.** If an existing test pins the list of `shop` sub-groups, `register_shop`'s registrations, the root `cli`'s command list, the guide's section text, or the count of CLI commands, it is updated with the reason in the commit message after a grep; a pin this phase cannot satisfy inside this plan is a stop.
- **A login or a credential: none in the build.** Every test makes fixture users with fixture passwords on a temporary database (`cli_db`'s form), and no test reads live (244H).
