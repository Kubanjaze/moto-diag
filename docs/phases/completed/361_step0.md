## S0-3: F178 re-verified

- **The values.** `PowertrainLiteral = Literal["ice", "electric",
  "hybrid_parallel", "hybrid_series"]` (`api/routes/vehicles.py:57–59`).
  `PowertrainType` holds `ice`, `electric`, `hybrid`
  (`core/models.py:67–69`). The list endpoint's `?powertrain=` filter uses
  the same literal (`:213`).
- **The API, probed** (`361_step0_probe_api.py`, a fresh database):

  | value | `POST /v1/vehicles` | `PATCH /v1/vehicles/{id}` |
  |---|---|---|
  | `ice`, `electric` | 201 | 200, stored |
  | `hybrid` | **422** (the literal) | **422** |
  | `hybrid_parallel` | 400 (`PowertrainType(...)` raises) | **200, stored as `hybrid_parallel`** |
  | `hybrid_series` | 400 | **200, stored as `hybrid_series`** |

  The update path hands the string to `update_vehicle_for_owner` →
  `update_vehicle` (`vehicles/registry.py:125`), which converts an enum
  instance to its value but never checks a string against the enum.
- **The safety checker, measured** on "fuel leak pooling under the tank":

  | stored value | rules compiled | fuel-leak alert |
  |---|---|---|
  | `None`, `ice`, `hybrid` | 19 | yes |
  | `electric` | 12 | no (by design) |
  | `hybrid_parallel`, `hybrid_series` | **12** | **no** |
  | `""`, `ICE`, `Hybrid` | **12** | **no** |

  Seven rules are scoped `("ice", "hybrid")` (`engine/safety.py:83, 112,
  125, 212, 225, 236, 247`). `_applies` (`:406–417`) shows every rule only
  for `None`; any other string outside the tuple hides all seven. So the
  hole is wider than F178 says: an empty string or a capitalised value, from
  a raw insert or an old row, hides them too. The docstring (`:392–396`):
  "a blank or wrong value must not be able to hide a fuel-leak warning".
- **The only reader that suppresses on the powertrain** is
  `SafetyChecker._applies`. The others compare with `"electric"` only
  (`knowledge/transmission.py:1013`, `knowledge/prompt_rows.py:157`), so an
  unknown value behaves as `None` there already. `workflow start` refuses
  when a stored value differs from the stated one (`cli/workflow.py:404`),
  which shows nothing and hides nothing.
- **The app can trigger it today.** `moto-diag-mobile`'s
  `src/types/vehicleEnums.ts:76–88` offers both hybrid variants;
  `VehicleDetailScreen.tsx:289–290` fills a missing powertrain with `'ice'`
  and sends it on every save (`:330`). No other app file names the
  variants, besides the generated `src/api-types.ts`.
- **No test** in `tests/` names `hybrid_parallel` or `hybrid_series`.

## S0-5: F177, every path that stores `four_stroke` nobody stated (re-verified)

`grep -rn -i "four_stroke\|FOUR_STROKE" src/` gives 12 lines; these store
it:
1. **The column default**, `engine_type TEXT DEFAULT 'four_stroke'`, in
   three places in `core/migrations.py`:
   - `:275`, Phase 110's `ALTER TABLE ... ADD COLUMN`;
   - `:220`, **migration 074's own rebuild** (`_vehicles_rebuild_074`),
     which the live table now carries: 360 rebuilt the table and kept this
     default by design;
   - `:2980`, an older rollback's rebuilt table (177's era), not edited.
2. **`VehicleBase.engine_type`**, `Field(EngineType.FOUR_STROKE, …)`
   (`core/models.py:156–159`); both registry inserts bind
   `vehicle.engine_type.value` (`vehicles/registry.py:71`, `:218`).
3. **`VehicleCreateRequest.engine_type: EngineTypeLiteral = "four_stroke"`**
   (`api/routes/vehicles.py:85`). Probed: a `POST` with no engine type
   stores `four_stroke`.
4. **`garage add`** derives `FOUR_STROKE` for anything but `electric`
   (`cli/main.py:483–486`). A hybrid is stored four-stroke too.
5. **`garage add-from-photo`**, the same (`cli/main.py:612–615`). The
   vision guess has no engine type at all (`intake/models.py:26–50`).

Not in `src`, the mobile repo's to change: the add-bike form preselects
`'four_stroke'` (`NewVehicleScreen.tsx:84–85`), and the edit screen fills a
missing engine type with `'four_stroke'` (`VehicleDetailScreen.tsx:292–293`)
and sends it on every save.

**Found by this Step 0: the engine type has F178's shape exactly.**
`EngineTypeLiteral` is `four_stroke, two_stroke, rotary, diesel, none`
(`api/routes/vehicles.py:61–63`); `EngineType` is `four_stroke, two_stroke,
electric_motor, hybrid, desmodromic` (`core/models.py:114–118`). Probed:

| value | `POST` | `PATCH` |
|---|---|---|
| `four_stroke`, `two_stroke` | 201 | 200 |
| `rotary`, `diesel`, `none` | **400** | **200, stored as given** |
| `electric_motor`, `hybrid`, `desmodromic` | **422** | **422** |

So the app cannot create a bike with "Rotary", "Diesel" or "N/A" (its
labels, `vehicleEnums.ts:94–108`), an edit stores them, and no API request
can record an electric motor. No reader gates anything on the engine type,
so nothing is hidden; the diagnose prompt would read "Engine: none".

## S0-8: the fork — three options for F177

**Common to all three:**
- **Migration 075 rebuilds `vehicles` with `engine_type TEXT`** (no
  default), by 074's pattern: `_vehicles_rebuild_074` gains an
  `engine_type_def` argument whose default is today's text, so 074's SQL is
  unchanged byte for byte (checked: 074's rebuilt line still reads
  `engine_type TEXT DEFAULT 'four_stroke'`). Foreign keys off, every column
  copied by name, the sequence carried, the three indexes recreated
  unchanged. The rollback rebuilds with `DEFAULT 'four_stroke'`.
  `SCHEMA_VERSION` 74 → 75.
- `VehicleBase.engine_type` becomes `Optional[EngineType] = None`; both
  registry inserts bind NULL.
- **The API's engine-type values become the enum's five**, the same
  decision as F178's part 2: create and update convert through the enum,
  and `update_vehicle` refuses a value outside it. `rotary`, `diesel` and
  `none` go; `electric_motor`, `hybrid` and `desmodromic` become settable.
  No live row holds a value outside the enum. *If the operator would rather
  add `rotary`, `diesel` and `none` to the enum, say so; that is a
  different phase's content.*
- **One derivation stays**: a stated `electric` powertrain gives
  `electric_motor`, because it follows from what was stated. A hybrid is
  no longer stored four-stroke: its combustion engine's cycle was not
  stated.
- `garage add` and `add-from-photo` gain `--engine-type`;
  `garage update` gains `--engine-type` (S0-2).
- Parts sourcing prints `unknown` for NULL.
- Every reader gets a test on a bike stored as NULL.
