## S0-6: the fork — three options for part 1

**Common to all three**, because each is needed whichever entry-point rule
is picked:
- **Migration 074 rebuilds `vehicles` with `powertrain TEXT` (no default).**
  The column default is itself a path (S0-3, item 6). The rebuild follows
  migration 064's precedent for `known_issues`: `PRAGMA foreign_keys=OFF`,
  create, copy every column by name, drop, rename, recreate the three
  indexes, `foreign_keys=ON`. `foreign_keys=OFF` is required, not defensive:
  **17 tables reference `vehicles`** (`sqlite_master` where `sql` contains
  `REFERENCES vehicles`), `get_connection` sets `foreign_keys=ON`
  (`core/database.py:250`), and DROP is refused while a child row points at
  it. The rebuild keeps every value, the column order, every other default
  and the `transmission` CHECK. `vehicles` has no view or trigger.
  - **A thing the deploy diff cannot see:** the diff skips `sqlite_%`
    tables (`deploy.py:108`), so `sqlite_sequence` is invisible to it. A
    plain rebuild resets `vehicles`' sequence to `max(id)`, which reuses a
    deleted bike's id. Live it is 10 = max(id), so live is unaffected, but
    the migration copies the old sequence across, and a test with a
    deleted top row holds it.
  - The rollback restores `DEFAULT 'ice'`, the pre-074 schema. The older
    rollbacks (003, 177) restore their own era's schema and are not edited.
  - Rejected: editing the default through `PRAGMA writable_schema`. SQLite
    documents it for exactly this change, but it depends on defensive mode
    being off, and the rebuild has a precedent here.
- `VehicleBase.powertrain` becomes `Optional[PowertrainType] = None`, and
  both registry inserts bind `None` as NULL.
- `garage list` prints `unknown` for NULL.
- **Every reader gets a test with a bike stored as NULL**, whatever the
  pick, because a NULL can arrive through a raw insert or the photo path.

**`workflow start` on a bike stored as unknown.** Today it passes, saves
the run with the stated value and leaves the bike NULL. Two ways, under any
option:
- (i) **Leave it as it is, and print a line:** "Bike #N has no powertrain
  on record; to store it: motodiag garage update --bike … --powertrain P."

data honest but no bike better known. (ii) records the one moment a
mechanic states the value.

## S0-7: the edit guard's design (part 2)

**What it enforces:** the working-rules line "Targeted edits only on
source and tests: no `re.sub`, `sed -i` or index surgery". The rule was
broken twice by the tool that should have prevented it:
- **356:** "the two edits to `integration_gaps_counts.py` were made with an
  exact-string replace in a short script that asserted one occurrence each,
  not the Edit tool" (`356_phase_log.md:92–95`). That is a heredoc-fed
  interpreter script.
- **357:** "the six commands were appended to `cli/workflow.py` with one
  heredoc" (`357_phase_log.md:124–128`). That is a `cat >> file <<'EOF'`.

**Shape.** `.claude/skills/closeout/edit_guard.sh`, a thin wrapper like
`pre_push_guard.sh`, runs `_edit_guard.py`. It is a second entry in the
`Bash` matcher's `hooks` list in `.claude/settings.json`, beside the push
guard. The input is the hook payload on stdin (`tool_input.command`,
`cwd`), as the push guard's tests already drive it
(`tests/test_phase255D_closeout_contract.py:215–221`).

**Early exit, as the push guard's docstring requires.** A command with
none of `>`, `tee`, `sed`, `perl`, `<<` or ` -c ` cannot be any blocked
form, so it exits 0 before parsing. That bounds the lockout surface of a
guard that fails closed. Recovery, if it ever blocks every Bash call:
edit `.claude/settings.json` with the Write tool, which is not Bash (255D).

**Blocked**, each with a planted positive control:
1. `sed -i` in any form, anywhere (the operator named it without a path):
   GNU `-i`, `-i.bak`, `--in-place`, `--in-place=.bak`; BSD `-i ''`,
   `-i.bak`; clusters `-Ei`, `-ni`, `-ie`; `gsed`; and after `xargs`,
   `find -exec` and `env`. The option word is scanned letter by letter up
   to one that takes an argument (`e`, `f`, `l`).
2. A redirect whose target resolves into this checkout's `src/` or
   `tests/`: `>`, `>>`, `>|`, `&>`, `&>>`, `N>`. This covers
   `cat`/`printf`/`echo` into a file, and `cat > f <<'EOF'` (the heredoc's
   opening line keeps its redirect).
3. `tee` or `tee -a` with a target there.
4. **A heredoc-fed or `-c` script whose body writes there** (356's form):
   - `python`/`python3` fed by `<<`, or given `-` or `-c`;
   - `bash`/`sh`/`zsh` fed the same way, whose body is judged again as a
     whole command line.

   A Python body is blocked when a write call targets a protected path.
   The write calls are `open(…, 'w'|'a'|'x'|'r+'…)`, `.write_text(`,
   `.write_bytes(`, `shutil.copy*/move(…, dst)` and `os.replace/rename(…,
   dst)`. The target counts as protected when it is a literal path there,
   or a name assigned such a literal in the same body; when the target
   cannot be resolved and the body names `src/` or `tests/` anywhere, the
   script is blocked too (fail closed).
5. `perl -i` / `-pi`, the same in-place class as `sed -i`. **Proposed, not
   in the operator's list**; struck if the operator says so.

**Path resolution.** A target is resolved against the payload's `cwd`,
followed through literal `cd DIR` segments in the same command line, with
`~`, `$HOME`, `$CLAUDE_PROJECT_DIR`, `$TMPDIR` and literal `NAME=value`
assignments made earlier in the line expanded. `/dev/*` is never
protected. A path is protected when it resolves (with symlinks resolved)
under `<repo>/src` or `<repo>/tests`.

**Fail closed**, each shown blocked by a test:
- a command it cannot parse: an unbalanced quote, an unterminated heredoc
  or `$(`;
- a write target it cannot resolve: an unknown `$VAR`, a backtick, `$(…)`
  or a glob. The reason tells the writer to use a literal path;
- any exception inside the guard;
- **its own time limit, 5 s under an alarm, inside a 30 s hook timeout**.
  358 measured that a hook killed by its timeout lets the command through,
  so the guard must never be the one killed. The test plants a slow
  analysis in a subprocess and shows exit 2.

**Allowed**, each shown by a negative control:
- the commit-message heredoc, `git commit -F - <<'MSGEOF'` with `sed -i`,
  `> src/x` and `;` inside the message (heredoc bodies are stripped before
  the line is split, as the push guard does);
- every other `git` command, including those that write the tree
  (`checkout`, `apply`, `stash pop`, `mv`): git is not a text edit;
- read-only heredoc scripts: a Python body that reads `src/…` and writes a
  literal scratchpad path; `sqlite3 <<EOF`; `cat <<EOF` to stdout;
- redirects into the session scratchpad and into `docs/`; `2>&1`,
  `>/dev/null`, `&>/dev/null`;
- `sed -n`, `sed 's/a/b/' file` (stdout), `grep '->'`, `awk '$1 > 5'`
  (quoted), `(( a > b ))`;
- the Edit and Write tools, which the `Bash` matcher never sees.

**Known limits**, to be written in the closeout skill's CHANGELOG and the
phase log:
- **A script file run by name** (`python x.py`, `bash x.sh`) is not
  opened. The mutation scripts (`356_mutate.py`, `357_mutate.py`) write
  into `src/` by design, and run this way.
- `cp`, `mv`, `install`, `rsync`, `dd`, `truncate`, `patch` and `git apply`
  into `src/` or `tests/` are file operations, not text edits, and are not
  blocked.
- A script body's `subprocess` calls, `eval`, and a variable whose value
  appears only at run time are not followed.
- Python bodies only: a `node`, `ruby` or `perl -e` body is blocked only
  when it names a protected path and a write call the guard can see.
- Only this checkout is protected. A second writer's worktree has its own
  guard, because the hook resolves `${CLAUDE_PROJECT_DIR}`.
- **Live proof.** Hooks are read when a session starts. The live proof is
  a headless `claude -p` started in a scratch worktree carrying the new
  settings, as 358 probed the timeout: a planted append into `tests/` is
  refused, and the file is shown absent.
