## S0-2 — the outside facts that decide question 1

From Tailscale's own page on Tailscale SSH (`tailscale.com/kb/1193`),
fetched 2026-10-20:
- "Tailscale SSH's server component is only available on" Linux and the
  macOS open-source build. **Windows is not one**, so Tailscale SSH on this
  PC means Tailscale running inside Ubuntu as a second device.
- "Tailscale implements the SSH File Transfer Protocol (SFTP) which lets
  SCP and SFTP work". File transfer is served by Tailscale itself, not by
  the user's shell, so a restricted shell does not limit it.
- The page lists "machines where you use `authorized_keys` to limit what
  commands remote users can run" as a case Tailscale SSH may not fit.
- An SSH rule's source can be a user, group, tag or autogroup, never a
  single device; its destination a user, tag or autogroup.

So **Tailscale SSH can give a full shell, but not a fixed list.** A fixed
list needs OpenSSH's forced command (`restrict,command=` in
`authorized_keys`), which also turns off file transfer and forwarding.

## S0-4 — the questions for the operator

Put to the operator in plain words; the record of the answer goes in the
phase log.

### Question 1 — the way in

- **1A (recommended): an SSH server inside Ubuntu, listening only on its own
  tailnet address.** Tailscale is installed inside Ubuntu as a second device
  (`motodiag-ops`, tagged, never expiring, not taking over Ubuntu's DNS). The
  SSH server listens on that device's tailnet address only, which does not
  exist on the home network, so the home network cannot reach it at all.
  - *How the Mac proves who it is:* two locks. The tailnet's rules let only
    the Mac's tailnet address reach port 22 on `motodiag-ops`; and a key
    the operator makes on the Mac, kept in the Mac's keychain, accepted only
    from the Mac's tailnet address and only for the fixed list. No password
    logins.
  - *What ships:* `ops/desktop/install_remote.sh` (the SSH server, its one
    listening address, the key's restriction); the tailnet rules as text.
- **1B: Tailscale's own SSH, on the same second device.** No keys at all: the
  Mac's tailnet sign-in is its proof. But it can only give a full shell
  (S0-2), and any of the operator's devices signed in could use it unless
  the tailnet rules shut them out.
- **1C: an SSH server inside Ubuntu, forwarded from Windows' tailnet
  address** (no second device). Windows forwards port 2222 into Ubuntu and a
  Windows firewall rule keeps it to the tailnet. The server would see every
  visitor as coming from Windows, so it cannot check that it is the Mac,
  and it depends on a Windows firewall rule staying right. Not recommended.

*What the operator does once at the PC (1A):* in the Ubuntu window, run one
committed script (it asks for the Ubuntu password), sign the new device in
to the tailnet in a browser, paste the Mac's public key when asked.

### Question 2 — what it lets the Mac do

- **2A (recommended): a fixed list of named operations,** run by one
  script on the PC that refuses anything else. The list:
  `status` (read only), `pull <branch>`, `dryrun <phase>`, `api-stop`,
  `apply-live <phase>`, `verify-live <phase>`, `api-start`,
  `backup [label]`, `server-pull`, `fetch <phase> <kind>` (send a written
  diff file back), `media-proof` (the six videos on a read-only copy), and
  `verify-phase` (below). A branch must be `master` or `phase-<id>`; a
  phase id must look like one. A control: an unlisted command, a shell
  trick in an argument, a file transfer and a forwarded port each refused.
- **2B: a full shell** as the PC's user. Simplest; the builder could do
  anything that user can, including read the PC's GitHub sign-in.
- **And `verify_phase.sh`'s live check on the Mac:**
  - **(i) (recommended):** on a machine whose live.json names a host and the
    way in, the check runs verify-live there through the fixed list, and
    passes or fails on its answer. With no way in it still fails.
  - **(ii):** the check stays PC-only; the Mac runs the whole of
    `verify_phase.sh` on the PC through the list.

### Question 3 — how the PC's diff files reach the branch

- **3A (recommended): the PC never commits.** The operation writes the file
  in the PC's checkout; the Mac fetches it through the way in, with both
  sides printing its sha256, writes it in its own tree and commits it under
  its guards. The PC's copy is removed only when its sha256 equals the one
  the Mac committed, so the PC's next pull is clean.
- **3B: the PC commits and pushes, as in 383,** run by the Mac remotely,
  outside the guards.
- **3C: the PC pushes to a side branch** and the Mac takes the commit in
  under its guards. Two writers to one remote.

### Question 4 — everything that needs the operator's password or a sign-in, one sitting (for 1A, 2A, 3A)

1. **Browser, Tailscale admin console (sign-in):** copy the current access
   rules into a file on the Mac so the new ones are written from them; then
   paste the new rules (they keep every device reaching the PC as now, add
   the `motodiag-ops` tag, and let only the Mac reach its port 22).
2. **PC, Ubuntu window:** run the install script (Ubuntu password), which
   installs Tailscale and the SSH server.
3. **PC, Ubuntu window, then the browser:** sign `motodiag-ops` in to the
   tailnet.
4. **Mac, Terminal:** make the key, with a passphrase stored in the
   keychain (typed by the operator); print the public half, which is not a
   secret.
5. **PC, Ubuntu window:** paste the public half when the script asks.

Nothing else needs the operator after that, except one use of the app for
the proof. The failing control from a device not on the tailnet is the Mac
with Tailscale disconnected, which the builder can switch itself; the
operator is asked only if it does not reconnect.
