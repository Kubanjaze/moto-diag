## Goal

Row 372, split from 273 on 2026-10-06 (the operator's 3A: "CLI only now"): "Routes to start an invoice payment, a Terminal payment and a shop's Stripe onboarding, with the app screens that would call them and checkout and portal screens for the tiers. Each moves the OpenAPI snapshot, so it needs a mobile session. Row 273 reaches every verb from the CLI."

Today every payment verb exists once, as a function under `src/motodiag/payments/` with a `motodiag` command in front of it (`src/motodiag/cli/payments.py`): `shop payments connect` and `status` (`connect_shop`, `onboarding_link`, `refresh_status` in `connect.py`), `shop invoice pay-link` (`start_checkout` in `invoice_payments.py`), `shop terminal pay` (`start_terminal`) and `shop invoice payments` (`payments_for_invoice`). No route reaches any of them: `src/motodiag/api/routes/billing.py` serves only the tiers' checkout session, the portal session, the subscription read and the webhook, the Step 0 census finds `/payments` nowhere under `src/motodiag/api/`, and nothing under `src/motodiag/api/` imports `stripe_api` or `ConnectError` today. A shop owner with a phone and no terminal window cannot connect the shop, send an invoice to the card reader or hand a customer a pay-link. Live payments have been on since 21:10 EST on 2026-11-11 (`docs/handoffs/2026-11-10_402_closed.md`, "Live payments went on"), so the server side is real and waiting.

After this phase:

1. Five routes under `/v1/shop/{shop_id}/…` call the Phase 273 functions as they are: read the shop's Stripe account, connect it and get its onboarding link, start a Checkout payment of an invoice, send an invoice to the shop's reader, and list an invoice's Stripe payments. Each checks the caller's tier, the shop's membership and the permission the verb needs. Not one line of `src/motodiag/payments/` changes, and the invoice is still paid only by Stripe's verified news (the payments feed of Phase 371).
2. The OpenAPI document carries them under a `payments` tag, and the phone app's snapshot is refreshed from this branch, as Phases 303 and 348 did.
3. (Moved to 372B by the operator's choice, K81.) The app gains three screens in a session rooted in the mobile repository, from a prompt this phase writes: card-payments setup for a shop, an invoice's payment (reader or pay-link, with the outcome), and the plan screen for the tiers (checkout and portal through the existing billing routes).
4. The operator's steps after the merge are one handoff in plain English: the server on the new code, the app's snapshot pushed and its types regenerated, the app's pull request merged.

Classification: extension (`372_step0.md`). It becomes a reshape only if an existing route or the live-key refusal changes, and this plan changes neither.
