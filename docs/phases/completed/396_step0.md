## S0-1. (a) The fenced code check gives no result

**Measured.** 385's code check run is kept on the desktop,
`~/.local/state/motodiag/fleet/runs/20261031_115942_check/run/check.txt`
(477 bytes, now `fixtures/slips396/a_385_fenced_code_check.txt`):

```
/bin/bash: -c: line 1: syntax error near unexpected token `then'
/bin/bash: -c: line 1: `/bin/sh -c if git cat-file -e ddcdfd6…:scripts/code_quality.py 2>/dev/null; then …'
```

**Cause.** `quartermaster.code_command` returns an argv,
`["/bin/sh", "-c", "<script>"]`. `dispatcher.check_run` turns every
`command` into one string with `" ".join(command)` and runs it as
`/bin/bash -c <string>`. The `sh -c` script's quoting is lost, so bash
reads `/bin/sh -c if …; then …` and stops on `then`. Not the fence's
paths, the venv, `git cat-file` or a time limit: the command never
started. The other three `command=` callers (the F9 lint, `verify_phase.sh`,
the weekly measure) pass argv with no spaces or shell words, which survive
the join; only this one breaks.

**Why no test saw it.** `tests/test_phase393_code_checks.py`'s stage tests
stub `Fleet.check` for any command containing `code_quality.py pr`, so the
real `check_run` never ran this command (389's rule, not followed in 393).

**The bare "no result".** `code_findings` passes `code.why[-300:]`; `why`
is the run's whole output, and its last 300 characters were bash's echo of
the mangled command, so the finding said "gave no result: ity.py
2>/dev/null; then git show …" (348, PR #40: `a_348_verdict_lines.txt`;
385, PR #43) and never named the syntax error.

**Fix.** `check_run` joins a command with `shlex.join`. `code_checks`'s
reason for no result is built by `quartermaster.no_result_why`: the exit,
and the first line of the output that names an error (else its last line),
never a tail of the command. The proof in the real fence is on 348's and
385's merged heads (S0-6).

## S0-2. (b) "No refute pass ran" before the Red Team runs

**Measured** (`fixtures/slips396/b_false_lines.json`, each line from `git
show` at the commit a rank judged): 303's log line 158 at `db87313` (V12,
PR #34); 348's v1.1 line 156, log line 194 and handoff line 7 at
`8f4e056` (the Red Team's round 2, PR #40); 385's v1.1 line 271 at
`46db82e` (Q7, PR #43).

**Cause.** A8 (`closeout_check.refute_record`) requires a log that
mentions "refut" to carry the `## Refuter pass` checklist or a line
"No refute pass ran". In a fleet phase the checklist arrives after the
close-out: the dispatcher commits the Red Team's table
(`red_team.record_in_log`). An Engineer whose log mentions the Red Team's
refute at close-out can pass A8 only by writing the line, which is false
the moment the Red Team runs. `record_in_log` then removes only the exact
line `No refute pass ran.` from the log, and nothing touches v1.1 or the
handoff. The brief (`engineer.BRIEF`, rule 7) says nothing about it.

**Fix, loosening nothing.** The brief's rule 7 tells the Engineer that the
phase goes to the Red Team after its close-out, so it writes no sentence
that a refute pass did or did not run, and leaves refute out of the phase
log; the dispatcher's committed table is the record (A8). A8 itself is
unchanged in what it accepts. A new refusal inside A8: a phase whose log
carries the `## Refuter pass` checklist, and whose v1.1, log (outside the
table) or handoff says "no refute pass", fails, naming file and line.

**Census.** Over master's 350 closed logs, 13 carry a checklist; one phase
contradicts it: 385's v1.1, lines 96 and 271. Line 271 is the false
claim; line 96 is the v1.0 plan's "no refute pass unless one runs". Both
are deleted (K9: delete rather than rewrite), with the phase log saying
so; no exemption is added.

## S0-3. (c) The next mission read from a stale plan

**Measured** (`fixtures/slips396/c_dispatcher_2026-10-31.log`):
11:07:17 the Quartermaster on 385; 385 merged at 11:37 (PR #43), which
closed #41; 12:00:00 the verdict; 12:00:02 "next: opened issue 44: Phase
385 …", then "next: the row is on master"; 12:05 the next cycle sees 385
✅ and opens #45 for 345.

**Cause.** `cycle()` calls `update_mirror()` once, at its start. The
issues are read live from GitHub each time, the ROADMAP and the plan from
the mirror. After a 53-minute stage `next_due` read 385 as 🚧 from the
11:07 mirror while `mission_issue` no longer found #41 (closed), so it
opened #44; `stage_next` then found the stale 🚧 row and stopped.

**Fix.** `cycle()` refreshes the mirror and re-reads master's rows right
before `next_due`, whatever ran before it in the cycle. A cycle with no
stage pays one `git remote update` more, which is cheap against the race
it closes (also a merge during the sweep). Of the prompt's two ways this
is the first ("re-read master's rows after any stage in the same cycle"),
done unconditionally because "a stage ran" would be one more thing to get
right.

## S0-4. (d) The Red Team handed the Captain's first draft

**Measured** (`fixtures/slips396/d_348_plan_history.json`): 348's plan
was changed by seven commits; `plan:approved` was last applied on #36 at
2026-10-30T12:51:15Z; the newest plan commit before it is `85b2db5`, the
operator's. The Red Team's round 1 read f1a4146 and said so: "The
approved v1.0 given to this review (f1a4146e6642) is a different plan."

**Cause.** `red_team.plan_commit` is `git log --diff-filter=A`'s oldest
commit: the one that first added the file, always the Captain's draft.
`quartermaster.gather` uses it too, for its v1.0-to-v1.1 diff.

**Fix.** `plan_commit(clone, phase, approved_at)` is the newest commit
that changed the plan at or before the time `plan:approved` was last
applied, by committer date. The dispatcher reads that time from the
issue's label events (`last_applied`, as the Quartermaster's due check
does) and passes it to both gathers. With no `plan:approved` on the issue,
the gathers say so in the header ("plan:approved was never applied on the
issue") and use the first commit, named as such: never silently called
"as approved".
