## S0-2: what the code adds to the picture

1. **The packet uses the intake's mileage but never prints it.** It
   prints "Mileage on record" (the bike's) and uses the intake's mileage
   only inside the coverage verdict. Reported problems are not in the
   packet at all. So "the mileage and problems reach the claim packet"
   needs two packet lines as well as the link.
2. **An intake's mileage and problems can be filled in later**:
   `shop intake update ID --mileage --notes` (`cli/shop.py:1222`), and the
   packet reads the intake row when it is rendered. So an intake created
   at check-in with no mileage can carry it before the claim goes out.
3. **Nothing closes an intake automatically.** Only `shop intake close`
   does. An intake made at check-in stays open, and `open-for-bike`
   lists it, which is what the duplicate warning in `intake create`
   reads.
4. **No schema change is needed** for any option below: the appointment
   already holds `work_order_id`, and the work order `intake_visit_id`.
   So no migration 082 and no deploy, whichever option is chosen.
5. **The app** has the intake types in `src/api-types.ts` and no
   appointment screen.

## S0-3: the stops (the operator's questions)

1. **How check-in brings the intake:**
   - (a) it creates the intake;
   - (b) it links an open intake, by id or found automatically;
   - (c) both;
   - (d) a narrow `work-order attach-intake`.

   (d) would add a second writer of `intake_visit_id`, which today is
   set only at creation. The rule exists so that the denormalised shop,
   customer and bike cannot drift from the intake: a mistake is fixed by
   cancelling and recreating the work order. A checked-in appointment
   cannot be checked in again, though, so a recreated work order cannot be
   linked back to it. That is F189's trap. **Recommended: (c),** which
   needs no relaxation.
2. **A check-in given no intake details:**
   - (a) no intake, as today;
   - (b) create one with the mileage unknown, which `shop intake update`
     fills in later;
   - (c) refuse.

   **Recommended: (b).**
3. **The command line only, or an API route too.** The API has no
   appointment route at all, and the app no appointment screen.
   **Recommended: the command line only.**

**The operator's answer** (verbatim in the phase log): 1c, 2b, the
command line only. Automatic linking only when exactly one open intake
matches the shop, customer and bike and was taken within a day of the
appointment; otherwise ask for `--intake`; always print the linked
intake's date and mileage. While an intake's mileage is unknown, the
packet says "not recorded".
