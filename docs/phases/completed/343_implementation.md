# Phase 343 — Telemetry + crash reporting (Sentry)

**Version:** 1.1 | **Tier:** Standard | **Date:** 2026-11-01 (v1.0 `c18d072`, revised `1e9f1fc`, `a17f8ac`)

---

## Goal

When the live API on the home desktop fails, nobody is told. `src/motodiag/api/errors.py`'s last-resort handler (`_unhandled_handler`) writes the stack trace to the journal and answers a bare 500, and that journal is read only when someone logs in to look. A mechanic who hits a crash at the bench sees "Internal server error" and the operator learns of it, if at all, when the shop phones. Step 0's census (run on this branch from `15e55c3`) found nothing to extend: 0 hits for `sentry_sdk`, `SENTRY_DSN`, `capture_exception`, `traces_sample_rate` and `init_sentry` in `src/`, `tests/`, `.claude/`, `docs/` and the mobile app's `src/`; the one `sentry` hit in `tests/` is the letters inside `TestEveryCanonicalNameResolvesToItsEntry` (`tests/test_phase379_lookup_and_relevance.py:27`). The hits Step 0 left unread were read for this plan: `rg -n -i telemetry src` finds the OBD adapter failure reports (`obd_reports/`, `api/routes/diagnostics.py`, `push/events.py`'s maintainer alert), the audio sweep's per-call counters and the predictor's "telemetry, not scoring" comment, none of which captures an exception or measures a request; `rg -n -i crash src` is 153 hits in 55 files, 128 of them in the knowledge corpus (a crashed bike) and the rest the ECU crash-recovery scenario, the recorder and the safety rules. So this is greenfield, as Step 0 classified it, and no existing path is duplicated or altered beyond the two seams named in Logic item 5 and the one mask in Logic item 2.

What exists to hang it on: every request already carries an id (`RequestIdMiddleware`, `request.state.request_id`, echoed as `X-Request-ID`), every request's duration is already measured (`AccessLogMiddleware`), `Settings` (`src/motodiag/core/config.py`) reads `MOTODIAG_`-prefixed names, and the live unit (`ops/desktop/motodiag-api.service`) already loads `~/.config/motodiag/server.env` (mode 600) through `EnvironmentFile`, the file the unit's own comment names as where "keys the operator adds go". `motodiag serve` runs uvicorn with `factory=True`, so `create_app()` runs in each worker and a per-app sender is a per-worker sender.

This phase ships the row's four promises as far as a backend can, and takes the rest to the operator at one stop:

- **Sentry integration.** A small client of Sentry's envelope protocol, in the standard library, turned on by one line in `server.env` (`MOTODIAG_SENTRY_DSN=`) and inert without it. The DSN lives only on the desktop, in that file, under the K62 pattern Phase 345 set for an outside account's key: never in the repository, a log, an issue, a chat or the fleet's fence. The one place in the repository that prints every setting, `motodiag config show`, masks it.
- **Crash reports.** Every unhandled exception the API answers with a 500 becomes one event: the exception's type, its message with session tokens redacted, the stack frames, the request id, the method, the route template and the release. Nothing else: no headers, bodies, query strings, local variables, user or customer. The exact rule is the operator's to confirm at the stop (part (d)); the plan carries the Captain's recommendation.
- **Performance monitoring.** One transaction per sampled request: the route template, the method, the status and the duration. The sample rate is a threshold and so the operator's (part (e)).
- **User session replay.** A replay records what is on a mechanic's screen, and that screen holds customer names and vehicle owners. There is no screen on the backend, no crash SDK in the phone's binary, and the launch checklist's privacy answers rest on there being none. Whether replay ships at all, and masked how, is a real fork and the operator's (part (c)). The Captain's recommendation is that it does not ship in this phase.

What the operator gets: a Sentry dashboard that shows each crash within seconds, with the request id that the mechanic's error screen can be matched to, and one command (`motodiag telemetry check`) that proves the wire is up.

## Logic

The build runs in this order. Item 1 is the Chief Engineer's first act, before any code, for the reason 303, 348 and 345 recorded (`docs/phases/completed/345_implementation.md`, Logic item 1): a stopped Engineer's commits are never pushed, so anything built before a stop is lost to the build.

1. **The one stop, first.** The Engineer stops once, with kind `login-or-credential` (the spelling in `.claude/skills/fleet/engineer.py`'s `STOP_KINDS`; `read_result` refuses any other kind), with one plain-English question for the operator carrying the five decisions below, each with the Captain's recommendation, so the operator can answer "go with your picks" or change any one. Parts (b) and (c) are forks and part (e) a threshold under CLAUDE.md rule 1; they travel in the same question because the fleet makes one stop, not three, and each is answered in the operator's own words.
   (a) **The account and where its key lives.** The operator opens a Sentry account and one project (platform: Python), and copies the project's DSN as one line, `MOTODIAG_SENTRY_DSN=…`, into `~/.config/motodiag/server.env` on the home desktop, the file `motodiag-api.service` already loads; the file stays mode 600. The DSN is never typed into the issue, the chat or a command line: the question says so, and the server reads it only from the environment the unit gives it. The question asks the operator to confirm, in their own words, that the project exists and the line is in the file, without quoting any value. The dispatcher's `needs-hands` hold on the mission issue already asked for the account; this is the confirmation the live proof (item 8) rests on.
   (b) **The official SDK or the repository's own client, a fork.** Recommended: the repository's own client (items 2 to 4), about two hundred lines over the protocol Sentry publishes, because the fleet's fence has a read-only venv with no `sentry_sdk` (checked for this plan: `.venv/lib/python3.14/site-packages/` holds no `sentry_sdk`), so a test of an SDK path could not run there, and a skip for a missing package is a new skip: every skip in a regression of record is pinned by its file and reason in `EXPECTED_SKIPS` in `.claude/skills/closeout/closeout_check.py` (or, for a run inside the fence, `FENCE_EXPECTED_SKIPS` in the same file), held by equality in `tests/test_phase383_regression_outcome.py` and `tests/test_phase389_fence_regression.py`, and K64 (2026-11-01) records that adding to the list is the operator's call, so a skipping SDK test would itself be a stop; and because the client sends exactly what part (d) allows and nothing an SDK's integrations add on their own (local variables, breadcrumbs, request headers). The alternative is `sentry-sdk[fastapi]` as a `telemetry` extra, which needs the operator to install it into the fence's venv by hand before the build and the SDK's `before_send` and `send_default_pii=False` for the scrubbing. The two ship different things; the operator picks.
   (c) **Session replay and the phone, a fork.** Recommended: no replay in this phase, and no crash SDK in the phone's binary in this phase; the backend only. Replay exists only in the browser and mobile SDKs, the phone (`../moto-diag-mobile`, React Native 0.85.2, no Sentry package) is built outside the fleet's fence, and `docs/launch-checklist.md` step 3 says the privacy questionnaire's answers are wrong "the day anyone adds Sentry or an analytics SDK" to the binary. The phone's crash reports and replay, with the masking rule the operator defines, go to a later row in the mobile repository, numbered by the ROADMAP's rules when it is opened. The alternatives are replay with masking or replay without; the operator picks.
   (d) **What an event carries, the scrubbing rule.** Recommended, and written into item 3 as the rule: the exception's type; its message, with every `mds_` session token replaced (the `SESSION_TOKEN_RE` pattern of `src/motodiag/cli/serve.py`, which Phase 303 wrote for the same reason) and cut to 500 characters; the stack frames as file, function, line number and an in-app flag, with no local variables and no source lines; the request id; the method; the route template (`/v1/shop/{shop_id}/work-orders/{wo_id}`, never the path with the ids in it); the response status; the release (`motodiag.__version__`); the environment; the host name. Never: a header, a body, a query string, a cookie, an API key, a user, a customer name, a vehicle owner, a breadcrumb. A transaction carries the same route template, method, status and the two timestamps. The operator may narrow or widen this; the Engineer applies the words.
   (e) **The numbers.** Recommended: transactions sampled at 0.1 (one request in ten; errors are never sampled, every one is sent); a send queue of 100 events per worker, beyond which an event is dropped and counted rather than making a request wait; a 5-second transport timeout; a flush of 2 seconds at process exit. The operator sets them in the same answer.
   The question ends with how the answer comes back, the same way as 345's (F231 is open): the operator writes the answers as a comment on the mission issue in their own words; one paste block for the Mac's Terminal window then fetches the branch into the operator's own checkout, writes the newest comment by the repository's owner verbatim into a new `docs/phases/in_progress/343_phase_log.md` under a dated heading "The operator's answers to the Chief Engineer's stop", commits it, runs `.claude/skills/closeout/wholetree.sh` and then `.claude/skills/closeout/roadmap_check.py` each on its own and stops on any nonzero exit, pushes, and re-applies `plan:approved` while removing `needs-admiral`, naming the repository on every `gh` call (R8). It prints ALL GOOD or SOMETHING IS OFF and carries no internal labels.
   **When the stop is already answered.** When `docs/phases/in_progress/343_phase_log.md` on the branch carries that heading, the Engineer does not stop again but goes to item 2, applying the operator's words literally. The check is the Engineer's first act in every session. If the operator picks the SDK in (b), items 2 to 4 are built as the SDK's `init` and transport instead, the fence venv gains the package by the operator's hand first, and v1.1's Deviations records the swap; the finish lines of items 5 and 6, and item 2's mask in `config show`, hold either way.
   Finish line: the stop is recorded in `/fleet/run/engineer.json` with kind `login-or-credential` and the question; the phase log on the branch carries the operator's words; the Engineer's next session logs that it read them and what each part decides.

2. **`src/motodiag/telemetry/__init__.py` and `src/motodiag/telemetry/dsn.py`** (new), three fields on `Settings` in `src/motodiag/core/config.py`, and one mask in `src/motodiag/cli/main.py`. `parse_dsn(text) -> Dsn` reads `https://<public key>@<host>[:port]/[<path>/]<project id>` into scheme, host, port, public key, project id and path prefix; `Dsn.envelope_url` is `<scheme>://<host>[:port]/<path>api/<project id>/envelope/` and `Dsn.auth_header` is `Sentry sentry_version=7, sentry_client=motodiag/<version>, sentry_key=<public key>`, the two things Sentry's developer documentation asks a client to send. It refuses a DSN with no key, no host or no project id, naming only what is missing and never echoing the text. `Dsn.__repr__` and `__str__` show the host and project id only, so no traceback or log line that formats a parsed `Dsn` can carry the key. The three settings, read from the environment with the `MOTODIAG_` prefix like every other: `sentry_dsn: str = ""` (empty means off); `telemetry_traces_sample_rate: float`, defaulting to part (e)'s value, with a validator that refuses anything outside 0.0 to 1.0 the way `ai_temperature` is bounded; `telemetry_environment: str = ""`, which falls back to `env.value` when empty. No new dependency and no new extra: `pyproject.toml` is unchanged.
   **The mask in `config show`.** `sentry_dsn` is a plain string on `Settings`, and `motodiag config show` (`src/motodiag/cli/main.py:247-249`) prints every field of `settings.model_dump()`, masking only a name that contains `api_key`. The `Dsn` repr does not help there, because the command never parses the field; without a change the full DSN with its key would print to the operator's terminal, and from there into a paste, a log or a chat, which the K62 pattern this plan adopts forbids. So the mask rule in `config_show` widens from the one substring to a tuple of secret names, `("api_key", "sentry_dsn")`, matched the same way (`any(name in key for name in …)`), and the display stays `"****"` plus the value's last four characters, which for a DSN are the end of the project id and never the key (the key sits before the `@`). `stripe_webhook_secret` has the same gap today and is not this phase's to fix: Step 0 does not support it, and the Engineer files it as a finding with the `finding` skill rather than widening the rule to `secret` (see Non-goals).
   Finish line: the example DSN from Sentry's documentation (`https://examplePublicKey@o0.ingest.sentry.io/0`) parses to its host, key and project id and its envelope URL ends `/api/0/envelope/`; a DSN missing its key, and one missing its project id, are each refused naming the missing part, and a planted key value appears nowhere in the refusal; the repr of a parsed DSN holds no key, with the control that the same assertion goes red when the key is printed on purpose; a sample rate of 1.5 is refused and 0.0 and 1.0 are read; an empty `MOTODIAG_SENTRY_DSN` gives settings that say off; `config show` under `CliRunner` with `MOTODIAG_SENTRY_DSN` set to a made-up DSN holding a planted key prints the `sentry_dsn` row with `****` and never the planted key, with the control that the same assertion goes red when the mask is bypassed for that field, and `tests/test_phase02_config.py::test_config_show` passes unchanged.

3. **`src/motodiag/telemetry/events.py`** (new): what an event is, as part (d) decides. `redact(text) -> str` applies `SESSION_TOKEN_RE` and the 500-character cut. `error_event(exc, *, request_id, method, route, status, release, environment, server_name, clock=None) -> dict` builds one Sentry event: `event_id` (32 lowercase hex from `uuid4`), `timestamp` (from `motodiag.core.timestamps.utc_now()` or the injected `clock`; no private `_now` helper, so `PRIVATE_HELPERS` stays at 19), `platform` "python", `level` "error", `logger` "motodiag.api", `release`, `environment`, `server_name`, `sdk` (`motodiag.telemetry` and the version), `tags` (request id, route, method, status), `request` (`method` and `url` set to the route template), and `exception.values[0]` with `type`, the redacted `value`, and `stacktrace.frames` from `traceback.extract_tb(exc.__traceback__)`: `filename` (relative to the package when the frame is under `motodiag`), `function`, `lineno`, `in_app` true for the package's own frames. The function takes no request, header, body or query string, so none can reach an event; that signature is the rule. `transaction_event(*, route, method, status, started, ended, request_id, release, environment, server_name) -> dict` builds one transaction: `type` "transaction", `transaction` "<METHOD> <route>", `start_timestamp`, `timestamp`, `contexts.trace` with a 32-hex `trace_id`, a 16-hex `span_id`, `op` "http.server" and a `status` of "ok" below 500 and "internal_error" from 500, `spans` empty, and the same `tags`. `message_event(text, **same)` builds the one event `motodiag telemetry check` sends. Every function is under McCabe 20, so `COMPLEX_FUNCTIONS` stays at 25.
   Finish line: an event built from an exception raised inside a planted function carries that function's name and line in a frame marked in-app, with no `vars` key and no `context_line` in any frame; a message holding a planted `mds_` token appears redacted, with the control that the assertion goes red when `redact` is skipped; a 2,000-character message is cut to 500; the `request.url` is the route template passed in and a path with a numeric id passed as the route is a test failure (the test passes a template and asserts no digit run of the id's length); `inspect.signature(error_event)` names no parameter called `request`, `headers`, `body` or `query`; a transaction's `status` is "ok" at 200 and "internal_error" at 500 and its two timestamps are the injected ones.

4. **`src/motodiag/telemetry/envelope.py` and `src/motodiag/telemetry/sender.py`** (new): the wire and the thread. `envelope(event, dsn, sent_at) -> bytes` writes Sentry's envelope: one JSON header line (`event_id`, `sent_at`, `dsn`), one JSON item-header line (`type` "event" or "transaction" by the event's own `type`, `length` in bytes) and the JSON payload, each line newline-terminated, UTF-8. `Sender(dsn, *, transport=urllib_transport, queue_size, timeout_s, traces_sample_rate, clock=None, rng=None)` has `enabled` True, `capture(event) -> bool` (`put_nowait` on a `queue.Queue(maxsize=queue_size)`; False and `dropped += 1` when full; never blocks, never raises), `sampled() -> bool` (`rng() < traces_sample_rate`, `rng` defaulting to `random.random`; the one place the sample decision is made, so the middleware in item 5 has no second seam), a daemon thread that takes one event at a time and posts its envelope to `dsn.envelope_url` with `Content-Type: application/x-sentry-envelope` and `X-Sentry-Auth: <dsn.auth_header>`, `flush(timeout_s) -> bool` (True when the queue drained in time), and `close()` (flush, then stop the thread), registered with `atexit` for part (e)'s 2 seconds. A non-2xx status is logged at WARNING at most once a minute, naming the status and the host and never the key; a 429 with `Retry-After` pauses sends for that many seconds (at most 60), dropping and counting meanwhile; a transport that raises (refused connection, timeout) is logged the same way and breaks nothing. The `transport` is one callable, `(url, headers, body) -> (status, reason_text)`; the default uses `urllib.request` with part (e)'s timeout, and tests pass an in-process fake, so no test opens a socket (`tests/support/network_guard.py` refuses anything but loopback, and the fence runs with no network). `NullSender` has `enabled` False, `capture` returning False, `sampled` returning False, `flush` returning True and no thread; `make_sender(settings)` returns it when `sentry_dsn` is empty, and never logs or raises on a bad DSN at import time: a bad DSN is logged once at ERROR, naming what is missing, and gives a `NullSender`, because a typo in `server.env` must not stop the API (the way `_unhandled_handler` and `notify_obd_failure` already put the product before the report). No `except Exception: pass` anywhere: every handler logs, so `SWALLOWED_EXCEPTIONS` stays at 22.
   Finish line: an envelope's three lines parse back and the item header's `length` equals the payload's byte length, with a control that a payload holding a non-ASCII character still matches; the fake transport receives the auth header carrying the key and the envelope content type; `sampled()` with an `rng` answering 0.05 is True at a rate of 0.1 and False with one answering 0.5, never at 0.0 and always at 1.0; a 429 with `Retry-After: 3` from the fake raises nothing, pauses sends and the next capture inside the pause is dropped and counted, with the control that a capture after the injected clock passes 3 seconds is sent; with a transport that blocks on a threading event, 150 captures through a queue of 100 return within 100 ms measured on the caller's thread and `dropped` is 50; `flush` returns True once the fake has received every envelope and False when the transport is held; a transport that raises `OSError` breaks no caller and is logged once; `NullSender` starts no thread (`threading.active_count()` unchanged); the default `urllib_transport` round-trips against an HTTP server on 127.0.0.1, as 345's did.

5. **`src/motodiag/api/telemetry.py`** (new) and two seams in existing code. `install_telemetry(app, settings)` builds the sender with `make_sender(settings)`, stores it at `app.state.telemetry`, and adds `TelemetryMiddleware`. `create_app` keeps its two keywords (`settings`, `db_path_override`); nothing new is threaded through it.
   **Where the middleware sits.** `create_app()` calls `install_telemetry(app, app_settings)` at the top of the request-scoped block in `src/motodiag/api/app.py`, before the `app.add_middleware(AuditMiddleware)` line (`app.py:99`), under the block's own comment "innermost first in FastAPI order": `add_middleware` inserts at the front and the stack wraps in reverse, so the first added is the innermost and the last added (`RequestIdMiddleware`) is the outermost. The telemetry middleware is therefore the innermost request-scoped middleware the repository adds, inside `RequestIdMiddleware`, `RateLimitMiddleware`, `AccessLogMiddleware` and `AuditMiddleware`. It is not the innermost layer of the application. Inside it sit two more: `CORSMiddleware`, which `app.py:89` adds before the request-scoped block and which therefore wraps tighter than anything added after it, and Starlette's `ExceptionMiddleware`, which `Starlette.build_middleware_stack` places as the very innermost layer around the router (`.venv/lib/python3.14/site-packages/starlette/applications.py:71`), with `ServerErrorMiddleware` at the very outermost (`applications.py:69`). The middleware's docstring states the stack as it is and the four consequences below.
   **Four consequences.** First, `request.state.request_id` exists before `call_next`, because the id middleware set it on the way in. Second, a request the rate limit refuses with a 429 never reaches it, so no transaction is sent for one. Third, a CORS preflight is answered below it and never reaches the router: Starlette's `CORSMiddleware.__call__` answers an `OPTIONS` request that carries `Origin` and `Access-Control-Request-Method` from `preflight_response` without calling the app (`.venv/lib/python3.14/site-packages/starlette/middleware/cors.py:91-94`), so to the telemetry middleware such a request returns with no route on the scope and would be sampled as an "unmatched" transaction, one per browser preflight, which is noise about CORS and not about a route. The decision, in the docstring: the middleware skips every `OPTIONS` request before `call_next`, the way it skips `/healthz`; the product registers no `OPTIONS` route, so nothing of the product's is lost. Fourth, a mapped error sends nothing because `ExceptionMiddleware` turns it into a response inside the telemetry layer: `register_exception_handlers` registers the handlers for `HTTPException`, the domain errors and request validation, Starlette runs those handlers in `ExceptionMiddleware`, and so a 404, a 422 or a `ReportBuildError` 500 reaches the telemetry middleware as a returned response, not as an exception; only an exception no handler maps passes up through `ExceptionMiddleware` and every middleware as an exception, to `_unhandled_handler` on `ServerErrorMiddleware`, the outermost layer, where Starlette places the handler registered for `Exception`.
   **How it works there.** It reads `request.app.state.telemetry` at request time, on every request, and never closes over a sender at install: a missing attribute, or a sender whose `enabled` is False, means it calls `call_next` and does nothing else, so an app built without `install_telemetry` and an app with no DSN both behave as today, and a test replaces `app.state.telemetry` after `create_app` to put the fake sender in. It skips `/healthz` and every `OPTIONS` request before `call_next`. It takes `time.perf_counter()` before `call_next`, as `AccessLogMiddleware` does. It wraps `call_next` in the same catch-and-re-raise `AuditMiddleware` uses (`src/motodiag/api/middleware.py`, `dispatch`): an unhandled exception passes through as an exception, so to this middleware a raised route is a status 500, tagged "internal_error", and the exception goes on unchanged to `_unhandled_handler`. After `call_next` returns or raises, it reads the route template from `request.scope.get("route")`, which `APIRoute.matches` places on the scope when a route matched (`.venv/lib/python3.14/site-packages/fastapi/routing.py:998-1001`; the same shape at lines 804 to 808 is `APIWebSocketRoute.matches`, not the one this plan relies on), taking its `path_format`; when no route matched (a 404 with no route) the template is "unmatched". Then, when `sender.sampled()` says so, it builds `transaction_event` with that template, the method, the status and the two times, and `capture`s it. It never changes a response and never raises.
   **The first seam:** that one call in `app.py`, and the ready log line (`"motodiag API ready — …"`) gains `telemetry=on <host>/<project id>` or `telemetry=off`. **The second seam:** `_unhandled_handler` in `src/motodiag/api/errors.py` gains three lines after its existing `logger.exception`: `getattr(request.app.state, "telemetry", None)` (None means no sender and no capture), build `error_event` with the request id, the method, the route template read from the scope by the same rule, and 500, and `capture` it. The log line and the bare RFC 7807 body are unchanged. Only the unhandled path captures: a mapped domain error (`ReportBuildError` 500, `BillingProviderError` 502, every 4xx) is the product answering, not crashing, and sends nothing, for the fourth consequence's reason; a request-validation 422 sends nothing.
   Finish line: with `app.state.telemetry` replaced by the fake sender after `create_app`, and the client built with `raise_server_exceptions=False` as `tests/test_phase175_api_foundation.py` and `tests/test_phase207_security.py` build theirs for the 500 path, a test route that raises `RuntimeError` reaches the sender with exactly one error event whose `tags.request_id` equals the response's `X-Request-ID` header and whose `request.url` is the route's template, and the response is the same bare 500 body those tests assert; with the fake's `sampled()` True, the same raising route also sends one transaction with status 500 and `status` "internal_error", with the control that removing the catch-and-re-raise leaves none; a route raising a mapped domain error (404) and a 422 each send no error event, with the control that the same assertion goes red when a 404 is captured on purpose; with `sampled()` True every request sends one transaction whose two timestamps cover a planted 50 ms sleep in the route and whose `transaction` names the template and not the path, with it False none, and `/healthz` none either way; a CORS preflight (`OPTIONS` with `Origin` and `Access-Control-Request-Method` against an allowed origin) answers 200 from CORS and sends no transaction with `sampled()` True, with the control that the same assertion goes red when the `OPTIONS` skip is removed; the stack read from `app.user_middleware` lists `CORSMiddleware` after (inside) `TelemetryMiddleware` and the four request-scoped middlewares before (outside) it; with no DSN, `app.state.telemetry.enabled` is False, `threading.active_count()` is unchanged by `create_app`, and every existing API test passes unchanged; `wholetree.sh` fast mode is green with the two seams in place.
