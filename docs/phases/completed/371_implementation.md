## Goal

Phase 273 built and proved payments in test mode: the gateway in `src/motodiag/payments/stripe_api.py`, the shops' connected accounts, the simulated card reader, the Checkout pay-link, and the one place news of a payment is applied, `dispatch_event` in `src/motodiag/billing/webhook_handlers.py`, reached today only through the signed webhook route `stripe_webhook` in `src/motodiag/api/routes/billing.py`. That route is on a server the internet cannot reach: live is on the home desktop, served on loopback and reached over the tailnet only (Phase 382, the operator's decision 3 of 2026-09-28). So in production nothing tells the server a customer has paid, and an invoice stays unpaid in the records however many times the card reader says approved.

The operator answered the fork on 2026-11-05 (K65): option A of `docs/reports/2026-11-05_stripe_options.md`, with three additions. The server asks Stripe for new events about every 20 seconds, for the platform account and each connected shop, and hands them to the existing handler; its place in the news is stored in the database, so a restore from a backup repairs itself; the backend stays tailnet-only. The three additions: an alarm outside the desktop (a check-in to a Sentry job monitor every 5 minutes, so Sentry emails the operator after about 15 minutes of silence), a daily limit check that sends one notice at 50 connected shops, at 100 connected shops, when news runs more than 2 minutes late or when Stripe refuses asks, and the upgrade steps written into the guide with a paused ROADMAP row and its prompt ready.

Step 0 classified this phase an extension, and this plan keeps it one: the webhook route, the handler and the gateway's refusal of a live key outside `env=prod` are not changed. Everything new sits beside them. The fleet starts before the live account exists (K66): the build tests with stand-ins, and the live key is first used in the operator's step after the merge, as 343 and 345 did with theirs.

After this phase:

1. A long-running job, `motodiag payments feed run`, asks Stripe for the eight event types the handler knows, for the platform account and for every connected shop, every 20 seconds, and feeds each event to `dispatch_event`. Its place per account is a row in a new table, and a round that finds the place older than the backup's time asks again from there.
2. Every 5 minutes the job checks in with a Sentry job monitor, through the DSN Phase 343 already reads; a stopped job, a dark desktop or a dead internet connection all end the check-ins, and Sentry emails the operator.
3. Once a day the job measures the four lines K65 names and sends one notice when a line is crossed, naming the guide's page.
4. `docs/guide/payments.md` tells the operator, in plain English, how news of a payment reaches the server, how to see that the feed is running, what each notice means and the steps of the upgrade; the ledger holds the upgrade as a paused row with its prompt written.
5. `motodiag config show` masks `stripe_webhook_secret` (F248), before any live secret sits in `server.env` beside it.
6. The desktop gets a unit for the job, `ops/desktop/motodiag-payments.service`, installed by one script as 345's backup unit was.

At the close-out (v1.1, 2026-11-08) all six are built and migration 089 is on live. None of them runs on live yet: the unit and the live key are the operator's steps after the merge, and those steps wait on the public address (F257, under Deviations).

2. **`src/motodiag/payments/event_feed.py`** (new): the asks and the place. Six new settings on `Settings` in `src/motodiag/core/config.py`, read from the environment with the `MOTODIAG_` prefix like every other, each with K65's number as its default and a comment naming the operator's decision: `stripe_poll_interval_s: int = 20`, `stripe_poll_checkin_s: int = 300`, `stripe_poll_monitor_slug: str = "motodiag-payments-feed"`, `stripe_feed_shops_plan: int = 50`, `stripe_feed_shops_upgrade: int = 100`, `stripe_feed_late_s: int = 120`. The module:
   - `FEED_TYPES` is the tuple of the eight keys of `HANDLERS` in `webhook_handlers.py`, read from that dict at import so the two cannot drift; a test holds the equality.
   - `accounts(settings, db_path) -> list[str]`: `platform`, then every `stripe_account_id` in `shop_payment_accounts` whose `livemode` equals the key's mode (`1` for a live key, `0` for a test key, by `stripe_api.is_test_key`), ordered by `shop_id`.
   - `poll_account(client, account, settings, db_path, clock) -> RoundResult`: reads the account's cursor row; with none, the place is the clock's time less the overlap. The overlap is 300 seconds: every round asks from `last_created - 300`, because Stripe's `created` times are not delivered in strict order, and a repeat costs nothing since `dispatch_event` acknowledges a seen `event_id` without its handler. A place older than 30 days is raised to 30 days back (Stripe keeps no more) and the gap is recorded in `last_error`. It asks `GET /v1/events` through `stripe_api.call` with `created[gte]`, `types` set to `FEED_TYPES` and `limit=100`, and follows `has_more` with `starting_after` until the page is short; for a shop it passes `stripe_account` as the request option, so the SDK sends the `Stripe-Account` header the call log already records. Events are handled oldest first. An event whose `account` is missing gets the shop's id written in before dispatch, because `_check_source` in `invoice_payments.py` compares it with the row's account and the options page records that Stripe's pages do not promise the name on a listed event. Each event goes to `dispatch_event(event, db_path=…, provider=get_billing_provider(settings=…), settings=…)`; a `retry=True` result leaves the cursor where it was, so the next round asks for the event again; `LiveEventRefused` is recorded in `last_error` and the round goes on. After the account's events are handled the cursor row is written: `last_created` (the newest `created` seen, never moved back), `last_event_id`, `polled_at`, `last_error` (`NULL` on a clean round), `livemode`.
   - `poll_once(settings, db_path, clock) -> list[RoundResult]`: `accounts`, then `poll_account` for each; a `StripeUnavailable` for one account is written to that account's `last_error` and does not stop the others. `RoundResult` carries the account, events seen, events handled, the largest lag (handled time less `created`), and the error's `kind` when there was one.
   - `run_forever(settings, db_path, *, clock, sleep, stop)`: a round, then a wait of the interval; after a `busy` (429) or `unreachable` answer the wait doubles up to 300 seconds and comes back to the interval on the next clean round; the warning is logged at most once a minute, the way `Sender._warn` does. It calls the monitor's check-in (item 3) when `stripe_poll_checkin_s` has passed since the last, and the limit check (item 4) at start and then on the first round of each UTC day. Every exception a round raises that is not one of the gateway's is logged with `logger.exception` and the loop goes on; nothing in the module is `except Exception: pass`, so `SWALLOWED_EXCEPTIONS` stays 22.
   - Nothing here prints or logs a key, a secret or a payload: the log names the account id, the event id, the type and the outcome.
   Finish line: with `FixtureHTTP` answering `(status, body)` tuples built in the test, one round against the platform and one shop makes exactly the asks named above, in that order, with `created[gte]` 300 seconds before the stored place, `types` equal to the eight, and the shop's ask carrying `Stripe-Account`; a two-page answer is followed by `starting_after` the first page's last id; a built `payment_intent.succeeded` event for a started payment, with no `account` field, is handed to the handler with the shop's id and the invoice turns paid; the same event on the next round is acknowledged and nothing changes; a cursor set back to before the payment (the restore) makes the next round ask from there and the paid invoice stays paid with no second payment row; a cursor 40 days old is asked at 30 days and `last_error` says so; a `busy` answer doubles the wait, seen through the injected `sleep`, and a clean round brings it back; a `retry=True` dispatch leaves `last_created` unchanged; a live-mode event under `env=dev` is recorded in `last_error` and the round finishes; `FEED_TYPES` equals `HANDLERS.keys()`, with the control that a planted ninth type turns the test red.
