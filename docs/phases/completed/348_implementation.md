**Version:** 1.1 | **Tier:** Standard | **Date:** 2026-10-30 (v1.0 `85b2db5`)

## Goal

A shop can answer "who did what, and when". Today nothing records it: Step 0 found no audit log, event log or `log_event` in src (its census, run on this branch from `47b93ea`). The pieces that look like one each record one thing: Phase 10's log lines, Phase 166's and 167's own audit tables, and the Stripe webhook record in `src/motodiag/billing/webhook_handlers.py`. Nothing enforces append-only behaviour on any of them. Phase 303 shipped staff logins and left the resolved caller on every credentialed request, `request.state.caller` (user id, credential kind, credential id), for this phase to read (`docs/phases/completed/303_implementation.md`, Goal: "What this makes for Phase 348").

This phase ships the row's three promises, as an extension (Step 0's classification), changing no existing route's or command's behaviour:

- **Immutable event log.** One event per write request on the API (POST, PUT, PATCH, DELETE), recorded by one middleware from the caller 303 leaves on the request: who (user id, username at the time, credential kind and id, client address), what (method, path without its query string, the handler's name, the path's ids, the shop when the path names one, the status) and when (UTC). The log is a new table of the main database, `audit_events`, added by migration 088: two triggers refuse UPDATE and DELETE, and every row carries a hash chained to the row before it, so a change or a removal in the middle is found by `motodiag audit verify`.
- **Security audit trail.** Two readers: `motodiag audit list` for the operator (the whole trail, filtered by user, shop, time and path, with `--json`), and `GET /v1/shop/{shop_id}/audit` for a shop member who holds `manage_users` at that shop, showing only that shop's events. Logins, failed logins, logouts, password changes and the owner's resets are in the trail by the same rule as every other write, because they are writes.
- **Compliance readiness.** What a compliance reader does: `motodiag audit verify` proves the chain intact and prints the count and the head hash; `motodiag audit export` writes the trail as JSON lines to a file the operator keeps. Nothing is ever deleted from the log, and no request body, query string, password or token is ever in it.

**Where the log lives: the operator's decisions.** The log is a table of the main database, made by migration 088 and built by the fleet through 395's database step; it is not a file of its own. That is K58 (`docs/decisions.md`, 2026-10-29), whose recorded words are the operator's "yes go ahead" to the advisor's reading of their "add it altogether to throw at it" on 348's database fork: "Phase 395, built by a builder session, gives the fleet the database step (F232 …), and then the fleet builds all of 348, its new table included." The plan of record's entry of 2026-10-29 says the same: "348, the audit log, needs a new table: its Step 0 (`abbafd4`, on its branch) finds no event store to extend." Two consequences follow, one settled and one pending the operator's merge:
- **The migration has a path.** Phase 395 closed F232: a plan with a migration names it under "The database step" below, the Chief Engineer stops after the regression of record with the outcome `deploy`, and the operator applies it from one paste block (`.claude/skills/deploy/through_fleet.py`), before the close-out (K18's order).
- **The deploy gates hold with a server that writes the table.** The gates compare live with its backup and set aside only what the running API writes by itself (`SERVER_WRITES` in `.claude/skills/deploy/deploy.py`, F208, F210); an audit table gains a row on every write request, so without an entry every apply and every `verify-live` after 348 would refuse. 3. **`src/motodiag/audit/__init__.py` and `src/motodiag/audit/log.py`** (new): the store, on the main database. `append_event(conn, event) -> int` runs one `BEGIN IMMEDIATE` transaction: it reads the last row's id and `row_hash` (the first row's `prev_hash` is `GENESIS`, sixty-four zeros), assigns the next id, computes `row_hash`, and inserts. **The hash is one definite thing:** SHA-256 over the compact JSON (no spaces, `ensure_ascii` on) of one JSON array whose elements are, in this order, `prev_hash` and then the row's fifteen fields from `id` to `status` in the table's column order as item 2 lists them (`id`, `occurred_at`, `request_id`, `actor_user_id`, `actor_username`, `credential_kind`, `credential_id`, `client_address`, `forwarded_for`, `method`, `path`, `endpoint`, `path_params`, `shop_id`, `status`), with a null field as JSON `null` and `path_params` as the stored string. The column list is one module constant, `HASHED_COLUMNS`, that both `append_event` and `verify_chain` read, so there is one order to recompute. `occurred_at` is `motodiag.core.timestamps.utc_now()`, no private helper (the ratchet's `PRIVATE_HELPERS` pin stays 19). `list_events(conn, *, shop_id, user_id, since, until, path_prefix, limit, before_id)` reads newest first. `verify_chain(conn)` walks every row in id order, recomputes each hash from `HASHED_COLUMNS`, checks each `prev_hash` against the row before, checks both triggers exist in `sqlite_master`, and returns the count, the head hash and the first bad id, or that the triggers are missing. `export_events(conn, out_path)` writes every row as one JSON line and refuses an existing file. Connections come from `motodiag.core.database.get_connection` on the database in use, as every other store does.
   Finish line: a row changed in a copy whose triggers were dropped is named by `verify_chain`, and so is a row removed from the middle; a hash recomputed by a test from the array as this item defines it equals the stored `row_hash`; two connections appending at once leave one intact chain; the table holds no `mdk_` or `mds_` text after a request that carried a token in its query string, with the control that a planted token turns the same assertion red; `list_events` on a fresh migrated database returns nothing.
