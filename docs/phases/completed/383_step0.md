## S0-3: Q2, F208's rule

382's row: `api_keys` id 2, `last_used_at` 2026-09-16T15:30:24Z →
2026-10-19T22:27:00Z, written by the phone's requests (M6) five hours after
V-A's apply (backup `motodiag_pre382_20261019_145601.db`). verify-live: `videos
+0 ~6 -0` (approved) and `api_keys +0 ~1 -0` (not), exit 3.

**2A. A named list of columns the running API writes (recommended).**
`deploy.py` holds `SERVER_WRITES = {"api_keys": {"last_used_at"}}`. In a
comparison of **live** with a backup (apply-live's drift check, its
after-apply comparison, verify-live), a change confined to a listed column
of an existing row is dropped; a row whose other fields changed still
shows, without the listed field. The dry runs (on copies, no API) do not
mask, so a migration that writes `last_used_at` still shows in its diff,
and a scope that names a listed column keeps it unmasked. On 382's row:
`api_keys` drops out, `videos +0 ~6 -0` equals the approved diff, exit 0.
Control: a change to `api_keys.name`, `is_active` or `revoked_at` on the
same row, an added `api_keys` row, or a listed column in another table
still fails (exit 3, and apply-live refuses).

**2B. A backup taken at the apply, and the list.** apply-live writes a
second backup immediately before it migrates, and verify-live compares
live with that one. On 382's row it does not help by itself: the write was
five hours after the apply, so 2B without the list still fails exit 3; with
the list, it gives 2A's verdict. What 2B adds is only a newer baseline,
which matters for writes between the dry run and the apply, and those 2A
already masks. Not recommended: more moving parts, the same answer.

**2C. Containment: the approved diff holds, anything outside it is
reported.** verify-live checks that every approved field holds its approved
value and the schema is as approved; any other difference is printed but
fails only if it touches a table, row or schema object the approved diff
names. On 382's row: passes, and so would a shop's new work orders after the
apply, which 2A would fail. Weaker: a write outside the approved diff is
never refused by check 8 (apply-live's own after-apply comparison still
checks equality at the moment of the apply). It becomes the right rule when
the first shop's traffic reaches live; not yet.

**Does apply-live's "changed since the dry run" follow the same rule?**
Recommended: **yes**, with the same list. The approval can take hours with
the API up, and one phone request would refuse the apply; any other drift
still refuses ("Stop and ask"). The alternative is no, with the API
stopped from the dry run to the apply, which takes the app down for the
length of an approval.

**What check 8 does on a machine without live.** Recommended: **unchanged,
it fails** (exit 4 → CHECK 8 FAILED). The close-out's `verify_phase.sh` of
record runs on the desktop, where all fourteen checks can pass (382 ran it
there: thirteen passed, check 8 failed only on F208). Alternatives: (ii)
check 8 prints "not run: live is on <host>" and does not count, with the
desktop's verify-live pasted into the handoff — a check that passes
without seeing live is not evidence; (iii) check 8 runs verify-live on
the desktop through `tailscale ssh` — opens SSH on the desktop, as 382's
rejected 1C would have.

## S0-4: Q3, F205's window

What ships either way: writers store the path relative to
`settings.data_dir` (`videos/shop_1/session_1/1.mp4`); readers resolve
`Path(settings.data_dir) / stored`. Joining an absolute path in pathlib
yields that absolute path, so the reader takes both forms without a second
branch. Migration 087 rewrites each `videos.file_path`,
`work_order_photos.file_path` and `voice_transcripts.audio_path` that is
absolute and carries the routes' layout (`…/videos/shop_N/…`,
`…/photos/shop_N/…`, `…/audio/shop_N/…`) to its suffix from that segment,
so it needs no machine's data folder; anything else is left unchanged.

**What the running server does in the window** (087 applied, the old code
still serving): it reads `Path("videos/shop_1/session_1/1.mp4")` relative to
its `WorkingDirectory`, `/home/lilcu/motodiag/server`, so `/file` and
`/analyze` answer "file missing on disk" for all six videos until the
restart. Nothing is written by those refusals. An upload in the window is
written by the old code with an absolute path, which 087 did not see; the
new reader still reads it, and it stays absolute until a later rewrite.
The analysis worker runs only on a new upload, whose path is absolute, so
it never meets a rewritten row.

**3A. The API stopped from the apply to the restart (recommended).**
`sudo -n systemctl stop motodiag-api.service` just before `apply-live`;
then the close-out commit, the merge, `git -C ~/motodiag/server pull
--ff-only`, `systemctl start`. No old code ever reads a rewritten row, no
upload lands in the window, and the apply itself runs with nothing writing
live. Cost: the app is offline for that stretch (about 15 to 30 minutes:
the close-out commit, the push guard's fast run, the merge). K18's order
is unchanged.

**3B. The new reader first, by a mid-phase merge.** The reader and the
relative writer are merged to master and the server restarted on them;
then the regression of record, 087's dry run and apply, the close-out and
the second merge. No downtime and no window. Cost: code on master before
the phase's regression of record (the push guard runs fast mode only),
two merges in one phase, and the server running branch code the close-out
has not yet verified.

**3C. Accept the window.** The API stays up; the six videos 404 from the
apply to the restart; uploads in it stay absolute. Nothing lost; media
broken for those minutes.
