## S0-2. What reading 176's code against Stripe's current API found: F187

The SDK to pin is `stripe==16.0.0` (PyPI, released 2026-10-01; wheel
sha256 `6a401baf…8c26`). Its `_api_version.py` reads `CURRENT =
"2026-09-30.endive"`, which Stripe's versioning page names as the current
version. Endive is a major release with breaking changes. Against it, 176's
webhook path would not change a tier: the user is never resolved, because
Checkout's `metadata` does not reach the Subscription; the billing period
is read where Stripe removed it in 2025 (Basil); missing values are
invented; event order is trusted; a failed handler is never retried. **Filed
as F187**, with the evidence. This phase fixes it, because "subscription
billing, proved against test mode" cannot pass without it.

Endive also removes `payment_method_types` from Checkout Sessions and
Payment Intents. New code uses `allowed_payment_method_types`, as Stripe's
own Terminal example does (`card_present`).

## S0-4. Decided (the reason for each is here and in the log)

**The SDK.** `stripe==16.0.0` pinned exactly in `pyproject.toml` (a
`[payments]` extra, so the core install does not grow), and the API
version the code sends is set explicitly to `2026-09-30.endive`, with a
test that it equals the SDK's own pinned version. Changing either is a
deliberate change with its own commit. Its dependency `requests` is
already in the venv (2.34.2).

**The money columns.**
- **New code is integer cents only.** New tables store `amount_cents
  INTEGER`; a Stripe amount (`amount`, `amount_received`, `amount_paid`) is
  stored as Stripe gives it, an integer in minor units.
- **`invoices.subtotal`, `tax_amount`, `total` stay as they are.** The
  amount charged is read through one function,
  `invoice_amount_cents(invoice_id)`, which uses 169's `_dollars_to_cents`.
  - Why not change them: 0 live rows, but five modules read them (169's
    invoicing, 277/278's export, 290's analytics, notifications, workflow
    conditions), all converting the same way. Every value is written from
    integer cents by `round(c / 100, 2)`, and that round trip is exact for
    any amount a shop invoices.
  - A test proves the round trip on every cent from 0 to 1,000,000 and on
    boundary values up to 10^11 cents (a billion dollars), so a later
    change that breaks it goes red.
  - Rebuilding the table to INTEGER would rewrite six readers and their
    tests for no measured defect; adding `total_cents` beside `total`
    would make two sources of truth.
- **`payments.amount` is not used.** 0 rows and no production writer. Its
  rows are per user (`user_id NOT NULL`), so a shop's customer paying an
  invoice does not fit it. Payments go into new tables with cents. The
  table and `payment_repo` are left as they are; removing them is a cleanup
  outside this row.

**Webhooks: twice and out of order.**
- An event id is handled once (176's `stripe_webhook_events`, kept).
- An invoice payment moves one way only: started → succeeded, or started →
  failed → succeeded. A late `payment_intent.payment_failed` after
  `succeeded` changes nothing, and a second success for the same Payment
  Intent changes nothing.
- Subscriptions: each subscription event makes the handler **re-read the
  subscription from Stripe** and store that, never the payload's status.
  This is Stripe's own advice ("Don't use `created` to determine event
  order"; "use the API to retrieve any missing objects"), and it makes
  order irrelevant. If the re-read fails, the webhook answers 503 and the
  event is not marked processed, so Stripe (or `stripe listen`) retries.
- Tests replay each event and deliver each pair in both orders; the
  database ends the same.

**An invoice becomes paid only on Stripe's verified event.**
- `payment_intent.succeeded`, signature verified, from the shop's own
  account (the event's `account` is the shop's), for a Payment Intent this
  app started for that invoice (its metadata names the invoice), with
  `amount_received` equal to the invoice's total in cents and the same
  currency. Anything else is recorded against the payment with the reason
  and leaves the invoice as it is.
- The command that starts a payment never marks the invoice paid, and says
  so. Only an invoice that is sent or overdue can be paid; a draft, paid
  or cancelled one is refused.
- `mark-paid` stays, for cash and cheques. A Stripe success on an invoice
  already marked paid is recorded and printed as "paid twice: refund one
  in Stripe", never silently absorbed.
- A refund made in Stripe (`charge.refunded`) is recorded on the payment
  and shown with the invoice; the invoice's status is not changed. No
  refund command is built: row 273 does not name one.

**Card terminals.** Server-driven, Stripe's simulated reader (no app SDK,
no hardware): a location for the shop, a simulated reader registered to
it, a Payment Intent with `allowed_payment_method_types=["card_present"]`
and automatic capture, `process_payment_intent` on the reader, then (test
mode only) `present_payment_method`. The same `payment_intent.succeeded`
rule marks the invoice paid. Automatic capture, because a manual capture
would add a second command and a two-day expiry for no gain here.

**A live key is refused** unless `env` is `prod`: a key starting `sk_live_`
or `rk_live_` stops every Stripe command and the server's provider before
any call, and an event with `livemode: true` is refused the same way. A
planted live-shaped key is the control.

**Secrets.**
- No command prints a key or a secret. `motodiag payments check` prints, for
  each of the key and the webhook secret, only "set" or "not set", and
  "test mode: yes" or "no" from the key's prefix.
- **The keys do not go in `.env`.** They go in a file outside the repo,
  `~/.config/motodiag/stripe-test.env` (mode 600). Only the smoke script
  and the server launched for the webhook run read it, by loading it into
  their own environment. The webhook secret is passed from
  `stripe listen --print-secret` straight into the server's environment
  and never printed.
- **The test session never sees them.** A `tests/conftest.py` fixture clears
  every `MOTODIAG_STRIPE_*` and `STRIPE_*` variable and makes Settings
  ignore Stripe values from `.env`. The proof is a spawned pytest run with
  a planted key in its environment and a planted `.env`: a test inside it
  must not find the key. With the fixture removed, the same run must find
  it (the control).
- Fixtures are signed at test time with a test-only secret
  (`whsec_test_only_…`, built in the test), on a fixed clock: the SDK's
  300 s tolerance reads `time.time()`, so the clock is frozen at the
  signing time, and a second test signs 301 s earlier and must be refused.

**Network.** 281's `tests/support/network_guard.py` holds for the Stripe
SDK too (it sends through `requests` over sockets). A planted test that
calls `stripe` with a fake key must fail on the guard.

**Migration 080** (new tables, and new columns on one table with 0 live
rows; no existing row changes):
- `shop_payment_accounts`: the shop, its Stripe account id, the
  configuration it was created with, whether `card_payments` is active,
  when last read from Stripe, livemode.
- `invoice_payments`: the invoice, the shop's account, the channel
  (checkout or terminal), the Checkout Session and Payment Intent ids,
  `amount_cents`, currency, status, when started and settled, the reason a
  payment did not settle the invoice, refunded cents.
- `terminal_locations` and `terminal_readers`: per shop, with whether the
  reader is simulated.
- `subscription_payments`: a subscription's Stripe invoice paid or failed,
  with `amount_paid_cents` (176's `invoice.payment_succeeded` was a no-op).
- `stripe_webhook_events` (0 live rows) gains `account` and `livemode`
  columns.
It goes through the deploy skill. The dry run must show new tables, the two
new columns and the `schema_version` row, and no existing row changed.

**The server stays as it is live:** no keys, no provider switch, no new
listener. The webhook run uses a server started by hand on a scratch copy
of the database.

## Questions for the operator

### 1. Connect: how a shop receives its customers' money

Stripe's current model is the Accounts v2 API, where an account has
*configurations*; the old names Standard, Express and Custom are legacy
(`273_sources.md`, C1–C3). Each option below is what this phase would ship.

**(A) Each shop is a connected account: `merchant` configuration,
`dashboard: full`, Stripe collects fees and carries losses
(`fees_collector: stripe`, `losses_collector: stripe`), direct charges.
(Recommended.)** Stripe calls this the "Stripe-owned pricing model" for a
SaaS platform.
- **Fees:** the shop pays Stripe's fees directly. You earn through the
  subscription tiers. An application fee per payment is possible later
  (Stripe deducts it for you); this phase sets none.
- **Refunds and disputes:** taken from the shop's Stripe balance; Stripe,
  not you, is liable if that balance goes negative. The shop handles them
  in its own Stripe Dashboard.
- **Onboarding:** `shop payments connect` creates the account and prints a
  Stripe-hosted onboarding link. The shop owner fills in Stripe's form
  (business, owner's identity, bank account); Stripe does the identity
  checks (KYC). In test mode it accepts test data.
- **Terminal:** the shop owns its readers and locations.
- **What you do once:** turn on Connect for your platform in the
  Dashboard (test mode), choosing a SaaS platform.

**(B) Each shop is a connected account, but you collect the fees and carry
the losses (`fees_collector: application`, `losses_collector:
application`), `dashboard: express` or `none`.** Stripe's "buy rate" model.
- **Fees:** Stripe charges you; you set an application fee per payment to
  cover them, and your margin is what you set.
- **Refunds and disputes:** still taken from the shop's balance, but if it
  goes negative, **you** are liable, and Stripe holds a reserve on your
  balance. You run risk management.
- **Onboarding:** the same Stripe-hosted form; with `dashboard: none` you
  also take on KYC collection. The shop has a limited dashboard or none, so
  refunds would need a command here.
- More for you to run and to carry; nothing in this batch needs it.

**(C) One Stripe account, the first shop's; Connect later.** The shop
signs up with Stripe itself and its keys are put in this app.
- **Fees, refunds and disputes:** all the shop's, in its own Dashboard.
- **Onboarding:** none in the app; the shop's ordinary Stripe sign-up.
- **What it ships:** invoice payment and Terminal for one shop. The Connect
  verb is not built; it becomes a paused row. The app holds a shop's
  secret key, and a second shop means building Connect then and moving
  the first.
- Your own subscription income would be a separate Stripe account.

Destination charges (the platform as the seller, fees and disputes on
you) are not offered: a shop's customer buys from the shop, and Stripe
recommends them for marketplaces.
