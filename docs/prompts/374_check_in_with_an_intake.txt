The measured facts, taken 2026-10-06 on master at 5f9097b. Re-verify each at Step 0.
- **Check-in** (`check_in`, scheduling/booking.py:410; `shop appointment check-in`, whose only option is `--wo`):
  - with `--wo`, it links an existing work order that isn't finished;
  - without it, it creates and opens a work order with no intake.
  - A checked-in appointment cannot be checked in again.
- **An intake** (`intake_visits`) records the shop, customer and bike, the mileage at intake, the reported problems, who took it, and its status (open, closed or cancelled). It is made by `shop intake create --shop --customer --bike --mileage --notes`. `shop intake open-for-bike` finds a bike's open intake.
- **A work order's `intake_visit_id` cannot be changed, by design.** shop/work_order_repo.py, at the update whitelist, says that if a mechanic captured the wrong intake, the work order is cancelled and recreated rather than mutating cross-table state. So today the hand-off holds only in one order: `intake create`, then `work-order create --intake`, then `check-in --wo`.
- **What the gap costs:** 373's claim packet reads the mileage at intake when the work order has an intake (inventory/warranty_claims.py:402), and otherwise the bike's recorded mileage. A work order opened by check-in never has one.
- **The API** has intake routes (`/{shop_id}/intakes`, api/routes/shop_mgmt.py) but no appointment or check-in route. So a CLI-only change leaves the app's API snapshot alone.
- **Live**, on a copy at 23:00: 0 appointments, 0 intakes, and 6 work orders, none with an intake. There is nothing to backfill.
